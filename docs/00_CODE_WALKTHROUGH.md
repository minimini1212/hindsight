# 코드 개관 — 어디에 무엇이 있고, 왜 그 모듈이 있나

> **최종 갱신: 2026-09-15**
>
> 🎯 **고리가 한 바퀴 돈다** — 기록 → 되돌리기 → 재생 → 채점 → 테스트 생성 →
> **그 테스트를 진짜로 돌리기**. 버그가 있는 코드에서 실패하고 고치면 통과하는 것을 측정했다.
> 🔴 아직 없는 것은 **진단(LLM)** 이다. 그리고 「고친 코드」는 아직 사람이 써 둔 것이라,
> **「LLM 이 고칠 수 있는가」는 확인된 바 없다.**
>
> | | 지금 |
> | --- | --- |
> | 모듈 | **4개** 있다 (전체 계획은 **6개** — §2) |
> | 소스 | 자바 **94개** (model 10 · core 40 · recorder-simple 22 · demo-app 22) |
> | 검사 | **237건** 통과 (core 162 · recorder-simple 43 · demo-app 32) |
> | 빌드 | Gradle 9.3 · 이중 툴체인 **실측 확인** — model major=61(Java 17), core major=65(Java 21) |
> | 빌드가 막는 것 | 문서 링크 · 에이전트 의존성 · 🔄 **기록기 의존성**(새로 생김) |
>
> 🔄 **왕복 검사가 한 겹 깊어졌다.** 2026-09-10 에는 **core 가 쓰고 core 가 읽는** 왕복뿐이었다.
> 이제는 **기록기가 만든 파일을 core 가 읽는다.** 다만 아직 코덱이 한 벌이라
> «진짜» 위험(쓰는 쪽과 읽는 쪽이 두 벌)은 v1 에이전트가 손으로 JSON 을 쓸 때 검사된다.
>
> 코드가 생길 때마다 이 문서를 **같은 커밋에서** 갱신한다 — 모듈 지도, 파일별 역할,
> 그리고 위의 「최종 갱신」 날짜까지.

## §0. 이 문서를 처음 보는 사람에게

| 말 | 뜻 |
| --- | --- |
| **에이전트(agent)** | 관측 대상 앱과 **같은 JVM 안에서** 도는 우리 코드. `-javaagent` 옵션으로 붙는다 |
| **계측(instrumentation)** | 원본 소스를 안 고치고 실행 시점에 코드를 끼워 넣는 것 |
| **경계(boundary)** | 프로세스 밖과 값이 오가는 자리. HTTP 요청·응답, DB 질의, 시각, 난수 |
| **기록(recording)** | 사고 순간 앞뒤의 경계 값을 묶은 파일 하나 |
| **재생(replay)** | 저장한 기록을 다시 흘려 넣어 그때 일을 한 번 더 일으키는 것 |
| **오라클(oracle)** | 테스트가 「맞았다/틀렸다」를 판정하는 기준. **입력만으로는 테스트가 아니다** |
| **셰이딩(shading)** | 의존 라이브러리를 내 패키지 이름 안으로 옮겨 남의 것과 안 부딪히게 하는 것 |
| **툴체인(toolchain)** | 이 모듈을 어느 자바 판으로 컴파일할지. 모듈마다 다르게 줄 수 있다 |
| **믹스인(mixin)** | 원본 클래스를 안 고치고 「이 클래스는 이렇게 읽어라」를 밖에서 알려주는 방식 |

## §1. 전체 흐름 — 이 도구가 하는 일

한 줄로 이렇다.

```
자바 앱이 사고 나면 → 그 순간을 기록해 → 재생해 실패 테스트를 만들고 →
LLM 이 고치면 → 재생으로 걸러낸 뒤 → PR 을 올린다.   배포는 사람이 한다.
```

여섯 마디이고, 각 마디가 모듈 하나에 대응한다.

```
   [관측 대상 앱의 JVM 안]              │        [바깥]
                                        │
   demo-app                             │
      │  요청이 들어오고 SQL 이 나간다   │
      ▼                                 │
   recorder-simple  (v0)                │
   agent            (v1)                │  ← 같은 일을 하는 두 벌.
      │  경계 값을 링 버퍼에 담는다      │     v1 이 v0 을 대체한다 (§2-1)
      │                                 │
      │  사고! (예외 · 지연)             │
      ▼                                 │
   ┌──────────────┐                     │
   │ 기록 파일     │ ────────────────────┼──▶  core       파일을 읽는다
   │ recording.json                     │       │        「모름」을 살려서
   └──────────────┘                     │       ▼
        ▲                               │     replay     다시 흘려 넣는다
        │ model 이 이 파일의 «모양»을 정한다     │        + 🔴 오라클 (무엇을 검사하나)
        │ 안쪽과 바깥쪽이 같은 model 을 쓴다     ▼
                                        │     brain      LLM 진단 → 패치
                                        │       │        ↕ 네 겹 채점
                                        │       ▼
                                        │     guard      🔴 패치가 건드려도 되는 경로인가
                                        │       │        파일을 쓰는 유일한 통로
                                        │       ▼
                                        │      PR        사람이 머지한다
```

🔴 **`model` 이 경계선 위에 걸쳐 있는 것이 이 구조의 핵심이다.** 앱 «안»에서 도는 코드와
«밖»에서 도는 코드가 **같은 자료 구조**를 써야 기록이 오간다. 그런데 안쪽은 남의 클래스패스라
의존성을 못 늘린다. 그래서 `model` 만 따로 떼어 **의존성 0, Java 17** 로 묶어 뒀다.

## §2. 모듈 지도 — 🔴 모듈은 6개뿐이고, 나누는 기준은 하나다

> 🔴 **모듈은 「누구의 클래스패스에 올라가나」로만 나눈다.**
> 읽기·재생·진단·명령줄 같은 구분은 전부 **패키지**다 (§3).
>
> ⚠️ 한때 13개로 나눴다가 **6개로 접었다** (2026-09-10). 「개념이 다르니 모듈도 다르게」로
> 나눴더니 클래스 한두 개짜리 모듈이 다섯 개 생겼고, *"이게 다 뭐냐"* 는 질문을 받았다.
> 🧭 무엇이 틀렸는지: [`rules/module-boundary-decision.md`](rules/module-boundary-decision.md)
>
> ⚠️ **모듈 폴더는 첫 파일을 쓸 때 그때 만든다.** 빈 폴더는 「누가 시작해 놨나」로 읽혀서,
> 다음 사람이 매번 열어 보고 비었다는 것을 확인해야 한다. 없으면 그 질문이 안 생긴다.

### 왜 「클래스패스」가 기준인가

관측 대상 앱 «안»에서 도는 코드는 **의존성을 함부로 못 늘린다.**

> 우리가 끌고 들어간 Jackson 2.17 이 그 앱의 2.15 와 부딪히면
> **우리 도구가 아니라 그 앱이 죽는다.**

그래서 「안으로 들어가는 것」과 「밖에 있는 것」은 **반드시** 갈려야 한다. 이건 취향이 아니라
물리다. 그 밖의 구분은 모듈로 갈라도 얻는 게 없다.

### 안으로 들어가는 것

| 모듈 | 있나 | 자바 | 역할 | 🔴 왜 «반드시» 따로여야 하나 |
| --- | --- | --- | --- | --- |
| `hindsight-model` | ✅ **있다** | **17** | 기록 파일의 자료 구조. record 뿐 | **안팎이 같이 쓰는 유일한 것.** 여기 라이브러리를 하나 붙이면 그게 남의 JVM 으로 간다 |
| `hindsight-recorder-simple` | ✅ 🔄 **있다** | 21 | v0 기록기. `Filter` + `DataSource` 감싸기 | 🔄 **2026-09-15 에 「모듈로 둔다」로 정했다.** 이 코드는 관측 대상 앱 «안»으로 들어가고 `core` 는 «밖»에 있어서, §1 의 기준대로 갈린다. 딸려 오는 것이 없는지는 빌드가 센다 (§2-4) |
| `hindsight-agent-boot` | ⬜ v1 | **17** | 부트스트랩에 올라가는 얇은 껍데기 (100줄 남짓) | **다른 클래스로더다.** 같은 jar 에 물리적으로 못 넣는다. 없으면 `NoClassDefFoundError` 로 **JVM 이 아예 안 뜬다** |
| `hindsight-agent` | ⬜ v1 | **17** | `premain` · 계측 · 링 버퍼 · 방아쇠 · 덤프 | 셰이딩된 별도 jar 이고 manifest 가 다르다 |

🔴 **Java 17 인 셋은 전부 여기 있다.** 실무에 Java 17 앱이 여전히 더 많고, 붙을 수 있는 앱이
많을수록 쓸모가 커진다. (`recorder-simple` 만 21 인 이유: demo-app 과 함께 쓰이는 v0 임시 코드라
호환 범위가 필요 없다.) 🧭 [`rules/stack-decision.md`](rules/stack-decision.md)

### §2-0 🔴 `hindsight-core` 안의 패키지 지도

모듈로 안 나눈다고 구분이 없는 게 아니다. **패키지로 나눈다.**

| 패키지 | 있나 | 역할 | 🧭 왜 따로 두나 |
| --- | --- | --- | --- |
| `core.store` | ✅ **있다** | 기록 읽기·쓰기, 판 번호 검사 | Jackson 이 여기까지만 온다 |
| `core.privacy` | ✅ 🔄 **있다** | 가명화 | 🔴 **한 곳에서만 한다.** 여러 곳에 흩으면 언젠가 한 곳이 빠지고, 그 순간 원본이 디스크에 남는다. 그래서 부르는 자리를 «쓰기와 같은 함수 안»에 묶었다 (`store/RecordingStore`) |
| `core.replay` | 🔄 **채점만 있다** | 재생 · **오라클** · JUnit 생성 | 🔴 오라클(무엇을 검사하나)을 재생과 **같은 자리**에 둔다 — 「입력만 재현하고 판정을 안 정하는」 실수가 이 프로젝트에서 가장 늦게 발견된 구멍이었다 |
| `core.guard` | ✅ 🔄 **있다** | 패치가 건드려도 되는 경로인지 검사 + 🔴 **파일을 쓰는 유일한 통로** | ⚠️ 한때 «모듈»이었다. 「파일을 쓰는 유일한 통로」라는 이유였는데 **모듈 경계는 파일 쓰기를 못 막는다** — 다른 코드가 `java.nio` 를 직접 부르면 그만이다. 막는 척한 것이었다 (§2-3) |
| `core.brain` | 🔄 **채점만 있다** | LLM 진단 · 네 겹 채점 · PR — 🔴 LLM 과 PR 은 아직 없다 | — |
| `core.cli` | ✅ 🔄 **있다** | `hs list` · `hs show` | 🔴 담긴 시간이 짧으면 **눈에 띄게 경고**한다. 의존성 0 |
| `core.mcp` | ⬜ v3 | 코딩 에이전트용 통로 | — |

⬜ **의존 방향은 아직 검사가 없다.** 「`replay` 가 `brain` 을 몰라야 한다」 같은 규칙은
지금 사람이 지킨다. 검사로 바꾸는 것은 TODOS 에 있다 — 모듈 다섯 개보다 검사 한 개가 싸다.

### §2-1 🔴 기록기가 왜 두 벌인가 (`recorder-simple` 과 `agent`)

같은 일을 하는 모듈이 둘이라 이상해 보인다. 일부러 그렇게 했다.

```
v0   recorder-simple    Filter + DataSource 감싸기      200줄, 오늘 된다
      └─ 소스를 고쳐야 한다. 아무 앱에나 못 붙는다
v1   agent              premain + ByteBuddy + 셰이딩    4~6주, 위험하다
      └─ 옵션 한 줄로 아무 앱에나 붙는다
```

처음 계획은 `agent` 부터 만드는 것이었다. 뒤집은 이유:

> 🔴 **일정이 밀리면 잘려나가는 건 항상 뒤쪽이다.** 그런데 뒤쪽에 이 프로젝트의 존재 이유
> (채점 고리)가 있었다. **잘릴 가능성이 가장 큰 것이 하필 핵심**이었다.

`recorder-simple` 로 먼저 고리를 한 바퀴 돌리면 **3주 뒤에 데모 영상이 나온다.**
그다음 기록기만 갈아끼운다. 이때 **이미 도는 시스템이 회귀 검사 역할을 한다** — 같은 상황에서
두 기록기가 같은 기록을 만드는지 비교하면 된다.

⚠️ **버리는 값은 나흘쯤이다.** 그 대신 「위험보다 데모가 먼저 온다」를 산다.
🧭 근거: [`rules/build-order-decision.md`](rules/build-order-decision.md)

### §2-2 🔴 `demo-app` 은 왜 「진짜」여야 하나

`demo-app` 은 버그를 심을 대상이니 대충 만들어도 될 것 같다. 그런데:

> 이 프로젝트를 다 끝내도 **스프링 코드를 거의 안 쓴 상태**가 된다. 자바·스프링 자리에
> 지원하면서. 그리고 **바이트코드 계측을 평가할 수 있는 면접관은 소수다.**
> ⚠️ 평가할 수 없는 포트폴리오는 높은 점수가 아니라 **0점**을 받는다.

그래서 JPA 연관관계·트랜잭션·페이징·Redis·Docker Compose·CI 를 갖춘 서비스로 만든다.
포트폴리오가 두 겹이 된다 — *"스프링 서비스를 만들었고, 그걸 디버깅하는 JVM 에이전트도 만들었다."*
앞쪽은 누구나 평가할 수 있고 뒤쪽은 아는 사람이 알아본다.

### §2-3 ⚠️ `guard` 를 모듈로 뺐던 것이 왜 자기기만이었나

원래 이유는 이랬다: *"패치 경로 검사를 자기 모듈에 두면, 우회하려면 눈에 띄게 이상한 것을
import 해야 한다."*

**틀렸다.** 모듈 경계는 파일 쓰기를 **못 막는다.** 같은 프로젝트의 다른 코드가
`java.nio.file.Files` 를 직접 부르면 그만이고, Gradle 은 그걸 모른다.
그건 우리 모듈을 «우회»한 게 아니라 **애초에 안 쓴 것**이다.

즉 그 모듈 경계는 **장치가 아니라 그림**이었다. 진짜로 막는 방법은 둘이다.

- ⬜ **검사로** — 「`brain` 이 `java.nio` 를 직접 부르면 실패」. 아직 없다 (TODOS)
- ✅ **채점으로** — 이미 있다. 패치가 건드린 경로를 `git apply` **전에** 확인하고,
  재생 테스트는 매번 기록에서 새로 만든다 ([`DESIGN.md`](DESIGN.md) §7-1)

🧭 **그림을 장치로 착각한 것이 이 실수의 본질이다.** 하는 일은 그대로이고 자리만 패키지로 옮겼다.

### §2-4 ⬜ 그래서 6개도 다 강제는 아니다

*"나머지는 꼭 나눠야 하는 것들인거야?"* 를 다시 물어서 하나씩 **「안 나누면 무슨 일이 나나」**로
따졌다. 답이 갈렸다.

| 모듈 | 안 나누면 | 판정 |
| --- | --- | --- |
| `hindsight-agent` | manifest 에 `Premain-Class` 가 있는 별도 jar 여야 하고 셰이딩이 필요하다 | ✅ **물리** |
| `hindsight-agent-boot` | 다른 클래스로더다. 같은 jar 면 `NoClassDefFoundError` 로 **JVM 이 안 뜬다** | ✅ **물리** |
| `hindsight-model` | **v0 에는 아무 일도 안 난다.** v1 부터 물리 | 🟡 **규율** |
| `hindsight-recorder-simple` | 아무 일도 «안 난다» — 그래도 나눴다 | 🔄 **판단** (아래) |

🔴 **진짜 강제는 둘뿐이고 그 둘 다 v1 이다.**

- **`model` 은 규율이지만 이미 값을 했다.** 합쳐 뒀으면 `Integrity.isIncomplete()` 가 샜을 때
  `@JsonIgnore` 한 줄 붙이고 넘어갔을 것이고, v1 에 레코드 여덟 개에서 걷어내야 했다.
  🧭 **나중에 붙이기 어려운 제약은 처음부터 붙인다.**
- 🔄 **v0 기록기는 2026-09-15 에 모듈로 정했다.** 미뤄 뒀던 질문의 답이다.

#### 🔴 `RecordingStore` 가 가명화와 쓰기를 «한 함수 안»에 묶은 이유

나중에 누군가 편의상 코덱을 직접 불러 파일을 쓰고, 그날이 **진짜 사용자 데이터가
디스크에 남는 날**이다. 그리고 파일은 정상으로 보여서 아무도 모른다.

```
write(recording)
   ├─ 1. 가명화          ← 🔴 건너뛰는 «경로가 없다»
   ├─ 2. JSON 으로
   ├─ 3. 파일로
   └─ 4. 총량이 넘으면 오래된 것부터 지운다
```

순서를 바꾸거나 빼려면 이 함수를 고쳐야 하고, 그건 눈에 띈다.

#### 🔴 토큰은 가명화가 아니라 «버린다»

가명화한 값은 **같은 원본이면 늘 같은 가짜 값**이 된다. 이메일에는 그 성질이 필요하다 —
같은 사람이 두 번 나온 것을 알아야 버그가 보인다. 그런데 인증 토큰은 그 성질이
**아무 값도 안 하면서** 「이 토큰을 쓴 요청들」을 이어 준다. 재생에도 안 쓰인다.
값이 없는 위험은 들고 있지 않는다.

🔴 **키가 없으면 가명화 대상을 버린다.** 고정된 가짜 키로 가명화하면
「한 것처럼 보이는데 아무나 되돌릴 수 있는」 상태가 된다 — 그게 가장 나쁘다.

#### 🔴 `Correlation` — 스레드 번호를 쓰면 왜 안 되나

요청이 동시에 열 개 들어오면 SQL 도 열 갈래로 섞여 나간다. 가장 쉬운 방법은
`Thread.currentThread().threadId()` 인데, **가상 스레드는 번호가 재사용된다.**
요청 A 가 끝나고 그 번호를 요청 B 가 받으면 **두 요청의 이벤트가 한 기록으로 합쳐진다.**
스프링 부트 3.2 부터 설정 한 줄로 가상 스레드가 켜지므로, 이건 「나중 일」이 아니다.

#### 🔴 `EventBuffer` — 옮기는 일은 «한» 스레드만 한다

사고 순간에는 큐에 남은 것을 급히 링까지 밀어 넣어야 한다(안 그러면 **사고를 일으킨
바로 그 이벤트가 빠진다**). 처음엔 그때 요청 스레드도 같이 옮기게 만들었는데,
두 스레드가 번갈아 꺼내면서 **링에 들어가는 순서가 섞였다** —
`select 1 · select 3 · select 2`. 재생은 이벤트를 «순서대로» 흘려 넣는 일이라
순서가 섞이면 재생 자체가 다른 일이 된다.

🔴 그래서 옮기는 것은 한 스레드만 하고, 「다 옮겨졌나」는 **큐가 비었나가 아니라
받은 개수와 넣은 개수를 맞춰** 본다. 큐에서 꺼낸 직후·링에 넣기 직전이라는
틈이 있어서, 「큐가 비었나」로 물으면 **마지막 이벤트를 빠뜨린다.**

⚠️ 이 결함은 **스무 번 중 한 번쯤만** 드러났다. 검사에 걸린 것이 운이 좋았다.

#### 🔴 `RecordingCodec` 이 지키는 것 셋

**① `null` 을 생략하지 않는다.** 흔히 `NON_NULL` 로 빈 필드를 지우는데, 여기서는 일부러 안 한다.
`null` 이 「안 봤다/못 봤다」라는 **내용 있는 값**이라서, 지우면 파일만 봤을 때
「못 알아냈다」와 「그런 게 없었다」가 똑같아 보인다.

**② 모르는 판 번호는 거부한다.** 기본값으로 대충 읽지 않는다. 잘못 읽은 재생 결과가
그대로 LLM 진단의 근거가 되기 때문이다. 그리고 **내용을 보기 전에 판 번호부터** 본다 —
순서가 바뀌면 실패 메시지가 「필드 이름이 이상하다」로 나와서 진짜 원인이 가려진다.

**③ 모르는 필드가 있으면 멈춘다.** 조용히 버리면 쓰는 쪽과 읽는 쪽이 갈라진 것을
몇 주 동안 아무도 모른다.

#### `EventMixin` — 클래스 이름을 JSON 에 안 적는 이유

Jackson 에게 종류를 알려주는 흔한 방법은 클래스 이름을 적는 것(`@class`)인데, 그러면
**기록 파일이 우리 패키지 구조에 묶인다.** 나중에 클래스를 옮기면 옛 기록을 못 읽는다.
기록은 오래 남아야 하므로 `HTTP_IN`·`SQL` 같은 **이름을 직접 정해 고정**한다.

정식 기록기는 `hindsight-recorder-simple` 모듈이다. 실험 코드를 지우지 않는 이유는
그 숫자들이 설계를 두 번 바꾼 근거이기 때문이다.

## §6. 아직 안 정해진 것

⬜ **결정하지 않은 것을 코드가 먼저 정하지 않게 한다.** 코드가 먼저 답을 정하면
그건 결정이 아니라 사고다.

- ✅ ~~진짜 서비스의 DB 를 기록 시점으로 어떻게 되돌리나~~ — **2026-09-11 정했다.**
  **스냅숏을 떠 두고 그걸로 되돌린다.** 트랜잭션 롤백은 카운터를 안 되돌려서 재생이 매번
  갈리고, 가짜 DB 는 정석 수정의 질의에 답을 못 준다
  🧭 [`rules/db-restore-decision.md`](rules/db-restore-decision.md)
  ⬜ 남은 것: 운영 규모 복원 시간 — v1 에서 진짜 DB 를 쓸 때 잰다
- **에이전트의 직렬화 형식** — 손으로 짠 JSON 이냐 이진 프레임이냐.
  리뷰는 이진을 권했다(이진 본문·짝 없는 서로게이트에서 JSON 이 깨진다).
  v0 에는 손으로 짠 기록기가 없으므로 **v1 에서 정한다**
- **기록 보관 기간** — 지금은 총량 상한만 있다
- **기록 저장소** — 파일에서 DB 로 옮길 시점. v3 에서 화면이 필요해지면

## §7. ✅ 계획을 떠받치던 가정 — 2026-09-11 전부 실측으로 확인됐다

⚠️ 이 셋이 아니라고 나오면 계획을 다시 짜야 했다. **셋 다 맞았다. 다시 재지 않는다.**

1. ✅ **`Filter` + `DataSource` 감싸기로 만든 기록으로 재생이 성립하는가**
   — 성립한다. 본문을 잡고도 앱이 200 을 돌려주고, 잡은 것«만»으로 재생하니 글자까지 같았다.
   바이트코드를 v1 로 미룬 근거(§2-1)가 유지된다
   🧭 [`reports/2026-09-11/http-capture-experiment.md`](reports/2026-09-11/http-capture-experiment.md)
2. ✅ **SQL 실행 횟수로 N+1 을 잡는 오라클이 실제 JPA 앱에서 안정적인가**
   — 주문 20건에 SQL 21번(1+20). **커넥션 풀 프록시 때문에 두 배로 세이지 않는다.**
   🔄 그리고 「총 횟수」보다 「모양별 반복」이 나은 신호라는 걸 알아내 오라클을 다듬었다
   🧭 [`reports/2026-09-11/sql-count-experiment.md`](reports/2026-09-11/sql-count-experiment.md)
3. ✅ 🔄 **쓰기 요청도 재생으로 채점할 수 있는가** — 할 수 있다. 되돌린 범위만 바꿔 세 번 재 보니
   「쓰기라서 다르다」가 아니라 **「안 되돌려서 다르다」**였다
   🧭 [`reports/2026-09-11/write-replay-experiment.md`](reports/2026-09-11/write-replay-experiment.md)

🔴 **그래서 다음에 만드는 것은 v0 기록기다.** 그 앞을 막고 있던 「DB 를 어떻게 되돌리나」는
2026-09-11 실측으로 정해졌다 — 스냅숏으로 되돌린다
([`rules/db-restore-decision.md`](rules/db-restore-decision.md)).
기록기가 무엇을 남겨야 하는지가 이걸로 정해진다: **복원했는지를 기록에 적을 수 있어야 한다**
([`DATA_CONTRACT.md`](DATA_CONTRACT.md) §7-3).
