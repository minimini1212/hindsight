# v0 기록기를 만들었다 — 그리고 진짜 앱에 붙여 보니 둘이 더 나왔다

> 2026-09-15. [설계](../../DESIGN.md)의 v0 2주차 첫 항목.
> 🔴 **이 문서는 「무엇을 재서 무엇이 바뀌었나」만 담는다.** 구조와 파일별 역할은
> [코드 개관](../../00_CODE_WALKTHROUGH.md)에, 모듈 판단의 근거는
> [모듈 경계 결정](../../rules/module-boundary-decision.md)에 있다.

## 1. 무엇이 생겼나

**기록을 «만드는» 코드가 처음 생겼다.** 그 전까지는 기록을 담는 그릇(`hindsight-model`)과
그 그릇을 읽고 쓰는 코드(`hindsight-core`)뿐이었고, **기록은 손으로 만든 표본밖에 없었다.**

이제 진짜 스프링 앱에 붙은 채로 요청을 받고, 사고가 나면 파일을 떨군다.

```
요청 ──▶ [RecordingFilter] ──▶ 스프링 MVC ──▶ 컨트롤러
   │                                             │
   │                         [감싼 DataSource] ──┘──▶ H2
   │                                 │
   └─ 예외가 났나? 3초를 넘겼나? ─────┴─▶ recordings/…json
```

| 잰 것 | 전 | 후 |
| --- | --- | --- |
| 모듈 | 3개 | **4개** |
| 자바 파일 | 25개 | **49개** |
| 검사 | **23건** | **67건** (core 20 · recorder 28 · demo-app 19) |
| 빌드가 «막는» 규율 | 2개 (문서 링크 · 에이전트 의존성) | **3개** (+ 기록기 의존성) |

## 2. 🎯 미뤄 뒀던 결정 하나를 재서 끝냈다

**「v0 기록기를 따로 모듈로 둘 것인가」** — 이 질문은 [모듈 결정 기록](../../rules/module-boundary-decision.md)
에서 *"만들 때 정한다"* 로 미뤄 둔 것이었다. 미룬 이유는 이랬다.

> 기록을 저장하려면 `core` 의 코덱이 필요하다 → demo-app 이 `core` 를 의존한다
> → **Spring AI 와 picocli 가 관측 대상 앱으로 딸려 들어간다**

**재 보니 전제가 틀렸다.**

| 잰 것 | 숫자 |
| --- | --- |
| demo-app 의 외부 의존성 — 기록기를 붙이기 **전** | **59개** |
| 붙인 **후** | **59개** |
| 늘어난 것 | 🎯 **0개** |

`hindsight-core` 가 «오늘» 쓰는 외부 라이브러리는 Jackson 하나뿐이고(2.18.2),
demo-app 은 `spring-boot-starter-web` 을 통해 **이미 같은 버전**을 들고 있었다.

🔴 **즉 딸려 온다던 것은 「오늘의 core」가 아니라 「미래의 core」였다.**
아직 오지 않은 문제를 근거로 오늘의 구조를 정하고 있었던 것이다.

### 그 미래가 오는 순간을 사람이 기억하지 않게 했다

`core` 가 진단(Spring AI)과 명령줄(picocli)을 갖는 날 이 판단은 뒤집혀야 한다.
그걸 문단으로 적어 두면 **그날 아무도 그 문단을 안 읽는다.** 그래서 검사로 바꿨다.

```
:hindsight-recorder-simple:checkRecorderDependencies
```

✅ **일부러 깨뜨려 확인했다** — picocli 를 한 줄 넣으니 빌드가 실패했고, 되돌리니 통과했다.
🔴 실패 메시지에 *「허용 목록에 이름을 더하는 것은 검사를 끄는 것이지 통과하는 게 아니다」*
를 적어 뒀다.

## 3. 🔴 진짜 앱에 붙여 보니 «따로 떼어 시험할 때는 안 보이던» 결함 둘

여기가 이 날의 가장 값나가는 부분이다. 기록기만 떼어 놓고 한 검사 28건은 **전부 통과**했는데,
같은 코드를 실제 스프링 앱에 붙이자 둘이 드러났다.

### ① 모든 사고의 방아쇠가 `ServletException` 으로 찍혔다

서블릿 컨테이너는 컨트롤러가 던진 예외를 **감싸서** 필터에게 준다. 벗기지 않으면
기록의 방아쇠가 전부 `jakarta.servlet.ServletException` 이 된다.

🔴 **이게 왜 치명적인가**: 같은 사고를 묶는 열쇠가 예외 종류를 포함하는데, 그게 전부 같아지면
**서로 다른 버그가 한 사고로 접힌다.** 그러면 첫 번째 것만 기록이 생기고 **그 뒤로는
기록이 아예 안 만들어진다** — 기록기가 조용히 일을 안 하게 된다.

떼어 놓고 한 검사에서는 **우리가 예외를 직접 만들어 넘겼기 때문에** 감싸는 일이
일어나지 않았다. 🧭 [증상으로 찾는 문서](troubleshooting/기록의-방아쇠가-전부-ServletException-으로-찍힌다.md)

### ② 이벤트가 가끔 순서가 섞여서 링에 들어갔다

사고 순간에는 큐에 남은 것을 급히 링까지 밀어 넣어야 한다 — 안 그러면 **사고를 일으킨
바로 그 이벤트가 기록에서 빠진다.** 처음엔 그때 요청 스레드도 «같이 옮기게» 만들었다.

그랬더니 두 스레드가 번갈아 꺼내면서 들어가는 순서가 섞였다.

```
넣은 것   : select 1 · select 2 · select 3
나온 것   : select 1 · select 3 · select 2      ← 🔴
```

재생은 이벤트를 **순서대로 흘려 넣는 일**이므로, 순서가 섞이면 재생 자체가 다른 일이 된다.

⚠️ **이 결함은 스무 번 중 한 번쯤만 드러났다.** 같은 검사를 다섯 번 더 돌려 확인했다.
🔴 **검사에 걸린 것이 운이 좋았다** — 조금만 덜 돌렸으면 이대로 재생기까지 갔을 것이다.

**고친 방법**: 옮기는 일은 한 스레드만 한다. 그리고 「다 옮겨졌나」를
**「큐가 비었나」가 아니라 「받은 개수와 넣은 개수가 맞나」로** 묻는다 —
큐에서 꺼낸 직후·링에 넣기 직전이라는 틈이 있어서, 큐만 보면 **마지막 이벤트를 빠뜨린다.**
그리고 그 마지막 이벤트가 바로 사고를 일으킨 그것이다.

### 🧭 여기서 배운 것

> **따로 떼어 한 검사는 「우리가 상상한 환경」에서만 통과한다.**
> 둘 다 「감싸는 쪽」과 「같이 도는 쪽」이 있어야 드러나는 종류였다.

설계가 실험 ⑨(진짜 앱에 붙여 돌리기)를 v0 안에 둔 것이 값을 했다.

## 4. 무엇을 확인했나 (실험 ⑨)

`demo-app` 에 붙인 채로 진짜 포트를 열고 요청을 보냈다. 6건 전부 통과.

| 물음 | 결과 |
| --- | --- |
| 🔴 본문 있는 요청이 기록기를 통과해도 앱이 정상인가 | ✅ 200 + 본문 그대로. **본문을 먼저 읽어 버렸다면 400 이 났을 것이다** |
| 예외가 나면 파일이 생기나 | ✅ 생긴다. 방아쇠·진입점·스택이 들어 있다 |
| 요청과 그 요청이 낸 SQL 이 같은 번호로 묶이나 | ✅ 묶인다 |
| 🔴 인증 헤더가 파일에 안 남나 | ✅ `[dropped]` 로 바뀐다 |
| 🔴 담으려던 시간과 담긴 시간이 둘 다 적히나 | ✅ 60 / 0.0x 초로 따로 적힌다 |
| 재생 정보가 `null` 인가 (아직 재생한 적 없음) | ✅ `null` |

## 5. ⬜ 하지 않은 것 — 「모름」으로 적어 둔 자리

🔴 **다음 사람이 「했는데 안 나온다」로 읽지 않게 여기 모아 둔다.**
아래는 전부 파일에 `null` 로 적히고, `null` 은 「안 봤다」다.

| 무엇 | 왜 안 했나 |
| --- | --- |
| SQL 결과 **행**(`rows`) | 세려면 우리가 커서를 움직여야 하는데, 그러면 **앱이 읽을 행이 사라진다** |
| 조회 질의의 **행 수**(`rowCount`) | 같은 이유. 갱신 질의는 셀 수 있어서 «센다» |
| 어느 컨트롤러가 받았나(`handler`) | 알려면 스프링에 물어야 하고, 그러면 기록기가 스프링을 의존하게 된다 |
| git 커밋(`gitCommit`) | v0 이 안 알아본다 |
| 커넥션 풀 표본(`connectionSamples`) | v0 은 풀을 안 본다. 🔴 `[]` 로 적으면 **누수가 「없었다」로 읽힌다** |
| JFR · 재생 정보 | 각각 v2 · 재생기가 생긴 뒤 |
| 나간 요청(`HTTP_OUT`) · 시각 · 난수 | v1 (바이트코드 계측이 필요하다) |

그리고 **아직 «재보지» 않은 것**:

- ⬜ **기록기를 붙였을 때 앱이 얼마나 느려지나.** 한 번도 안 쟀다.
  설계는 성능 측정 하네스를 v0 안에 두라고 했다 — 「나중에 잰다」로 두면 안 재게 되므로.
- ⬜ **이벤트 크기 «어림»이 실제와 얼마나 다른가.** 문자 하나를 2바이트로 보고
  레코드당 256바이트를 얹는 방식인데, 그 어림이 실제 메모리와 몇 배 차이 나는지 모른다.
  바이트 상한이 메모리를 지키는 장치이므로 **이 어림이 틀리면 상한도 틀린다.**

| 검사 | 무엇을 막나 |
