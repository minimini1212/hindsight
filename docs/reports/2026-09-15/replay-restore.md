# 되돌리고 재생해서 채점까지 한 바퀴 — 그리고 채점기가 «잘못된 근거로 통과»하던 것을 잡았다

> 2026-09-15. [재생 채점](replay-oracle.md)을 만든 직후. v0 3주차.
> 무엇을 왜 이렇게 되돌리는지는 [결정 기록](../../rules/db-restore-decision.md)에 있다.

---

## 1. 무엇이 생겼나

**기록을 「되돌린 자리」에서 다시 흘려 넣고 채점까지** 돌아간다. 그 전까지는
「재생해 보니 이랬다」를 사람이 손으로 넣어 줘야 했다.

```
스냅숏을 뜬다        ← 기록 «시점»의 상태
원본 요청을 보낸다    → 기록 파일이 생긴다
세상이 움직인다       → 다른 요청들이 DB 를 바꾼다
되돌린다             ← 스냅숏으로 (행 + 「다음 id 는 몇 번」)
재생한다             → 재생 중에도 «같은» 기록기가 보고 있다
채점한다             → 등급 + 판정
```

| | 전 | 후 |
| --- | --- | --- |
| 검사 | 120건 | **133건** (core 61 · recorder 43 · demo-app 29) |
| 자바 파일 | 63개 | **67개** |

---

## 2. 🔴 채점기가 «잘못된 근거로» 통과하고 있었다

처음 한 바퀴를 돌렸더니 이렇게 나왔다.

```
PARTIAL · 오라클 2/2 통과
  PASS  같은 모양의 질의가 기록보다 더 반복되지 않는다 — 가장 많이 반복된 모양이 1번. 기록의 5번 이하다
  PASS  응답 상태와 본문이 기록과 같다
```

🔴 **코드를 하나도 안 고쳤는데 전부 통과다.** 「N+1 이 그대로인데 왜 통과지」가 이상해서
기록 파일을 열어 봤고, 세 가지가 나왔다.

### ① 기록에는 «그 요청과 무관한 질의»가 섞여 있다

```
전문층 이벤트 16건 중
  corrId = null      14건   ← 스키마 생성 · 테스트 seed
  corrId = r-42cd…    2건   ← 진짜 그 요청이 낸 질의
```

이건 기록기가 틀린 게 아니다. 요청 «밖»에서 난 질의는 상관 식별자가 없는 게 맞고,
없는 것을 지어내지 않는 것이 규율이다. 🔴 **읽는 쪽이 걸러야 하는 것이다.**

### ② 🔴 오라클이 데이터 계약을 어기고 있었다

데이터 계약은 두 층을 가르면서 못 박아 뒀다 — 전문층은 **「재생에 쓸 수 있는 유일한 층」**,
요약층은 **「재생엔 못 쓰고 사람이 원인을 찾는 데 쓴다」**.

그런데 내 오라클이 **요약층을 채점 기준으로 삼고 있었다.** 요약층은 60초 창이라
남의 질의가 들어 있고, 그래서 「기록의 최대 반복」이 **seed 의 `insert` 5번**으로 잡혔다.
재생의 1번이 그보다 작으니 통과 — **아무 상관 없는 숫자를 문턱으로 쓴 것이다.**

**고침**: 진입점의 상관 식별자로 **그 요청이 낸 질의만** 골라 센다.
가려낼 수 없으면 통과가 아니라 **「판정 못 함」**이다.

### ③ 🔴 더 큰 문제 — 오라클이 «구조적으로» 실패할 수 없었다

②를 고치고 나니 이번엔 이렇게 됐다: 기록의 최대 반복 3번, 재생도 3번 → **통과**.

기준이 「기록보다 **더** 나빠지면 실패」였기 때문이다. 🔴 **그런데 기록은 «버그가 있는»
실행이다.** 버그가 그대로인 재생은 기록과 같으므로 «항상 통과»한다.

그러면 **「패치 전에 정말 실패했나」가 영영 참이 될 수 없다.** 데이터 계약이
*"생성된 테스트가 패치 전 코드에서 실패하지 않으면 등급은 `FAILED` 다"* 라고 못 박은 바로 그
조건을 만족할 수 없고, **아무것도 채점되지 않는다.**

**고침**: 「기록 **만큼** 반복되면 실패」로 바꿨다(초과 → 이상).
그리고 기록의 최대 반복이 2번 미만이면 **애초에 반복 결함이 없는 기록**이므로 판정하지 않는다 —
안 그러면 「1번 ≥ 1번 이므로 실패」 같은 헛말이 나온다.

### 고친 뒤

```
PARTIAL · 오라클 1/2 통과 · 못 잡은 것: WINDOW
  FAIL  같은 모양의 질의가 기록만큼 반복되지 않는다 — 한 모양이 5번 반복된다. 기록도 5번이었다
  PASS  응답 상태와 본문이 기록과 같다
```

✅ **N+1 이 그대로이므로 실패.** 이게 「패치 전에 실패했다」를 만드는 자리다.

## 3. 🔴 그리고 시험 자체도 결함을 재현하지 못하고 있었다

②③ 을 고치는 과정에서 하나 더 나왔다. 시험이 심어 둔 데이터가 **주문 5건을 모두 같은 회원**에게
붙이고 있었다. 그러면 하이버네이트가 영속성 컨텍스트에서 같은 객체를 돌려줘서
**회원 조회가 한 번밖에 안 나간다** — 즉 **N+1 이 일어나지 않는다.**

🔴 **재현하려는 결함이 재현되지 않는 시험은, 통과해도 아무것도 말해 주지 않는다.**
주문마다 다른 회원을 붙이도록 고쳤고, 그제야 질의가 1+5 로 나왔다.

## 4. 되돌리기 — 무엇을 확인했나

| 물음 | 결과 |
| --- | --- |
| 🔴 안 되돌리면 정말 갈라지나 | ✅ **갈라진다.** 같은 쓰기 요청이 다른 답을 낸다 |
| 🔴 되돌리면 정말 같아지나 | ✅ **글자까지 같다** |
| 되돌린 것을 «확인»할 수 있나 | ✅ 행 `true` · 「다음 id」 `true` — 되돌린 «뒤에» 다시 물어서 확인 |
| 안 본 것은 어떻게 남나 | ✅ 캐시 `null` · 외부 `null` — 「보았고 못 되돌렸다」(`false`)와 다른 사실 |
| 스키마를 통째로 지웠다 만든 뒤에도 앱이 도나 | ✅ 커넥션 풀과 JPA 가 그대로 돈다 |
| 재생이 기록과 같은 질의를 내나 (갈라짐 오탐) | ✅ `DIVERGED` 아님 |
| 관찰이 없으면 통과로 치나 | ✅ **「판정 못 함」** 이고 자동 PR 이 안 된다 |
| 채점 결과를 기록에 적으면 왕복하나 | ✅ `null` 이 `null` 로 남는다 |

**되돌리는 방법**은 H2 의 `SCRIPT TO` 로 뜨고 `DROP ALL OBJECTS` + `RUNSCRIPT FROM` 으로 되돌린다.
🔴 `DROP` 이 **반드시 앞에 와야 한다** — 없이 `RUNSCRIPT` 만 돌리면 덮어써지는 게 아니라
**행이 더 늘어난다.** 되돌린 게 아니라 두 배가 되는데, 눈에 잘 안 띈다.

---

## 5. 🔴 「가려낼 수 없다」를 「괜찮다」로 접지 않게 한 자리

②를 고치면서 부수적으로 하나가 더 드러났다. 기록에서 그 요청의 질의를 가려낼 수 없을 때
갈라짐 판정이 **조용히 「갈라지지 않았다」**가 되고 있었다. 확인한 적 없는 주장이다.

지금은 그 경우 등급이 `PARTIAL` 이고 `missing` 에 `QUERY_SCOPE` 가 들어간다.

---

## 6. ⬜ 아직 확인 안 된 것

- **운영 규모에서 스냅숏 복원이 몇 초 걸리나** — 안 쟀다. v0 는 재생 환경이 H2 라 문제가
  없고, v1 에서 진짜 DB 를 쓸 때 잰다
- 🔴 **되돌린 「범위」가 DB 안뿐이다** — 앱 안에 쌓인 캐시, 정적 변수, 커넥션 풀 상태는
  **안 봤다**. 그래서 `caches` 가 `null` 이다. 그게 재생을 갈라지게 하는 사례는 아직 못 봤지만,
  **못 봤다는 것이 없다는 뜻은 아니다**
- **오라클이 「나아졌나」만 본다** — 반복이 5번에서 4번으로 줄어도 통과한다.
  「고쳐졌나」를 보려면 무엇이 「고쳐진 것」인지 정의해야 하는데, 일반적으로는 정의할 수 없다.
  ⚠️ 이건 특성화 테스트의 한계이고, 숨기지 않고 적어 둔다
- **동시에 여러 재생을 돌리면 관찰이 섞인다** — 지금은 한 번에 하나씩만 돌린다.
  여러 개를 돌리게 되면 상관 식별자로 걸러야 한다. **그때까지는 동시에 돌리지 않는다**
