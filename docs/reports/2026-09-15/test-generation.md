# 기록을 「실패하는 JUnit 테스트」로 바꾼다 — 그리고 컴파일해 보니 생성물이 혼자서는 안 돌았다

> 2026-09-15. v0 3주차 마지막 항목.
> 왜 생성된 테스트를 믿지 않고 매번 새로 만드는지는 [설계](../../DESIGN.md)의
> 「채점표를 고치지 못하게 막는다」 절(§7-1)에 있다.

---

## 1. 무엇이 생겼나

**기록 하나를 JUnit 테스트 소스로 바꾼다.** 목표는 「통과하는 테스트」가 아니라
**「지금은 실패하고, 고치면 통과하는 테스트」**다 — 패치 전에 통과하는 테스트는
아무것도 증명하지 않고, 그런 테스트로 「고쳤다」를 선언하면 도구는
**아무것도 안 고친 패치로 PR 을 올린다.**

| | 전 | 후 |
| --- | --- | --- |
| 검사 | 133건 | **150건** (core 78 · recorder 43 · demo-app 29) |
| 자바 파일 | 67개 | **71개** |

---

## 2. 🔴 가장 중요한 규칙 — 기록에 «없는» 것은 단언하지 않는다

가장 쉬운 실수는 모든 자리를 다 단언하는 것이다. 그러면 기록이 못 잡은 자리 때문에
**버그와 무관하게 실패하는 테스트**가 되고, 채점기는 그 실패를 「패치가 못 고쳤다」로 읽는다.
🔴 **아무 잘못 없는 패치가 벌을 받는다.**

| 기록의 상태 | 생성물 |
| --- | --- |
| 응답 본문이 `null`(안 잡혔다) | 본문을 **단언하지 않는다**. 「빈 본문이어야 한다」로 바꾸지 않는다 |
| 응답 본문이 `truncated: true` | **단언하지 않는다** — 잘린 것끼리 견주면 「앞부분만 같으면 통과」가 된다 |
| 요청 본문이 `null` | `null` 로 보낸다. 🔴 빈 문자열로 바꾸면 **다른 요청**이 된다 |
| 질의 반복이 1번 | 반복을 **단언하지 않는다** — 애초에 반복 결함이 없는 기록이다 |
| 들어온 요청이 아예 없다 | 🔴 **통과하는 빈 테스트를 만들지 않는다.** 「재생할 수 없다」고 «말하는» 테스트를 만든다 |

그리고 단언 못 한 자리는 **조용히 빼지 않고** 이름으로 남긴다 —
생성된 소스의 머리말과 요약에 「검사하지 «못한» 것」으로 나온다.
🔴 **안 보이면 「다 확인했다」로 읽히기 때문이다.**

### 반복은 「미만」으로 단언한다

```java
assertThat(관찰.worstQueryRepeat()).isLessThan(20);
```

🔴 **「이하」로 두면 기록 그대로인 실행이 통과한다.** 기록은 «버그가 있는» 실행이므로,
버그가 그대로인 재생은 기록과 같다 — 그러면 이 테스트가 **패치 전에 실패하지 않고**,
채점 자체가 성립하지 않는다. (같은 함정을 [하루 전에 채점기 쪽에서도 밟았다](replay-restore.md).)

## 3. 🔴 컴파일해 보니 생성물이 «혼자서는» 안 돌았다

생성된 소스가 진짜 자바인지 보려고 **javac 로 실제로 컴파일하는 검사**를 붙였다.
그랬더니 문법이 아니라 **구조** 문제가 나왔다.

```
GetApiOrdersReplaya1b2Test is not abstract and does not override
abstract method 재생한다(String,String,String) in ReplayTestBase
```

생성된 테스트는 「되돌린다」와 「요청을 보낸다」를 **기반 클래스에 맡기고** 있었는데,
그 기반 클래스가 <b>추상</b>이었다. 즉 **생성물만으로는 컴파일되지 않는다.**

🔴 **되돌리는 방법도 요청을 보내는 방법도 앱마다 다르다.** 어떤 앱은 스프링 부트 테스트로,
어떤 앱은 진짜 포트로, 어떤 앱은 DB 가 H2 가 아니다. **생성기가 그걸 알 수는 없다.**

**고침**: 생성기가 「상속할 구체 클래스 이름」을 **받는다.**
못 받으면 기본값을 넣지 않고 **거절한다** — 「알아서 되겠지」로 기본값을 넣으면
**컴파일 안 되는 소스가 말없이 만들어지고, 그걸 PR 에 붙이게 된다.**

### 그 과정에서 두 번 헛짚었다

| 시도 | 왜 안 됐나 |
| --- | --- |
| 구체 기반 클래스를 시험 클래스 «안»에 중첩 | 생성된 소스는 **패키지 없는** 소스라, 바깥 클래스가 package-private 이면 **접근할 수 없다**. 🔴 그런데 오류 메시지는 그걸 「추상 메서드를 안 채웠다」로 말해서 **원인이 가려진다** |
| javac 의 클래스패스를 기본값에 맡김 | Gradle 테스트 JVM 의 `java.class.path` 를 그대로 믿을 수 없다. **명시로 넘긴다** |

✅ **검사가 진짜로 막는지 확인했다** — 따옴표 이스케이프를 한 줄 빼니 **17건 중 2건이 실패**했고,
되돌리니 통과했다. JSON 본문에는 따옴표가 **반드시** 들어 있으므로, 이 검사가 없으면
**거의 항상** 깨진 소스를 만들어 낸다.

## 4. 🔴 생성물이 스스로 「고쳐도 소용없다」고 말한다

LLM 에게 *"테스트를 통과시켜라"* 라고 하면 **테스트를 지워서 통과시킨다.**
그래서 채점에 쓰는 판단은 **디스크에 있는 소스를 거치지 않는다** — 매번 기록에서 새로 만든다.

생성된 소스 머리에 그 사실이 적혀 있다.

```java
// 🔴 이 파일은 «기록에서 만들어진» 것이고, 채점할 때마다 새로 만들어진다.
//    고쳐도 다음 채점에 반영되지 않는다 — 디스크에 있는 것을 믿지 않기 때문이다.
```

그리고 **같은 기록이면 글자까지 같은 소스**가 나온다(클래스 이름 포함).
이름이 매번 바뀌면 사람이 「전에 본 그 테스트」인지 알 수 없다.

---

## 5. ⬜ 무엇이 아직 확인 안 됐나

- 🔴 **생성된 테스트를 «실제로 돌려» 본 적이 없다.** 컴파일되는 것은 확인했지만,
  그걸 앱에 붙여 「패치 전에 정말 실패하는가」를 본 적은 없다 — 그게 채점 네 겹의 첫 겹이고,
  4주차 과제다
- **관측 대상 앱이 기반 클래스를 아직 안 만들었다.** `demo-app` 에 구체 클래스가 없어서,
  생성물을 demo-app 에서 돌릴 수 없다. 지금 있는 구체 클래스는 **시험용 껍데기**뿐이다
- **생성물을 파일로 «쓰는» 코드가 없다.** PR 에 붙이려면 어딘가에 써야 하는데,
  🔴 파일을 쓰는 통로는 `guard` 하나여야 한다는 규율이 있어서 그쪽이 생긴 뒤에 붙인다
- **질의 파라미터를 단언하지 않는다.** 기록은 값을 들고 있지만 생성물은 모양만 본다.
  값까지 보면 가명화된 값과 재생이 만든 값이 달라서 **버그와 무관하게 실패**할 수 있다 —
  ⬜ 다만 **그게 실제로 문제가 되는지는 안 쟀다**
