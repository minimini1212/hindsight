# 재생 채점을 만들었다 — 그리고 만들기 직전에 조용한 고장을 하나 피했다

> 2026-09-15. v0 3주차의 첫 항목.
> 무엇을 왜 이렇게 판정하는지는 [설계](../../DESIGN.md)의 「재생과 오라클」 절(§6)에 있다.
> 🔴 여기엔 **무엇을 재서 무엇이 바뀌었나**만 적는다.

---

## 1. 무엇이 생겼나

**재생 결과를 채점하는 코드.** 기록 하나와 「재생해 보니 이랬다」를 넣으면
**등급**과 **판정**이 나온다. 🔴 **전부 순수 함수다** — 파일도 DB 도 안 건드린다.

| | 전 | 후 |
| --- | --- | --- |
| 검사 | 80건 | **120건** (core 56 · recorder 43 · demo-app 21) |
| 자바 파일 | 54개 | **63개** |

### 🔴 축이 둘이고, 섞으면 판단이 통째로 망가진다

```
등급(grade)      이 재생을 얼마나 믿을 수 있나     ← ReplayGrader
판정(verdict)    패치가 버그를 고쳤나              ← Oracle
```

**믿을 수 없는 재생에서 나온 「통과」는 통과가 아니다.** 그래서 자동으로 PR 을 올릴지는
둘을 «같이» 본다. 등급이 최고여도 오라클이 하나라도 「판정 못 함」이면 안 올라간다.

---

## 2. 🔴 만들기 직전에 피한 조용한 고장 — 지문을 두 벌로 만들 뻔했다

재생이 「기록에 없는 질의가 생겼나」를 보려면 **질의를 모양으로 접어 지문을 붙여** 기록의
요약층과 대조해야 한다. 그런데 그 계산이 **기록기 모듈 안에만** 있었다.

```
hindsight-recorder-simple  ──의존──▶  hindsight-core
        │                                   │
        └─ 지문 계산이 여기 있었다            └─ 재생이 여기 있다 (거꾸로는 못 본다)
```

의존 방향이 한쪽이라 `core` 가 그 계산을 **쓸 수 없었다.** 그대로 갔으면 재생 쪽에
**두 번째 구현**을 만들었을 것이다.

### 그러면 무슨 일이 났을까

두 구현이 조금이라도 다르면 **모든 질의가 「기록에 없는 것」으로 보인다.**
그러면 **모든 재생이 `DIVERGED` 가 되어 아무것도 채점하지 못한다.**

🔴 **그런데 오류는 하나도 안 난다.** 빌드도 통과하고 검사도 통과한다.
도구가 조용히 쓸모없어지고, 원인을 찾기까지 한참 걸린다.

### 어떻게 했나

계산을 **안팎이 같이 쓰는 유일한 모듈**인 `hindsight-model` 로 옮겼다(`SqlShapes`).
정규식과 SHA-256 은 JDK 가 주는 것이라 **「의존성 0」 약속은 그대로**다.

그리고 그 상태를 지키는 검사를 만들었다 — 기록기가 진짜 기록 파일을 만들고,
재생 쪽이 계산한 지문과 **글자까지 같은지** 본다.

✅ **일부러 어긋나게 해서 막는 것을 확인했다.** 기록기 쪽 계산을 한 글자 바꾸니
**4건 중 2건이 실패**했고, 되돌리니 통과했다. 그중 하나가
「기록과 같은 질의를 다시 내면 갈라졌다고 하지 않는다」 — **조용한 고장을 바로 잡는 자리**다.

## 3. 판정 기준 셋 — 그리고 넷째 결과

| 방아쇠 | 무엇으로 판정하나 |
| --- | --- |
| 예외 | 그 예외가 안 나감 **＋ 응답 상태·본문이 기록과 같음** |
| 지연·N+1 | 🔴 **같은 모양의 질의가 기록보다 더 반복되면 실패** |
| 값이 틀림 | 응답 본문이 기록과 같음 |

### 🔴 예외 방아쇠에도 「응답 대조」가 항상 낀다

「그 예외가 안 나온다」만 보면 **예외를 삼키고 `null` 을 돌려주는 패치가 통과한다.**
본문까지 봐야 「값이 맞나」를 물을 수 있다.

### 🔴 지연을 「시간」이 아니라 「횟수」로 잡는다

N+1 은 예외를 안 던지고 응답도 정상이다. 느려질 뿐인데, **재생 환경에서는 180ms 짜리
지연이 0ms 가 된다** — 시간으로 재면 재생에서 버그가 사라진다.
실행 «횟수»는 그렇지 않고, 게다가 완전히 결정론적이다.

그리고 **총 횟수가 아니라 모양별 반복**을 본다. 문턱은 **기록에서 가져온다** —
기록 당시 가장 많이 반복된 모양의 횟수다. 고정값을 안 쓰는 이유는 어떤 앱은 3번이 정상이고
어떤 앱은 50번이 정상이라, **고정값은 거짓 경보 아니면 놓침 중 하나**가 되기 때문이다.

### 🔴 결과가 넷인 이유 — 「판정 못 함」이 「통과」가 되면 안 된다

| 결과 | 뜻 |
| --- | --- |
| `PASS` | 기준을 만족했다 |
| `FAIL` | 기준을 어겼다 |
| `DIVERGED` | 🔴 기록에 없는 경계를 건드렸다. **통과도 실패도 아니다** |
| `NOT_JUDGED` | 🔴 판정할 자료를 못 봤다. **통과가 아니다** |

가장 흔한 실수는 판정할 자료가 없을 때 조용히 통과시키는 것이다. 그러면 도구가
**아무것도 확인하지 않고 초록불을 켜고**, 그 초록불을 근거로 PR 이 올라간다.

「모름」을 「없음」으로 접지 않는다는 규율이 여기서는
**「판정 못 함」을 「통과」로 접지 않는다**로 나타난다.

## 4. 🔴 `DIVERGED` — 제대로 고칠수록 여기로 온다

N+1 을 고치는 정석은 질의 201개를 **조인 하나**로 바꾸는 것이다. 그런데 **그 새 질의는
기록에 없다.** 즉 **「제대로 된 수정」일수록 재생이 깨진다.** 이걸 실패로 처리하면
채점기가 **얕은 패치를 구조적 수정보다 높게 친다** — 정확히 거꾸로다.

그래서 실패도 통과도 아닌 세 번째 결과로 두고, **무엇이 무엇으로 바뀌었는지**를 붙인다.

```
before  select * from member where id = ?    20번
after   select * from orders o join member m on o.member_id = m.id    1번
verdict 질의 20개가 1개로 줄었다. N+1 해소와 부합한다
```

검사로 확인한 것: 조인으로 고치면 `DIVERGED` 가 되고, 그 안에 **20 → 1** 이 들어 있고,
🔴 **자동 PR 로는 안 간다**(통과가 아니므로).

## 5. 등급을 정하는 순서 — 위가 이긴다

```
① 재생이 아예 안 돌았다       → FAILED     🔴 LLM 을 부르지 않는다
② 기록에 없는 질의를 만났다    → DIVERGED
③ 되돌리기가 모자랐다         → PARTIAL + missing:["STATE"]
④ 기록 자체에 구멍이 있었다    → PARTIAL + missing:[…]
⑤ 그 밖                     → VERIFIED_DETERMINISTIC
```

### 🔴 ③ 이 위에 있는 이유

되돌리지 않은 채 돌린 재생이 원본과 다른 것은 **패치 탓이 아니라 우리가 만든 차이**다.
그걸 `DIVERGED` 나 `FAILED` 로 적으면 **아무 잘못 없는 패치가 벌을 받는다.**

특히 **행만 되돌린 재생이 가장 위험하다.** 데이터 계약이 그렇게 부르는 이유는,
「다음 `id` 는 몇 번」이 안 돌아와서 **재생이 예외로 죽고, 채점기가 그 죽음을
「패치가 못 고쳤다」로 읽기** 때문이다. 그 경우를 검사로 못 박아 뒀다.

### ④ 기록의 구멍도 등급을 내린다

큐가 차서 버린 이벤트, 버퍼에서 밀려난 이벤트, 스스로 꺼진 계측, 담으려던 시간보다
훨씬 짧게 담긴 창 — 전부 `PARTIAL` 로 내린다.
🔴 **이걸 안 보면 구멍 난 기록에서 나온 재생이 「전부 맞았다」로 적힌다.**
버린 그 이벤트가 사고의 원인이었을 수 있다.

### 🔴 `missing` 이 `null` 일 때와 `[]` 일 때는 다른 사실이다

- `FAILED` → `missing` 은 **`null`**. 무엇을 못 잡았는지 **모른다**
- `VERIFIED_DETERMINISTIC` → `missing` 은 **`[]`**. **보았고 없었다**

## 6. ⬜ 아직 없는 것 — 이 브랜치가 하지 «않은» 것

🔴 **채점하는 코드는 생겼지만 «재생하는» 코드는 아직 없다.**
지금은 「재생해 보니 이랬다」를 사람이 넣어 줘야 한다. 다음 것들이 남았다.

| 무엇 | 왜 이번에 안 했나 |
| --- | --- |
| **재생 엔진** — 기록을 실제로 앱에 다시 흘려 넣기 | 채점 기준이 먼저 서야 엔진이 무엇을 모아야 할지 정해진다. 거꾸로 하면 두 번 만든다 |
| **복원 단계** — 스냅숏을 떠 두고 되돌리기 | 엔진과 같이 만든다. 방법은 이미 정해져 있다(스냅숏) |
| **아웃바운드 가짜** — 나간 요청을 흉내 내기 | v0 기록기가 나간 요청을 «안 잡는다». 잡을 것이 없으면 흉내 낼 것도 없다 |
| **JUnit 테스트 생성** | 채점 기준을 코드로 뽑아내는 일이라, 기준이 굳은 지금이 시작점이다 |

그리고 **아직 재보지 않은 것**:

- ⬜ **진짜 재생에서 이 판정이 맞는지** — 지금 검사는 전부 손으로 만든 관찰로 돈다.
  진짜 앱을 되돌리고 다시 흘려 넣어 본 적은 «없다»

## 7. 🔄 질의 모양 접기의 한계는 «재서» 검사로 적어 뒀다

예측으로 적으려다 재서 확인했다. 지금 규칙(따옴표 문자열과 숫자를 지우기)이
**듣는 것 5가지와 안 듣는 것 2가지**를 검사로 못 박았다.

```
✅ where id = 7   /  where id = 8          → 한 모양
✅ name = '홍길동' /  name = '김철수'        → 한 모양
✅ 줄바꿈·공백이 달라도                      → 한 모양
🔴 in (1, 2)     /  in (1, 2, 3)          → 다른 모양 (자리 «개수»가 남는다)
🔴 배치 크기를 1~10 으로 바꾸면             → 모양이 10개로 흩어진다
```

**영향**: 모양이 흩어지면 「한 모양이 N번 반복」이라는 신호가 약해진다.
🔴 **원래부터 배치 크기가 들쭉날쭉한 앱에서는 N+1 을 놓칠 수 있다.**

⬜ **진짜 앱의 SQL 에서 이게 얼마나 흔한지는 안 쟀다.** 고치는 방법은 `in (?, ?, ?)` 를
`in (?)` 로 한 번 더 접는 것인데, 🔴 그러면 「값 3개로 부른 것」과 「값 300개로 부른 것」이
같아진다 — 그 둘은 성능상 **다른 사실**이라 접어도 되는지가 분명하지 않다. **재고 나서 정한다.**
