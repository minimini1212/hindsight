# 기록기를 붙이면 얼마나 더 드나 — 처음 쟀다

> 2026-09-15. [v0 기록기](v0-recorder.md)를 만든 직후.
> 설계가 측정 하네스를 v0 과제로 못 박은 이유는 하나다 — 🔴 **「나중에 잰다」로 두면 안 재게 된다.**

---

## 0. 한 줄

**목표 넷 중 둘은 지켰고, 하나는 못 지켰다가 고쳐서 지켰고, 하나는 이 방법으로는 «못 쟀다».**

| 설계 §10 의 목표 | 잰 값 | 판정 |
| --- | --- | --- |
| 경계 이벤트 하나당 **2µs 이하** | SQL **0.46µs** · HTTP **0.65µs** (p50) | ✅ 🔄 **처음엔 5.42µs 로 못 지켰다. 원인을 재서 고쳤다** |
| 요청당 **50µs 이하** | 🔴 **못 쟀다** — 재려는 값이 잡음(2,326µs)보다 작다 | ⬜ **「없다」가 아니라 「이 자로는 안 보인다」** |
| 상시 메모리 **32MB 이하** | 이벤트 5만 건에 실제 힙 **7.9MB** | ✅ 다만 🔴 **어림이 실제의 2.6배 과대평가**다 |
| 앱 시작 시간 **+300ms 이하** | 🔴 **못 쟀다** (§5) | ⬜ |

## 1. 🔄 목표를 못 지켰다 → 어디가 비싼지 재서 찾았다 → 고쳤다

### 처음 잰 값 — SQL 이벤트만 목표의 2.7배

```
SQL  이벤트 하나   p50  5.416µs   p99 10.649µs      🔴 목표 2µs
HTTP 이벤트 하나   p50  0.961µs   p99  2.587µs      ✅
```

같은 링 버퍼에 같은 방식으로 넣는데 **다섯 배 넘게** 차이가 났다.
🔴 **다른 일을 하는 자리가 하나 있다**는 뜻이고, 고치기 전에 «어디인지»부터 쟀다.

### 어디가 비싼가 (실험 ⑩-⑤)

```
정규화(정규식 3개)   p50  2.421µs      ← 여기다
지문(SHA-256)      p50  0.215µs
정규화 + 지문       p50  3.342µs      ← SQL 이벤트 5.416µs 의 62%
```

🎯 **고칠 자리는 링 버퍼가 아니라 요약층의 「모양 만들기」였다.**
질의에서 값을 지워 모양으로 접는 일(`where id = 7` → `where id = ?`)에 정규식이 세 번 돈다.

🔴 **안 재고 고쳤으면 링 버퍼를 만졌을 것이다** — 그리고 안 빨라진 뒤에도
「버퍼가 원래 느린가 보다」로 넘어갔을 것이다.

### 고친 방법 — 같은 SQL 문자열이면 계산을 재쓴다

같은 SQL 문자열에 대한 `(모양, 지문)`을 들고 있다가 재쓴다.
**이 도구가 겨누는 대표 버그인 N+1 은 같은 SQL 이 수백 번 반복되는 모양**이라,
캐시가 가장 잘 듣는 자리가 하필 가장 중요한 자리다.

🔴 **상한(1,000개)이 «반드시» 필요하다.** 값을 문자열로 이어 붙여 SQL 을 만드는 앱이 있고
(`"... where id = " + id`), 그러면 서로 다른 SQL 문자열이 **무한히** 생긴다.
상한이 없으면 우리 캐시가 남의 앱 힙을 먹어 치운다 — 관측 도구가 관측 대상을 죽이는 모양이다.
⚠️ 상한을 넘으면 캐시를 **비우지 않고 «넣기만 멈춘다»**. 비우면 상한 근처에서
채우고-비우고를 반복하며 **캐시가 없을 때보다 느려진다.**

### 고친 뒤

| | 전 | 후 | |
| --- | --- | --- | --- |
| SQL 이벤트 p50 | 5.416µs | **0.463µs** | 🎯 **11.7배** |
| SQL 이벤트 p99 | 10.649µs | **0.980µs** | 🎯 **10.9배** |
| HTTP 이벤트 p50 | 0.961µs | 0.650µs | (잡음 범위) |

✅ **둘 다 목표 2µs 안으로 들어왔다.**

## 2. ✅ 버퍼가 가득 찬 뒤에도 비용이 안 늘어난다

장애가 길어지면 링 버퍼는 계속 가득 찬 상태로 돈다. 넣을 때마다 앞에서 밀어내는 일이
같이 일어나므로, **여기가 비싸지면 장애가 길어질수록 앱이 더 느려진다.**

```
빈 버퍼        p50 1.052µs   p99 1.653µs
가득 찬 버퍼    p50 0.586µs   p99 0.710µs
차이           Δp50 -0.466µs
```

🔴 **차이가 음수로 나왔다. 이건 「밀어내기가 공짜보다 싸다」가 아니라 「차이가 잡음보다 작다」다.**
0 으로 바꿔 적지 않는다 — 그러면 「쟀고 차이가 없었다」로 읽히는데, 진짜 뜻은
**「이 방법으로는 구별이 안 된다」**이다. 실용적인 결론은 같다: 밀어내기는 눈에 띄는 값을 안 먹는다.

## 3. 🔴 사고가 나서 파일을 떨구는 데 12ms — 요청 스레드가 이걸 기다린다

```
기록 파일 하나 쓰기   p50 12,271µs (12.3ms)   p99 23,531µs (23.5ms)
  (링에 이벤트 2,000건이 담긴 상태)
```

**평상시 비용이 아니다.** 사고가 났을 때만, 그리고 묶기 장치에 막히지 않은 첫 건에만 든다.
그래도 🔴 **그 요청은 12ms 를 더 기다린다.** 이미 사고가 난 요청이므로 실용적으로는
받아들일 만하지만, **숫자를 모르는 채로 두는 것과는 다르다.**

⬜ **v1 의 과제로 남긴다** — 파일 쓰기를 요청 스레드 밖으로 내보내는 것.
지금 안 하는 이유는, 내보내면 「앱이 그 직후 죽을 때 기록이 안 남는」 새 문제가 생기기 때문이다.
그 맞바꿈은 v1 에서 정한다.

### ⚠️ 이 숫자는 처음에 «틀리게» 쟀다

처음 잰 값은 **8.1µs** 였다. 파일 쓰기가 8µs 일 리 없다는 것이 단서였다.

원인: 재는 코드가 회차 번호를 사고의 열쇠로 썼는데, **덥히는 구간이 그 번호를 다 써 버려서**
본 측정에서는 묶기 장치가 전부 막았다. 즉 「파일 쓰기」가 아니라 **「막히는 데 걸리는 시간」**을
재고 있었다. 🔴 지금은 «파일이 실제로 생겼는지»를 검사로 확인한다 —
**재는 코드도 틀릴 수 있고, 틀린 줄 모르면 그 숫자가 문서에 남는다.**

## 4. 🔴 메모리 어림이 실제의 2.6배 — 과대평가 쪽이라 안전하지만 공짜가 아니다

```
넣은 이벤트    50,000건 (전부 링에 담김)
우리 어림      21,900,000 바이트 (20.9 MB)
실제 힙 증가    8,292,656 바이트 ( 7.9 MB)
실제 / 어림    0.38 배
```

⚠️ 힙 측정은 `System.gc()` 가 **부탁이지 명령이 아니라서** 자릿수로만 읽는다.

**방향은 안전하다.** 실제보다 많이 쓴다고 «치므로» 상한에 일찍 걸리고, 메모리를 덜 쓴다.
🔴 **그런데 공짜가 아니다.** 32MB 상한이 실제로는 **12MB 남짓의 데이터**만 들고 있다는 뜻이고,
그만큼 **담기는 시간이 짧아진다.** 「60초를 담으려 했는데 4초만 담겼다」가 더 심해진다.

⬜ **어림을 실제에 맞추는 것은 다음 과제다.** 지금 고치지 않는 이유는, 힙 측정 자체가
자릿수 수준이라 **무엇에 맞춰야 하는지가 아직 정확하지 않기** 때문이다.
✅ 다만 파일에는 `windowActualSeconds` 로 **실제 담긴 시간이 적히므로**, 이 과대평가가
읽는 사람을 속이지는 않는다.

## 5. 🔴 두 가지는 «못 쟀다» — 그리고 그건 「0 이었다」와 다르다

### ① 요청당 추가 시간 (실험 ⑪)

기록기를 **뗀 앱**과 **붙인 앱**을 같은 기계·같은 JVM 에서 견줬다.

```
뗀 쪽    p50 3,441.7µs   p99 5,768.1µs
붙인 쪽  p50 2,951.1µs   p99 4,041.8µs
차이     Δp50  -490.5µs  Δp99 -1,726.3µs
잡음     기준선의 p99−p50 = 2,326.4µs
```

**차이가 잡음의 5분의 1 밖에 안 된다.** 게다가 부호가 음수다 — 붙인 쪽이 «빨라» 보인다.
🔴 **이건 기록기가 앱을 빠르게 만든다는 뜻이 아니다. 이 자로는 안 보인다는 뜻이다.**

원인은 분명하다. 재려는 값은 **수십 µs** 인데 스프링 요청 하나는 톰캣·JSON·JPA 를 지나며
**밀리초 단위로 흔들린다.** 바늘을 건초더미에서 찾는 것이 아니라, **건초더미의 무게 변화로
바늘의 무게를 재려는** 것이다.

✅ **그래서 µs 단위의 값은 실험 ⑩ 이 따로 잰다** — 기록기의 입구를 직접 두드리는 방식으로.
요청 하나가 이벤트를 20건 낸다고 보면 **0.46µs × 20 ≈ 9µs** 이고, 이건 목표 50µs 안이다.
🔴 **다만 이건 계산이지 측정이 아니다.** 「쟀다」로 적지 않는다.

### ② 앱 시작 시간 증가

같은 JVM 에서 두 앱을 차례로 띄웠더니 **5.695초 → 0.855초**가 나왔다.
🔴 **이 숫자는 쓸 수 없다.** 두 번째 앱은 첫 번째가 이미 클래스를 다 읽어 둔 JVM 에서
뜨기 때문에, **기록기의 값이 아니라 「두 번째로 뜨는 값」**을 잰 것이다.

⬜ **제대로 재려면 JVM 을 따로 띄워야 한다.** 다음 과제로 남긴다.

## 6. 검사로 남긴 것 — 그리고 «일부러» 안 건 것

| 무엇 | 어떻게 |
| --- | --- |
| 이벤트 하나당 비용이 **자릿수가 바뀌면** 실패 | 목표 2µs 의 **50배**(100µs)에 그물을 걸었다 |
| 파일 쓰기가 **1초를 넘기면** 실패 | 디스크가 개입하므로 훨씬 느슨하게 |
| 파일이 **정말 써졌는지** | §3 의 측정 버그를 다시 안 만들려고 |
| 모양 캐시가 **무한히 안 자라는지** | 값이 SQL 에 박힌 앱을 흉내 내어 5,000건 → 캐시 1,000 이하 |
| 캐시가 상한에 닿아도 **접기는 그대로인지** | 5,000건이 여전히 한 모양으로 접힌다 |

🔴 **목표값(2µs·50µs)에 검사를 걸지 «않았다».** 절대값에 검사를 걸면 기계가 바쁜 날
빌드가 빨갛게 되고, **가끔 실패하는 검사는 사람이 「또 그거네」 하고 넘기게 만들어
진짜 고장까지 같이 넘어간다.** 진짜 숫자는 출력으로 남기고 이 문서에 손으로 옮긴다.

## 7. ⬜ 남은 것

- **앱 시작 시간 증가** — JVM 을 따로 띄워서 재야 한다
- **요청당 추가 시간을 «측정»으로** — 지금은 이벤트 비용 × 이벤트 수라는 «계산»뿐이다
- **메모리 어림을 실제에 맞추기** — 2.6배 과대평가는 담기는 시간을 그만큼 줄인다
- **파일 쓰기 12ms 를 요청 스레드 밖으로** — v1. 맞바꿈이 있어서 지금 안 한다
- 🔴 **동시 요청에서 재기** — 지금은 전부 한 스레드로 쟀다. 여러 스레드가 같은 링 버퍼를
  두드릴 때 잠금 다툼이 어떻게 되는지는 **안 봤다**
