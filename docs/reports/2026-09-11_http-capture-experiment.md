# 2026-09-11 실측 2 — Filter 로 잡은 것이 재생에 쓸 만한가

> TODOS 의 「먼저 확인해야 결정이 유지되는 것」 중 **남은 하나**였다.
> 이게 안 되면 바이트코드를 v1 로 미룬 근거([만드는 순서 결정](../rules/build-order-decision.md) §5)가 사라진다.
> 코드: `demo-app/src/test/java/io/hindsight/demo/experiment/HttpTap.java`

## §1 진짜 걱정이었던 것 — 본문은 한 번만 읽을 수 있다

HTTP 요청 본문은 **흐르는 물**이다. `getInputStream()` 으로 한 번 읽으면 사라진다.

```
Filter 가 「기록해 두려고」 본문을 읽는다
   → 앱에는 «빈 본문»이 도착한다
   → 요청이 400 으로 실패한다
```

🔴 **관측하려다 관측 대상을 망가뜨리는 것**이고, 이 프로젝트가 절대 하면 안 되는 일이다.
응답도 똑같다 — 우리가 읽으면 클라이언트에게 안 간다.

**푼 방법**: 스프링의 `ContentCachingRequestWrapper`·`ContentCachingResponseWrapper`.
흘러가는 물을 **지나가는 김에 복사해 두는** 껍데기다. 앱은 원래대로 읽고 우리는 복사본을 본다.

⚠️ 응답 쪽에는 함정이 하나 더 있다. **`copyBodyToResponse()` 를 마지막에 반드시 불러야 한다.**
잊으면 클라이언트가 **빈 응답**을 받는다. 실험이 이것도 확인한다.

## §2 결과

### 실험 ④ — 본문을 잡고도 앱이 정상인가

```
│ 앱이 돌려준 상태  : 200
│ 앱이 돌려준 본문  : {"id":3,"product":"모니터","memberName":"홍길동"}
├─ 우리가 «잡은» 것
│ 메서드·경로       : POST /api/orders
│ 요청 본문         : {"memberId":1,"product":"모니터"}
│ 응답 상태         : 200
│ 응답 본문         : {"id":3,"product":"모니터","memberName":"홍길동"}
│ 헤더              : [content-type, content-length]
```

✅ **앱이 200 을 돌려줬고 본문도 온전하다.** 우리가 먼저 읽었는데도 앱이 제대로 받았다.
✅ **재생에 필요한 것을 다 잡았다** — 메서드·경로·본문·응답 상태·응답 본문.
✅ `Authorization`·`Cookie` 는 **처음부터 안 담았다**. 나중에 붙이면 그 사이 기록에 남는다.

### 실험 ⑤ — 잡은 것«만»으로 재생하면 같은 응답이 나오나

🔴 원본 코드를 안 보고 **기록만 보고** 요청을 다시 만들었다. 그게 재생이다.

```
원본 응답 : 200 [{"id":4,"product":"키보드",...},{"id":5,"product":"마우스",...}]
재생 응답 : 200 [{"id":4,"product":"키보드",...},{"id":5,"product":"마우스",...}]
```

✅ **글자 하나까지 같다.** 읽기 요청은 재생이 성립한다.

### 🔴 실험 ⑥ — 상태를 바꾸는 요청을 재생하면

```
원본 응답 : {"id":8,"product":"의자","memberName":"홍길동"}
재생 응답 : {"id":9,"product":"의자","memberName":"홍길동"}
같은가    : false
주문 개수 : 4 건 (재생이 하나 더 만들었다)
```

🔴 **다르다. 그리고 이건 결함이 아니라 알아야 할 사실이다.**

주문을 만드는 요청을 재생하면 **주문이 하나 더 생긴다.** DB 가 이미 달라져 있으니
`id` 도 달라진다. 설계 §4-2 의 「앱 안에 쌓인 상태는 재현 안 된다」가 **눈에 보이는 형태**로 나왔다.

## §3 그래서 무엇이 정해졌나

| 확인할 것 | 결과 |
| --- | --- |
| 본문을 잡고도 앱이 정상인가 | ✅ 200, 본문 온전 |
| 응답이 클라이언트에 가나 | ✅ `copyBodyToResponse()` 로 해결 |
| 잡은 것만으로 재생되나 | ✅ 읽기 요청은 **글자까지 동일** |
| 쓰기 요청은? | 🔴 **다르다. 같아질 수 없다** |

🎯 **v0 기록 방식이 성립한다.** 바이트코드를 v1 로 미룬 근거가 유지된다.

### 🔄 그리고 설계에 없던 구분이 하나 필요해졌다

지금 설계는 재생 결과를 네 등급으로 나눈다
(`VERIFIED_DETERMINISTIC` · `PARTIAL` · `DIVERGED` · `FAILED`).
그런데 **쓰기 요청은 이 중 어디에도 정확히 안 맞는다.**

- `FAILED` 가 아니다 — 재생 자체는 잘 됐다
- `DIVERGED` 가 아니다 — 패치가 질의 모양을 바꾼 게 아니다.
  **아무것도 안 고쳐도 매번 다르다**

⬜ **필요한 것**: 기록에 「이 요청은 상태를 바꾼다」를 표시하고, 그런 요청은
**응답 전체 비교 대신 다른 기준으로 채점**해야 한다. 예를 들어
- `id` 처럼 매번 달라지는 자리를 빼고 비교
- 또는 「던진 예외가 사라졌나」·「SQL 모양이 바뀌었나」만 본다

🔴 **이걸 안 정하면, 쓰기 요청에서 난 사고는 전부 「고쳐지지 않았다」로 판정된다.**
아무리 잘 고쳐도. → TODOS 에 올렸다.

## §4 겪은 것

- `@TestConfiguration` 안에서 `Filter` 를 빈으로 내놓으면 스프링 부트가 자동으로 체인에 끼워 준다.
  따로 등록할 필요가 없었다
- 기록은 `finally` 에서 남긴다. 🔴 **앱이 예외를 던져도 기록은 남아야** 한다 —
  사고가 났을 때 기록이 없으면 이 도구는 존재 이유가 없다
