# 생성된 테스트를 «진짜로» 돌렸다 — 패치 전에 실패하고, 고치면 통과한다

> 2026-09-16. v0 4주차. 🔴 **채점 네 겹의 첫 겹이 처음으로 «측정»됐다.**
> 왜 이 겹이 맨 앞인지는 [데이터 계약](../../DATA_CONTRACT.md)의
> 「패치 전에 실패하지 않았으면 채점이 아니다」 절(§7-1)에 있다.

---

## 1. 무엇이 바뀌었나

**여기까지 이 프로젝트는 생성된 테스트가 «컴파일되는 것»까지만 확인했다.**
이번에 처음으로 **컴파일해서 돌렸다.**

| | 전 | 후 |
| --- | --- | --- |
| 검사 | 234건 | **237건** (core 162 · recorder 43 · demo-app 32) |
| 자바 파일 | 91개 | **94개** |

### 왜 이 겹이 없으면 나머지가 다 무의미한가

생성된 테스트가 패치 전에도 통과하면 **패치 전에도 초록불이고 패치 후에도 초록불**이다.
그런데 도구는 「통과했다」며 **아무것도 안 고친 패치로 PR 을 올린다.**
🔴 채점기가 있다고 «믿는» 구조에서 이건 치명적이다.

## 2. 🎯 잰 값

```
── 실험 ⑬-① 버그가 «있는» 코드에서 ──
  돌았나: true   통과했나: false
  이유: 같은 모양의 질의가 5번 반복되던 것이 그대로면 안 고쳐진 것이다:
        select m1_0.id,m1_0.name from member m1_0 where m1_0.id=?

── 실험 ⑬-② 「고친」 코드에서 ──
  돌았나: true   통과했나: true
```

**고리가 한 바퀴 돌았다.** 기록 → 되돌리기 → 재생 → 채점 → 테스트 생성 →
**그 테스트를 진짜로 돌리기** 까지 이어진다.

### 생성된 테스트가 실제로 검사한 것

```
✅ 재생 전에 기록 시점 상태로 되돌렸다 (행 + 「다음 id 는 몇 번」)
✅ 응답 상태가 200 이다
✅ 응답 본문이 기록과 글자까지 같다
✅ 같은 모양의 질의 반복이 5번보다 줄었다

🔴 검사하지 «못한» 것:
⬜ 요청 본문 — 기록에 없다(앱이 본문을 안 읽었거나 못 잡았다)
```

🔴 **「못 한 것」이 같이 나온다.** GET 요청이라 요청 본문이 없었고, 생성기는 그걸
「빈 본문이어야 한다」로 바꾸지 않고 **못 했다고 말한다.**

---

## 3. 🔴 이 시험이 «증명하지 않는» 것

⚠️ **「고친 코드」는 사람이 미리 써 둔 것이다.** `OrderRepository` 에 `join fetch` 질의를
넣어 두고, 설정 한 줄로 갈아탄다.

🔴 **그래서 이 시험이 보이는 것은 「고리가 도는가」이지 「LLM 이 고칠 수 있는가」가 아니다.**
후자는 LLM 을 실제로 부르기 전까지 알 수 없고, 그건 API 키가 필요해서 아직 못 한다.

---

## 4. 어떻게 돌렸나 — 세 가지 제약

### 🔴 디스크의 파일을 «읽지» 않는다

소스를 파일로 떨궈 두고 그걸 컴파일하면 **LLM 이 그 파일을 고쳐서 통과시킬 수 있다.**
그래서 **메모리 안에서 컴파일한다** — 디스크에는 클래스 파일만 잠깐 생긴다.
✅ 생성된 소스가 저장소 어디에도 안 남는 것을 검사로 확인했다.

### 스프링 빈이 아니라 «정적 자리»에서 도구를 받는다

생성된 테스트는 **실행 시점에 만들어져 컴파일되는** 클래스다. 스프링 테스트 문맥이
그런 클래스를 알 리 없고, 알게 만들려면 문맥을 다시 띄워야 한다 —
🔴 **그러면 되돌려 놓은 DB 가 그 사이에 다시 바뀐다.**

⚠️ 이 방식은 **한 번에 재생 하나만** 돌릴 수 있다. v0 는 그렇게만 쓰므로 괜찮고,
여러 개를 동시에 돌리게 되면 이 자리부터 바꿔야 한다.

### 클래스로더의 부모를 «지금» 로더로 둔다

안 그러면 생성된 테스트가 기반 클래스를 **따로 읽어서** 타입이 둘이 되고,
`ClassCastException` 이 난다.

---

## 5. 🔴 「안 돌았다」를 「실패」로 치지 않는다

```
돌았나(실행은 됐나)   통과했나
   false                —      → 「못 돌린 것」. 컴파일이 안 됐거나 테스트가 0개다
   true               false    → 🔴 «이것»이 「패치 전에 실패했다」이다
   true               true     → 통과
```

컴파일이 안 돼서 못 돌린 것을 「실패」로 세면, **버그를 못 살린 테스트가
「기준선 실패」를 통과해 버린다.** 그리고 「생성된 클래스에 테스트가 0개」인 경우도
통과로 치지 않는다 — 아무것도 안 돌린 것이다.

---

## 6. ⬜ 무엇이 아직 확인 안 됐나

- 🔴 **LLM 이 고칠 수 있는지는 모른다.** 위에 적은 대로, 「고친 코드」는 사람이 써 둔 것이다
- **㉢(앱의 기존 테스트)과 ㉣(되돌리기)을 이 경로로 안 돌렸다.** 채점 네 겹의 판단 코드는
  있지만, 그 둘을 «진짜 앱에» 연결한 것은 아직 없다 — 지금은 ㉠㉡ 만 진짜로 돌았다
- **재생을 한 번에 하나만 돌릴 수 있다.** 정적 자리에 도구를 걸어 두는 방식이라,
  동시에 둘을 돌리면 섞인다
- **생성된 테스트의 클래스 이름이 기록마다 다르다.** 같은 기록이면 같은 이름이지만,
  기록 번호가 매번 새로 만들어지므로 ⬜ 「어제 그 테스트」를 이름으로 찾을 수는 없다
- **패치를 «파일로» 적용하고 돌리는 경로는 아직 없다.** 지금은 설정 한 줄로 갈아타는
  흉내이고, 진짜 패치는 `PatchApplier` 가 파일을 쓴 «뒤» 앱을 다시 띄워야 한다 —
  ⬜ 그 다시 띄우는 비용을 **안 쟀다**
