
# `hs` 명령어 — 그리고 어제 만든 감시선이 «오늘» 울렸다

> 2026-09-16. v0 2주차에 남아 있던 마지막 항목.
> 무엇을 왜 경고하는지는 [데이터 계약](../../DATA_CONTRACT.md)의
> 「담으려던 시간과 담긴 시간은 반드시 둘 다 적는다」 절(§8-1)에 있다.

---

## 1. 무엇이 생겼나

**기록을 사람이 들여다보는 명령어.** 기록 파일은 JSON 이고 열면 수백 줄이라,
그 안에서 **「이 기록을 믿어도 되나」**를 찾아 읽는 것은 아무도 안 한다.
그래서 그 답을 **맨 위에 눈에 띄게** 올린다.

```
hs list           기록 목록 (최근 것이 위)
hs show <번호>    기록 하나를 자세히
```

| | 전 | 후 |
| --- | --- | --- |
| 검사 | 208건 | **234건** (core 162 · recorder 43 · demo-app 29) |
| 자바 파일 | 87개 | **91개** |

## 2. 🔴 어제 만든 감시선이 오늘 울렸다 — picocli 를 못 쓴다

설계는 명령줄에 **picocli** 를 쓴다고 적어 뒀다. 넣어 보고 쟀다.

```
:hindsight-recorder-simple:checkRecorderDependencies
  → v0 기록기가 관측 대상 앱으로 새 의존성을 끌고 들어간다: [picocli]
  → BUILD FAILED
```

그리고 **demo-app 의 의존성 목록에 picocli 가 실제로 나타나는 것도 확인했다.**
즉 이건 이론이 아니었다.

```
core 에 picocli 를 넣는다
  → recorder-simple 이 core 를 의존한다
    → demo-app 이 recorder-simple 을 의존한다
      → 🔴 picocli 가 «관측 대상 앱»의 클래스패스로 들어간다
```

### 🎯 2026-09-15 에 예측한 그 일이다

모듈을 가를 때 이렇게 적어 뒀다 — *"「Spring AI 와 picocli 가 딸려 온다」는 오늘의 core 가
아니라 **미래의** core 이야기였고, 그 미래가 오는 순간은 `checkRecorderDependencies` 가 잡는다."*

**하루 만에 그 미래가 왔고, 감시선이 잡았다.** 사람이 기억할 필요가 없었다.

### 그래서 어떻게 했나 — 의존성을 «안» 쓴다

검사의 실패 메시지는 *"이제 `core.store` 를 떼어낼 시점이다"* 라고 말한다. 그런데
**명령이 둘이고 옵션이 거의 없다.** 직접 읽으면 40줄이다.

🔴 **둘짜리 명령어가 모듈을 하나 쪼개는 값을 치를 이유가 없다.**
라이브러리가 진짜로 필요해지는 날(진단이 Spring AI 를 쓸 때) 그때 쪼갠다 —
그리고 그날도 이 감시선이 알려 줄 것이다.

⚠️ **설계 문서가 이 제약을 몰랐다.** 설계의 모듈 표는 core 의 의존성에 picocli 를 적어
뒀는데, 「recorder-simple 이 core 를 의존한다」와 양립하지 않는다. 설계를 고쳤다.

## 3. 🔴 화면이 가장 크게 말해야 하는 것

설정에 60초라고 써 있어도 트래픽이 많으면 실제로는 4초치만 담긴다. 이때 조용히 넘어가면
읽는 사람은 **30초 전에 시작된 커넥션 누수가 일어나지 않았다고 결론 내린다.**

```
🔴 담으려던 60초 중 실제로는 4.2초만 담겼다.
   그 앞에서 시작된 일은 이 기록에 «없다» — 커넥션 누수처럼 30초 전에
   시작된 것을 찾고 있다면, 여기서 「없었다」고 결론 내리면 안 된다.
🔴 큐가 차서 17건을 «못 받았다». 그중에 원인이 있었을 수 있다
```

목록 화면에서도 `🔴 4.2/60초` 로 한눈에 보이고, 아래에 한 줄이 더 붙는다.

⚠️ **온전한 기록에는 아무 경고도 안 붙는다.** 늘 켜져 있는 경고등은 꺼져 있는 것과 같다.

### 「안 봤다」와 「보았고 없었다」를 화면에서도 가른다

| 자리 | 화면 |
| --- | --- |
| 재생한 적이 없다 | `아직 재생한 적이 «없다»` — `FAILED` 가 아니다 |
| 되돌리기의 `null` | `캐시 안 봤다` — `아니오` 가 아니다 |
| 질의 모양이 `null` | `«안 봤다»` / 빈 목록이면 `보았고 하나도 없었다` |
| 응답 본문이 `null` | `응답 본문을 «못 잡았다»` — 「비었다」가 아니다 |
| 커넥션 표본이 `null` | `커넥션 풀은 «안 봤다» — 누수를 찾고 있다면 여기서는 알 수 없다` |

## 4. 🔴 통째로 찍어 보고 하나 더 잡았다

[어제 PR 글에서 그랬듯이](pull-request-draft.md), 조각 단언만으로는 안 보이는 것이 있었다.
화면을 통째로 출력해서 읽어 보니 이렇게 나왔다.

```
── 담긴 것 ──
  들어온 요청 1건 · SQL 0건

── 질의 모양 (많이 반복된 순) ──
  🔴   20번  select * from member where id = ?
```

**SQL 0건인데 20번?** 둘 다 맞는 값이다 — 전문층(본문까지 담는 층, 짧고 무겁다)은
밀려났고, 요약층(모양과 횟수만 담는 층, 길고 가볍다)은 남은 것이다.
🔴 **그런데 화면이 그걸 설명하지 않으면 읽는 사람은 둘 중 하나가 틀렸다고 생각한다.**

그래서 어긋날 때만 한 줄을 붙인다.

```
⚠️ 위의 「담긴 것」보다 여기 횟수가 많다. 둘 다 맞다 —
   전문(본문까지 담는 층)은 0건만 남았고, 여기 요약(모양과 횟수만 담는 층)은 21건을 세었다.
   🔴 재생에 쓸 수 있는 것은 «전문»뿐이다. 요약은 사람이 원인을 찾는 데만 쓴다.
```

⚠️ **어긋나지 않으면 안 붙인다** — 늘 뜨는 설명은 안 읽힌다.

## 5. 그 밖에 화면이 지키는 것

- **N+1 이 눈에 띈다.** 한 모양이 10번 이상 반복되면 🔴, 3번 이상이면 ⚠️ 가 붙고,
  **많이 반복된 것이 위로** 온다 — 스무 줄 아래에 있으면 못 본다
- **못 읽은 파일을 조용히 빼지 않는다.** 깨진 JSON 이 섞여 있어도 나머지는 보여 주되,
  🔴 **「못 읽은 기록이 있다」고 말한다** — 안 보이면 그 파일이 «없는 것»으로 읽힌다
- **「기록이 없다」와 「폴더를 못 읽었다」를 다르게 말한다**
- **비밀이 화면에 안 나온다.** 가명화가 «쓰기 직전»에 이미 했으므로 파일에도 없다 —
  화면은 그 파일을 읽을 뿐이다. 검사로 확인했다

## 6. ⬜ 무엇이 아직 확인 안 됐나

- 🔴 **`hs` 를 진짜 터미널에서 돌려 본 적이 없다.** 검사는 출력을 문자열로 받아서 본다.
  ⬜ 윈도우 콘솔에서 한글과 이모지가 어떻게 나오는지는 **안 봤다** —
  이 프로젝트는 이미 [테스트 출력의 한글이 깨지는 일](../2026-09-11/troubleshooting/gradle-테스트-한글-깨짐.md)을
  겪었으므로, 콘솔에서도 깨질 가능성이 있다
- **실행 가능한 `hs` 가 없다.** `main` 은 있지만 jar 로 묶거나 실행 스크립트를 만들지 않았다
- **기록이 많을 때 어떻게 보이는지 안 봤다.** 목록이 1,000줄이면 페이지 나누기가 필요한데
  ⬜ 얼마부터 필요한지 **안 쟀다**
- **`hs show` 가 이벤트를 다 안 보여 준다.** 요청 줄만 보여 주고 SQL 하나하나는 안 보여 준다 —
  ⬜ 그게 필요한지는 써 보고 정한다
