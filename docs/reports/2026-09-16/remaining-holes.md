# 남아 있던 구멍을 막고, 안 재던 둘을 쟀다

> 어느 구멍이 남아 있었는지는 코드를 다시 읽으며 하나씩 확인했다(§1).

## 2. 🔴 ⑤ 가명화 — 한 곳에서 한다더니 두 자리를 건너뛰었다

규율에는 *"가명화는 정확히 한 곳에서, 기록을 쓰기 직전에"* 라고 적혀 있다.
그런데 그 한 곳이 이랬다.

```java
return new Recording(
        recording.schemaVersion(),
        recording.id(),
        recording.capturedAt(),
        recording.trigger(),        // 🔴 그대로 나간다
        applyToApp(recording.app()),
        events,                     // ← 여기만 훑는다
        recording.summary(),        // 🔴 그대로 나간다
        ...);
```

### 새고 있던 자리는 «셋»이었다

```
entryPoint          GET /api/users/hong@example.com/orders
exception.message   없는 회원: hong@example.com (010-1234-5678)
dedupKey            🔴 entryPoint 를 «그대로 이어 붙인» 것이다
```

⚠️ **세 번째가 놓치기 쉬운 자리다.** `Trigger.dedupKeyOf` 는 해시가 아니라
**문자열 이어 붙이기**다. `entryPoint` 만 가리고 `dedupKey` 를 놔두면
**같은 값이 바로 옆 자리에 그대로 남는다.**

가명화가 결정적(같은 입력 → 같은 가명)이라 **둘을 같은 함수로 훑으면 아귀가 맞은 채로**
가려진다. 그걸 검사로 못 박았다.

```java
assertThat(out.dedupKey())
        .as("dedupKey 는 진입점으로 시작한다. 둘이 다른 가명이면 같은 사고가 안 묶인다")
        .startsWith(out.entryPoint());
```

### 요약층에서는 «무엇을 안 훑는지»가 더 중요하다

| | 훑나 | 왜 |
| --- | --- | --- |
| `RequestLine.path` | ✅ | 진입점과 같은 모양이고 같은 값이 박힌다 |
| `SqlShape.normalized` | ❌ | 이미 값이 `?` 로 빠진 뒤의 모습이라 남을 값이 없다. 🔴 그리고 바꾸면 **`sqlHash` 와 아귀가 안 맞아** 진단이 「이 해시가 무슨 질의였나」를 영영 못 찾는다 |
| `PoolSample` | ❌ | 숫자뿐이다 |

✅ **되돌려서 확인했다** — `applyToTrigger`/`applyToSummary` 를 빼니 **6건이 실패**한다.

## 3. 🔴 ⑨ 클라이언트는 500 을 봤는데 기록에는 200 이 적혀 있었다

```
컨트롤러가 던진다
  → 우리 필터를 «지나» 나간다        ← 이 시점에 우리가 getStatus() 를 읽었다
    → 그 «뒤»에 컨테이너가 상태를 세팅한다
      → 🔴 기록에 적힌 값은 아무도 본 적이 없는 값이다
```

진짜 앱에서 재 봤다.

```
── 실험 ⑮ ──
  클라이언트가 본 상태: 500
  기록에 적힌 상태    : null      ← 고친 뒤
  방아쇠              : EXCEPTION
```

✅ **되돌리니 `200` 이 나왔다.** 그 200 으로 재생하면
**「응답 상태가 기록과 같다」로 통과**하는데, 그 상태는 아무도 본 적이 없다.

### ⚠️ 500 으로 「고쳐」 적지 않는다

컨테이너가 무엇을 세팅할지 **우리는 모른다** — `@ExceptionHandler` 가 있으면 200 일 수도 있다.
🔴 **모르는 것은 모른다고 적는다.** 그러면 오라클이 그 항목을 「판정 못 함」으로 둔다.

## 4. 🔴 ⑦ 사고 묶음 장부가 남의 JVM 안에서 무한히 자랐다

묶음 열쇠는 진입점을 그대로 들고 있고, 진입점은 URI 다.

```
GET /api/orders/1 · GET /api/orders/2 · GET /api/orders/3 …
🔴 전부 «다른 열쇠»다. 경로에 식별자가 들어가는 API 가 하나만 있어도 끝없이 늘어난다
```

⚠️ **관측 도구가 앱을 죽이는 모양**이고, 이 프로젝트에서 가장 굳은 규율을 정면으로 어긴다.

### 두 겹으로 막되, 잊은 것을 «센다»

```
① 시간   마지막으로 본 지 6시간이 지나면 잊는다
② 개수   그래도 1만 개를 넘으면 «가장 오래 안 본 것»부터 잊는다
```

🔴 **②가 없으면 「보통은 괜찮은」 방어다.** 사고가 한꺼번에 수만 가지로 나면
①의 시간이 지나기 전에 메모리가 먼저 찬다 — 그리고 그게 바로 지켜야 하는 순간이다.

🔴 **조용히 지우지 않는다.** 잊은 열쇠가 다시 오면 `dedupCount` 가 1 부터 다시 센다.
그건 틀린 숫자는 아니지만 **「한 번 났다」로 읽히는** 숫자다. 그래서 잊은 수를 센다.

### ⚠️ 청소는 «가끔»만 한다 — 이 코드는 요청 스레드에서 돈다

처음 판은 `admit()` 마다 장부를 통째로 훑었다. 열쇠 1만 개면 사고 한 번에 1만 번 비교다.
**기록기가 앱을 느리게 하면 안 된다는 규율이 그것보다 앞선다.**

```
장부가 상한을 넘었다        → 지금 청소한다 (메모리는 미룰 수 없다)
마지막 청소 후 1분이 지났다 → 청소한다
그 밖                       → 아무것도 안 한다
```

### 🔴 시험이 내 실수 둘을 잡았다

**① 상한을 하나 넘겼다.** `size() > 상한` 으로 두면 넣고 난 뒤가 상한+1 이다.
그건 「상한을 지킨다」가 아니라 「상한 근처에 머문다」다.

**② 「아직 안 훑었다」를 `Long.MIN_VALUE` 로 나타냈다.**

```java
private long 마지막청소나노 = Long.MIN_VALUE;   // ❌
nowNanos - Long.MIN_VALUE                      // 🔴 넘쳐서 «음수»가 된다
```

「시간이 한참 지났다」가 「아직 멀었다」로 뒤집혀서 **첫 청소가 영영 안 돌았다.**
지금은 `Long` 에 `null` 을 쓴다 — **「없다」를 특별한 «숫자»로 나타내면 이런 일이 난다.**

## 5. 🆕 읽다가 하나 더 — 응답 본문의 「없음」과 「빈 것」

요청 본문은 `bodyWasRead()` 로 이 둘을 갈랐는데, **응답 쪽에는 그 구별이 없었다.**
잡은 바이트가 0이면 무조건 빈 문자열로 적혔고, 그래서
**「스트림을 못 감쌌다」가 「빈 응답이었다」로 기록됐다.**

🔴 이 프로젝트가 잡으려는 결함과 **정확히 같은 모양**이다.

## 6. 🎯 잰 것 ① — 동시에 두드려도 비용이 그대로인가 (실험 ⑯)

실험 ⑩ 은 전부 **한 스레드**로 쟀다. 그런데 진짜 앱에서 링 버퍼를 두드리는 것은
톰캣 워커 수십 개이고, **사고가 나는 순간이 바로 그 수십 개가 동시에 두드리는 순간**이다.

```
── 실험 ⑯ 동시 기록 비용 ──
  스레드 1개: 3.00µs/건
  스레드 8개: 8.90µs/건
  배수      : 3.0배
  버린 이벤트: 93,829건 (큐가 차서 «못 받은» 것 — 버리는 것이 설계의 «의도»다)

── 실험 ⑯-② 한 건이 가장 오래 걸린 시간 ──
  스레드 16개 · 각 5,000건 → 최악 0.95ms
```

**스레드가 8배 늘 때 건당 비용은 3배**다. 선형 이하이므로 자물쇠가 무너지지는 않는다.
그리고 **한 건이 최악 0.95ms** — 넣는 쪽이 기다리는 설계였으면 여기서 초 단위가 나온다.

### ⚠️ 이 숫자를 실험 ⑩ 과 «나란히 놓으면 안 된다»

```
실험 ⑩  SQL 이벤트 하나  p50 0.793µs · p99 1.412µs   ← 백분위수
실험 ⑯  스레드 1개       3.00µs                       ← 평균, 링이 가득 찬 상태 포함
```

🔴 **재는 방법이 다르다.** ⑯ 은 평균이고 워밍업 뒤 링이 이미 가득 차서 밀어내기가
섞여 있다. 그래서 ⑯ 에서 의미 있는 값은 **절대값이 아니라 배수**다.

⬜ **요청당 추가 시간은 여전히 못 쟀다.** 요청 전체의 잡음(수 ms)이 재려는 값(수 µs)보다
세 자릿수 커서, 요청 안에서 재면 아무것도 안 보인다.

## 7. 🔴 잰 것 ② — 질의 모양 접기가 IN 절에서 «안 듣는다» (실험 ⑰)

```
── 실험 ⑰ IN 절의 모양 ──
  ... where o1_0.id in (?,?)
  ... where o1_0.id in (?,?,?)
  ... where o1_0.id in (?,?,?,?)
  ... where o1_0.id in (?,?,?,?,?)
  ... where o1_0.id in (?,?,?,?,?,?)
  🔴 같은 코드 한 줄이 만든 «서로 다른 모양»: 5가지
```

그래서 이렇게 된다.

```
── 실험 ⑰-② 반복이 얼마나 보이나 ──
  실제로 같은 코드가 돈 횟수: 5번
  🔴 오라클이 보는 「가장 많이 반복된 모양」: 1번
```

🔴 **5번 반복된 것이 오라클에는 1번으로 보인다.** 반복 문턱이 2이므로
**이 모양의 N+1 은 통째로 안 잡힌다.**

✅ **접기 자체는 듣는다** — IN 이 없으면 값 5가지가 모양 1가지로 접힌다.
문제는 IN 절 하나다.

### ⚠️ 여기서 «고치지 않았다»

고치려면 `in (?,?,?)` 를 `in (...)` 로 접어야 하는데, 그건 **기록기와 재생이 둘 다
같은 규칙으로** 바뀌어야 하는 일이다(`ShapeAgreementTest` 가 지키는 계약).
🔴 **기록 형식의 뜻이 바뀌는 판단이라 사람이 정할 일이다.**

## 8. ⬜ 무엇이 아직 확인 안 됐나

- 🔴 **IN 절 접기를 어떻게 할지 안 정했다.** 위 §7 이 「얼마나 나쁜가」만 못 박았다.
  ⬜ 접으면 **기록 형식의 뜻이 바뀐다** — 판 번호를 올릴지까지 같이 정해야 한다
- ⬜ **잊은 묶음 수가 기록 파일에 안 적힌다.** 적으려면 `Integrity` 에 자리를 하나 더
  만들어야 하고, 그건 기록 형식이 바뀌는 일이다. 지금은 코드에서만 읽을 수 있다
- ⬜ **⑧ 큐에 넣은 직후의 틈**은 그대로다. `accepted` 증가가 여전히 `offer` 뒤에 있다
- ⬜ **④ 되돌리기 부족이 `DIVERGED` 로 찍히는 것**도 그대로다. 등급은 아직 두 사실을
  뭉개고, PR 본문이 따로 적어서 가리고 있다
- ⬜ **동시 요청에서의 «요청당» 추가 시간**은 여전히 못 쟀다 (§6)
- ⬜ **32MB 상한이 실제로는 12MB 남짓만 담는 것**은 안 건드렸다
- 🔴 **「LLM 이 고칠 수 있는가」는 여전히 모른다.** 이건 API 키가 있어야 알 수 있다
