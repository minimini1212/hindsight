# 사람이 지키던 규율 둘을 빌드가 지키게 했다

> 2026-09-16. v0 4주차. 두 규율 다 **「나중에 붙인다」로 엿새 동안 남아 있던 것**이다.
> 무엇을 왜 접었는지는 [모듈 경계 판단](../../rules/module-boundary-decision.md)에 있다.

---

## 1. 무엇이 바뀌었나

| | 전 | 후 |
| --- | --- | --- |
| 빌드가 지키는 검사 | 3개 | **4개** (`checkPackageDirection` 추가) |
| 검사(테스트) | 237건 | **245건** (core 170 · recorder 43 · demo-app 32) |

### ① 패키지가 누구를 봐도 되는지 — `checkPackageDirection`

모듈을 13개에서 6개로 접을 때, 잃는 것은 **의존 방향 강제**뿐이고
「모듈 다섯 개보다 검사 한 개가 싸다」고 적어 뒀다. 그 검사가 이것이다.

지금 재어 본 실제 방향은 이렇다.

```
store   → privacy
privacy → (없음)
replay  → (없음)
guard   → (없음)
brain   → guard · replay
cli     → 전부 (조립하는 자리)
```

`cli` 는 조립하는 자리라 전부 열어 뒀다. 방향은 **아래쪽이 위를 못 보게** 하는 것으로 지킨다.

그리고 같은 검사가 하나 더 본다 — 🔴 **`brain` 은 파일을 직접 못 건드린다.**
이건 「`hindsight-guard` 는 막는 척한 것이었다」의 뒷정리다. 모듈 경계는 파일 쓰기를
못 막는다는 걸 그때 알았고, **진짜로 막는 자리를 여기 만들었다.**

### ② 본문이 파일까지 갔다 와도 글자 그대로인가 — 검사 8건

기존 왕복 시험은 `toJson → fromJson` 을 **메모리에서** 돈다. 실제 경로는 파일이고,
파일로 나갈 때 **UTF-8 로 부호화하는 단계가 하나 더** 있다. 그 단계는 메모리 왕복에서
절대 안 드러난다.

## 2. 🎯 잰 값

### 검사를 일부러 깨뜨려 봤다 — 넷 다 잡힌다

```
ⓐ brain 에 java.nio.file.Files 를 넣는다        → BUILD FAILED ✅
ⓑ store 가 brain 을 import 하게 만든다          → BUILD FAILED ✅
ⓒ 코덱에서 「왜 못 썼는지」 설명을 뺀다          → 시험 실패 ✅
ⓓ Files.writeString 대신 Files.write(bytes) 로  → 시험 실패 ✅
   (조용히 대체 문자로 바꿔 쓰게 된다)
되돌린 뒤                                        → BUILD SUCCESSFUL ✅
```

🔴 **통과만 하는 검사는 검사가 아니다.** ⓓ 가 특히 중요하다 — 파일 쓰는 방법을 한 줄
바꾸는 것만으로 본문이 조용히 바뀌는데, 그 한 줄은 리뷰에서 눈에 안 띈다.

### 본문에서 살아남는 것과 못 살아남는 것

```
✅ 제어 문자 (NUL · BS · FF · LF · CR · TAB · ESC · US)
✅ 따옴표 · 역슬래시 · 슬래시 · </script>
✅ BMP 밖 글자 — 이모지 · 높은음자리표 · 국기(지역 표시 두 개)
✅ CR LF 가 LF 로 안 접힌다
✅ 「빈 본문」과 「본문 없음」이 왕복 뒤에도 다르다

🔴 짝 없는 대리 문자 → 파일로 «안 써진다». 터진다
🔴 바이너리       → 코덱이 아니라 «잡는 자리»에서 이미 손실이다
```

### 🔴 주석을 걷어내는 것은 지금 «차이가 없다»

검사가 주석을 걷어내고 본다. 그런데 **지금 저장소에서는 걷어내나 안 걷어내나 0건으로 같다.**

```
주석 포함: 0건    주석 제거: 0건
```

⚠️ 그러니까 주석 제거는 **지금 무언가를 고친 게 아니라, 앞으로 생길 거짓 양성을 막는
것**이다. `PatchGuard` 의 javadoc 에 「`java.nio.file.Path#normalize()` 를 안 쓰는 이유」가
적혀 있는데, `guard` 는 파일을 건드려도 되는 패키지라 애초에 세는 대상이 아니었다.

🔴 **설명을 적었다는 이유로 검사에 걸리면, 다음 사람은 설명을 지운다.** 그 값이면 충분하다.

## 3. 🔴 이번에 «찾은» 것 — 기록이 통째로 날아가는데 이유를 안 알려 준다

짝 없는 대리 문자(surrogate, BMP 밖 글자를 `char` 두 개로 나눠 담을 때 쓰는 반쪽짜리 값)가
든 본문을 파일로 쓰면 이렇게 터졌다.

```
java.io.UncheckedIOException / 기록 파일을 쓰지 못했다: ...\broken.json
java.nio.charset.UnmappableCharacterException / Input length = 1
```

**운영자가 보는 것은 「Input length = 1」 뿐이다.** 그건 디스크 문제처럼 읽힌다.
실제로는 「본문에 UTF-8 로 적을 수 없는 글자가 있다」는 뜻인데도.

그래서 메시지가 이렇게 나오게 고쳤다.

```
기록 파일을 쓰지 못했다: ...\broken.json — UTF-8 로 적을 수 없는 글자가
JSON 885번째 자리에 있다 (U+D800, 짝 없는 대리 문자). 본문을 문자로 잡는
과정에서 깨진 것이다. 디스크 문제가 아니다.
```

🔴 **찾는 검사는 실패한 «뒤»에만 돈다.** 성공 경로의 비용은 0이다.

⚠️ **여기서 「고쳐서」 쓰지 않는다.** 물음표나 대체 문자로 바꿔 쓰면 기록은 남지만,
재생이 그 **바뀐 것끼리** 비교해서 「같았다」로 통과한다. 그건 이 도구가 잡으려는
결함 그 자체다 — 차라리 안 쓰고 시끄럽게 실패한다.

## 4. 까다로운 글자를 소스에 «적지» 않는다

처음에는 시험 문자열을 소스에 유니코드 이스케이프로 적었다. 그랬더니 —

```
소스 파일 안의 날 제어문자: NUL 1개 · US(0x1F) 1개
소스 파일 안의 진짜 이모지: 있음 (Write 도구가 이스케이프를 글자로 바꿔 넣었다)
```

javac 는 소스를 낱말로 쪼개기 **전**에 유니코드 이스케이프를 진짜 글자로 바꾼다.
그래서 이스케이프로 적으면 **소스 파일 안에 날 NUL 바이트가 들어앉고**, 이 시험이
무엇을 재는지가 편집기와 파일 인코딩에 따라 달라진다. 실제로 `\u00XX` 를 주석에
적었더니 `illegal unicode escape` 로 **컴파일이 깨졌다** — 주석인데도.

지금은 코드로 만든다. 그리고 **만든 값이 맞는지부터 단언한다.**

```java
String 제어문자들 = new String(new char[]{0, 8, 12, 10, 13, 9, 27, 31});
String 짝없는것 = ((char) 0xD800) + "짝이없다";
assertThat(Character.isHighSurrogate(짝없는것.charAt(0))).isTrue();
```

현재 소스 파일에 남은 날 제어문자: **0개**.

## 5. ⬜ 무엇이 아직 확인 안 됐나

- **진짜 바이너리 본문으로 기록을 떠 본 적이 없다.** 위 시험은 PNG 머리 8바이트를
  손으로 디코딩해서 흉내 낸 것이지, `demo-app` 에 파일 업로드를 보내 본 게 아니다.
  ⬜ 실제 업로드에서 이 실패가 어떤 모습으로 나오는지 **안 봤다**
- 🔴 **본문을 바이트로 잡는 쪽으로 바꿀지 «판단하지 않았다».** 지금 기록기는 본문을
  문자열로 잡는다(`CachingRequest` 가 문자셋으로 디코딩). 바이트로 잡으면 이 손실이
  사라지지만 기록 형식과 재생 비교가 같이 바뀐다 — 데이터 계약을 건드리는 결정이다
- **`cli` 에는 방향 제약이 사실상 없다.** 조립하는 자리라 전부 열어 뒀는데,
  ⬜ `cli` 가 커지면 이 판단을 다시 봐야 한다
- **검사가 보는 것은 `hindsight-core` 안뿐이다.** `recorder-simple` 과 `demo-app` 의
  패키지 방향은 ⬜ 안 본다
- **`getBytes`/`FileOutputStream` 같은 다른 파일 쓰기 통로는 안 센다.** 검사는
  `java.nio.file` 과 `java.io.File` 이름만 본다 — ⬜ 우회로가 남아 있다
