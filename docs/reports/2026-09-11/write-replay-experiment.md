# 2026-09-11 실측 3 — 「쓰기 요청은 채점할 수 없다」가 사실인가

> 같은 날 [Filter 포획 실측](http-capture-experiment.md)의 실험 ⑥ 이 내린 결론을 다시 쟀다.
> **뒤집혔다.** 코드: `demo-app/src/test/java/io/hindsight/demo/experiment/WriteReplayExperimentTest.java`

## §1 왜 다시 쟀나 — 실험 ⑥ 은 두 가지를 한 번에 바꿨다

실험 ⑥ 은 주문 생성(`POST /api/orders`)을 재생하고 응답이 다른 것을 보았다.
거기서 **「쓰기 요청은 같아질 수 없다 → 등급 체계가 하나 더 필요하다」**는 결론이 나왔다.

그런데 그 실험은 **원본 요청이 이미 DB 를 바꿔 놓은 자리 위에서** 재생을 돌렸다.

```
원본 POST ─▶ 주문 3번이 생긴다 ─▶ 그 상태 «그대로» 재생 ─▶ 주문 4번이 생긴다
                                    └ 되돌리는 단계가 없다
```

즉 한 번의 관찰에 원인 후보가 둘 섞여 있었다.

| 후보 | 맞다면 |
| --- | --- |
| ① **쓰기 요청이라서** 다르다 | 🔴 등급을 하나 더 만들어야 한다. 설계가 커진다 |
| ② **DB 를 안 되돌려서** 다르다 | 만들 게 없다. 재생 절차에 「복원」이 빠져 있었을 뿐이다 |

🔴 **둘은 완전히 다른 결론으로 간다.** 그래서 갈라서 쟀다.

## §2 어떻게 갈랐나 — 원본은 셋 다 같고, 되돌린 범위만 다르다

원본 요청·기록·재생 요청은 세 갈래가 전부 동일하다. **재생 직전에 DB 를 어디까지
되돌렸는지만** 다르다. 씨 뿌리는 절차도 하나로 묶어서, 결과가 갈리면 그 이유가
「되돌린 범위」 말고 다른 것일 수 없게 했다.

```
⑦-A  아무것도 안 되돌린다     ← 실험 ⑥ 과 같은 조건 (대조군)
⑦-B  «행»만 되돌린다          delete 로 지우고 같은 행을 다시 넣는다
⑦-C  «행 + 자동 증가 카운터»  truncate ... restart identity 로 지우고 다시 넣는다
```

⑦-B 와 ⑦-C 를 가르는 것은 **눈에 안 보이는 상태**다. 행을 다 지워도 H2 가 들고 있는
「다음 `id` 는 몇 번」이라는 숫자는 안 돌아간다. 그것도 DB 상태다.

## §3 나온 것

```
┌─ ⑦-A  되돌린 범위: 없음
│ 원본 응답 : 200 {"id":3,"product":"의자","memberName":"홍길동"}
│ 재생 응답 : 200 {"id":4,"product":"의자","memberName":"홍길동"}
│ 같은가    : false                     주문 행수 4 건
└─

┌─ ⑦-B  되돌린 범위: 행만
│ 기록된 요청    : {"memberId":1,"product":"의자"}
│ 복원 후 회원 id: 2   🔴 기록은 1 번을 가리키는데 실제로는 2 번이다
│ 재생 결과      : 예외 — 없는 회원: 1    주문 행수 2 건
└─

┌─ ⑦-C  되돌린 범위: 행 + 자동 증가 카운터
│ 원본 응답 : 200 {"id":3,"product":"의자","memberName":"홍길동"}
│ 재생 응답 : 200 {"id":3,"product":"의자","memberName":"홍길동"}
│ 같은가    : true                      주문 행수 3 건
└─
```

| 되돌린 범위 | 재생 결과 |
| --- | --- |
| 없음 | 응답이 다르다 (`id` 3 → 4) |
| 행만 | 🔴 **응답이 다른 게 아니라 재생이 터진다** — `없는 회원: 1` |
| 행 + 자동 증가 카운터 | ✅ **글자까지 같다** |

## §4 그래서 뒤집힌 것

### 🔴 ① 「쓰기 요청은 채점할 수 없다」는 틀렸다

⑦-C 가 반례다. **쓰기 요청도 글자까지 같은 응답이 나온다.** 원인은 쓰기라는 성질이 아니라
**되돌리지 않은 상태**였다. 등급을 하나 더 만들 필요가 없어졌다 —
네 등급(`VERIFIED_DETERMINISTIC`·`PARTIAL`·`DIVERGED`·`FAILED`)은 그대로 쓴다.

### 🔴 ② 축이 HTTP 메서드가 아니었다

「읽기는 되고 쓰기는 안 된다」로 갈랐던 것 자체가 틀린 축이다. 되돌리지 않으면
**읽기 요청도** 갈라진다 — 그 사이 다른 요청이 DB 를 바꿨으면 목록 조회의 응답도 달라진다.
실험 ⑤ 의 읽기 재생이 통과한 것은 읽기여서가 아니라 **그 사이 아무도 DB 를 안 바꿔서**다.

**진짜 축은 「복원했나」 하나다.**

### 🔴 ③ 행을 되돌리는 것은 상태를 되돌리는 것이 아니다 — ⑦-B 가 가장 무서운 결과다

⑦-B 는 행을 정확히 같은 내용·같은 개수로 복원했다. 그런데도 재생이 **예외로 죽었다.**
행에 붙은 `id` 가 1·2·3 이 아니라 2·4·5 여서, 기록에 담긴 `memberId: 1` 이 가리키는
회원이 없어졌기 때문이다.

🔴 **이게 가장 나쁜 모양인 이유**: 채점기는 이 예외를 「패치가 못 고쳤다」로 읽는다.
패치는 아무 잘못이 없는데 **복원을 덜 한 우리 쪽 때문에** LLM 이 벌을 받는다.
그리고 화면에는 「재생 실패」라고만 뜬다 — 원인을 볼 방법이 없다.

## §5 설계에 반영한 것

내용은 여기 다시 적지 않는다. 🧭 [`rules/replay-state-decision.md`](../../rules/replay-state-decision.md)

- 재생의 정의에 **복원**을 넣었다 ([`DESIGN.md`](../../DESIGN.md) §6-4)
- 복원을 어디까지 했는지 기록에 적는다 — 못 했으면 `PARTIAL` + `missing: ["STATE"]`
  ([`DATA_CONTRACT.md`](../../DATA_CONTRACT.md) §7-3)

## §6 이 실험이 «답하지 않은» 것

🔴 여기까지만 쟀다. 아래를 「됐다」로 읽으면 안 된다.

- **진짜 서비스의 DB 를 어떻게 기록 시점으로 되돌리나.** 이 실험은 H2 메모리라
  `truncate ... restart identity` 한 줄이면 됐다. 운영 DB 는 그렇지 않다. → TODOS 미결정
- **「행으로 안 보이는 상태」가 자동 증가 카운터 말고 또 뭐가 있나.** 전수로 안 세었다.
  지금 아는 것은 한 종류뿐이다
- **시각·난수는 여전히 못 잡는다.** 복원과 무관한 별개의 구멍이고, 그 기록은 그대로 `PARTIAL` 이다
- **`demo-app` 엔티티 2개·주문 3건**에서 잰 결과다. 연관이 깊어지면 복원 순서 문제가
  새로 생길 수 있다
