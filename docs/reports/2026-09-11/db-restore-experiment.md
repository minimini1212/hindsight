# 2026-09-11 실측 4 — DB 를 기록 시점으로 «어떻게» 되돌리나

> [쓰기 재생 실측](write-replay-experiment.md)이 「되돌리면 쓰기 요청도 글자까지 같다」를
> 보여 주고 남긴 숙제를 잰다. 그 실험은 H2 메모리라 `truncate ... restart identity`
> 한 줄이면 됐고, **되돌리는 방법 자체는 안 정했다.**
> 코드: `demo-app/src/test/java/io/hindsight/demo/experiment/StateRestoreExperimentTest.java`

## §1 두 가지를 잰다

| | 무엇을 | 왜 지금 |
| --- | --- | --- |
| **①** 「행으로 안 보이는 상태」를 **전수로** 센다 | 지금 아는 것은 자동 증가 카운터 하나뿐이고 **세어 본 적이 없다** | 목록이 다섯을 넘으면 복원 방식 자체를 다시 봐야 한다 |
| **②** 복원 후보 셋을 **갈라서** 잰다 | ㉠ 가짜 DB · ㉡ 스냅숏 · ㉢ 트랜잭션 롤백 | v0 재생기를 만들기 전에 정해야 한다 — 안 그러면 코드가 먼저 정한다 |

🔴 **기대값을 먼저 박지 않았다.** 숫자를 찍어 보고 그다음에 검증을 넣었다. 「스냅숏이 되겠지」로
시작하면 안 될 때 원인을 찾는 대신 실험을 고치게 된다.

## §2 ⑧-A 전수 세기 — 기억이 아니라 DB 에게 물었다

**세는 방법**: 「또 뭐가 있을까」를 떠올리지 않는다. H2 에게 *무슨 객체를 들고 있나*를 묻고,
그 목록을 훑어서 **값을 들고 있을 수 있는 것을 전부** 센다.

```
분모: INFORMATION_SCHEMA 가 노출하는 목록 35 개
     CHECK_CONSTRAINTS, COLLATIONS, COLUMNS, COLUMN_PRIVILEGES, CONSTANTS,
     CONSTRAINT_COLUMN_USAGE, DOMAINS, DOMAIN_CONSTRAINTS, ELEMENT_TYPES, ENUM_VALUES,
     FIELDS, INDEXES, INDEX_COLUMNS, INFORMATION_SCHEMA_CATALOG_NAME, IN_DOUBT,
     KEY_COLUMN_USAGE, LOCKS, PARAMETERS, QUERY_STATISTICS, REFERENTIAL_CONSTRAINTS,
     RIGHTS, ROLES, ROUTINES, SCHEMATA, SEQUENCES, SESSIONS, SESSION_STATE, SETTINGS,
     SYNONYMS, TABLES, TABLE_CONSTRAINTS, TABLE_PRIVILEGES, TRIGGERS, USERS, VIEWS
```

| 행 밖에서 **값**을 들고 있을 수 있는 것 | 개수 |
| --- | --- |
| 시퀀스 | **0** |
| 뷰 (스키마 `PUBLIC`) | **0** |
| 트리거 | **0** |
| 루틴(프로시저·함수) | **0** |
| 상수 | **0** |
| 도메인 | **0** |
| 동의어 | **0** |
| 미결 2단계 커밋 | **0** |
| **합계** | **0 개** |

⚠️ **스키마를 `PUBLIC` 으로 좁히지 않으면 뷰가 20개로 나온다** — `INFORMATION_SCHEMA` 자신의
뷰가 「우리 뷰」로 세인다. 좁히기 전 첫 측정이 그렇게 나왔고, 숫자가 거짓말을 하고 있었다.

### 🔴 그런데 시퀀스가 0 개인데 카운터는 있다 — 어디에 있나

「다음 `id` 는 몇 번」은 `INFORMATION_SCHEMA.SEQUENCES` 에 **안 나온다**(H2 2.x).
자동 증가 컬럼의 메타데이터를 통째로 찍어서 찾았다.

```
자동 증가 컬럼 2 개
  ── MEMBER.ID              ── ORDERS.ID
     IDENTITY_GENERATION = BY DEFAULT
     IDENTITY_START     = 1
     IDENTITY_INCREMENT = 1
     IDENTITY_BASE      = 4     ← 🎯 이게 「다음 id」다. 행 3건을 넣은 뒤라 4
     IDENTITY_CACHE     = 32    ← 🔴 처음 보는 항목. §5 에서 다룬다
```

🔴 **복원해야 할 것을 읽는 자리가 DB 마다 다르다.** H2 는 `COLUMNS.IDENTITY_BASE`,
PostgreSQL 은 시퀀스, MySQL 은 `AUTO_INCREMENT` 테이블 속성이다. v1 에서 DB 가 바뀌면
이 자리도 바뀐다.

### 그래서 복원 목록은 **둘**이다

**행**, 그리고 **자동 증가 카운터**(컬럼마다 하나 = 여기서는 2개). 다섯을 넘지 않았으므로
「목록이 다섯을 넘으면 복원 방식을 다시 본다」는 조건은 걸리지 않는다.

⚠️ 이 숫자는 **엔티티 2개짜리 `demo-app`** 에서 나온 것이다. 뷰·트리거·시퀀스를 쓰는 앱은
합계가 0 이 아니고, 그러면 목록이 늘어난다. **재는 방법이 결론보다 오래 쓰인다.**

## §3 ⑧-B · ⑧-C ㉢ 트랜잭션 롤백 — 행은 돌아오고 카운터는 안 돌아온다

```
┌─ ⑧-B 롤백이 되돌리는 범위
│ 주문 행수    : 3 → 3     ✅ 되돌아왔다
│ 다음 주문 id : 4 → 5     🔴 안 되돌아왔다
└─
```

**롤백은 행만 되돌린다.** 자동 증가 카운터는 롤백해도 전진한 채로 남는다 — DB 가 그 숫자를
트랜잭션 밖에서 관리하기 때문이다(그래야 동시에 들어온 트랜잭션들이 같은 `id` 를 못 받는다).

즉 ㉢ 은 데이터 계약이 **「가장 위험한 기록」**이라고 부르는 그 모양을 만든다 —
`rows: true, identityCounters: false` ([`DATA_CONTRACT`](../../DATA_CONTRACT.md) §7-3).

그 결과가 ⑧-C 다.

```
┌─ ⑧-C 롤백으로 감싼 재생을 두 번
│ 원본     : {"id":4,"product":"의자","memberName":"회원1"}
│ 재생 1회 : {"id":5,...}   🔴 원본과 다르다
│ 재생 2회 : {"id":6,...}   🔴 1회와도 다르다
│ 주문 행수: 4 건 (행은 매번 되돌아왔다)
└─
```

🔴 **재생이 결정론이 아니다.** 같은 기록을 두 번 재생하면 두 번 다른 답이 나온다. 채점기는
그 차이를 「패치가 못 고쳤다」로 읽고, 아무 잘못 없는 패치가 벌을 받는다.

## §4 ⑧-D ㉡ 스냅숏 — 행과 카운터를 «같이» 되돌린다

H2 의 `SCRIPT TO` 로 스냅숏을 뜨고, `DROP ALL OBJECTS` + `RUNSCRIPT FROM` 으로 되돌렸다.

```
┌─ ⑧-D 스냅숏
│ 스냅숏 크기       : 1,280 바이트   (회원 3 · 주문 3 건)
│ 뜨는 데           : 31 ms
│ 되돌리는 데       : 16 ms
│ 다음 주문 id      : 4 → (원본 요청 실행) → 4     ✅ 카운터까지 되돌아왔다
│ 복원 후 주문 행수 : 3 건
│ 원본 응답         : {"id":4,"product":"의자","memberName":"회원1"}
│ 재생 응답         : {"id":4,"product":"의자","memberName":"회원1"}   ✅ 글자까지 같다
└─
```

**되돌릴 목록을 우리가 나열하지 않아도 된다는 것**이 이 방식의 값이다. ⑧-A 에서 합계가 0 이었지만
뷰·트리거·시퀀스를 쓰는 앱에서는 0 이 아니고, 스냅숏은 그걸 **세지 않고도** 되돌린다.

⚠️ **16 ms 는 H2 메모리 · 6 행의 숫자다.** 운영 규모에서 얼마나 걸리는지는 **재지 않았다.**
이 결정을 뒤집는 조건이 그것이고, 결정 기록의 §4 에 적었다.

## §5 🔴 이 실험이 새로 찾은 것 — `IDENTITY_CACHE = 32`

전수 세기를 하다 나왔다. H2 는 자동 증가 값을 **세션에게 32개씩 미리 나눠 준다.**
행에도 안 보이고, 「다음 `id`」 한 숫자에도 안 담기는 상태가 **연결 쪽에** 하나 더 있다는 뜻이다.

🔴 **영향은 재지 않았다.** ⑧-B 에서 카운터는 4 → 5 로 한 칸만 움직였으니 이 실험 조건에서는
32개 블록이 눈에 띄는 모양으로 작동하지 않았다. 확인하려면 세션을 여러 개 띄워야 하고,
그건 이 실험의 범위 밖이다. **모른다고 적어 두고, 복원 목록에는 올린다** —
이게 「모름」을 「없음」으로 접지 않는 자리다.

## §6 ⑧-E ㉠ 가짜 DB — 「제대로 고친 패치」에 답할 값이 없다

가짜 DB 가 가진 것은 **기록에 담긴 질의뿐**이다. 그래서 N+1 의 정석 수정(회원을 조인으로 함께 읽기)이
보내는 질의에 답할 수 있는지를 셌다.

```
기록에 담긴 질의 모양 2 가지 · 실행 4 번
   1회  select o1_0.id,o1_0.member_id,o1_0.product from orders o1_0
   3회  select m1_0.id,m1_0.name from member m1_0 where m1_0.id=?      ← N+1 의 N

패치가 보낸 질의 1 가지
        select o1_0.id,m1_0.id,m1_0.name,o1_0.product
          from orders o1_0 join member m1_0 on m1_0.id=o1_0.member_id

그중 기록에 있던 것 : 0 / 1     🔴 가짜 DB 는 답할 값을 하나도 못 가지고 있다
```

같은 패치를 **복원된 진짜 DB** 에 돌리면 이렇게 된다.

```
원본 응답 : [{"id":1,"product":"상품1","memberName":"회원1"}, …3건]
패치 응답 : [{"id":1,"product":"상품1","memberName":"회원1"}, …3건]
같은가    : true     ✅ 채점이 된다
```

🔴 **이 0 / 1 이 후보 ㉠ 을 복원 수단에서 탈락시킨다.** 가짜 DB 로 재생하면 이 도구가 겨누는
대표 버그의 **정석 수정이 전부 채점 불가**(`DIVERGED`)로 떨어진다. 복원된 실 DB 는 같은 패치를
글자까지 같은 응답으로 채점한다.

⚠️ 가짜 DB 자체를 버리는 것이 아니다. **기록에 없는 질의를 알아채는 장치**로서는 그대로 필요하다
([`DESIGN`](../../DESIGN.md) §6-2). 그건 「채점하는 방법」이 아니라 「채점할 수 없다고 말하는 방법」이다.

## §7 설계에 반영한 것

내용은 여기 다시 적지 않는다. 🧭 [`rules/db-restore-decision.md`](../../rules/db-restore-decision.md)

- 복원 수단을 **스냅숏 되돌리기**로 정했다 ([`DESIGN.md`](../../DESIGN.md) §6-4)
- 복원 목록이 **둘(행 · 자동 증가 카운터)** 로 확인됐고, 세는 방법을 남겼다
- `IDENTITY_CACHE` 를 「보았지만 영향은 모른다」로 목록에 올렸다

## §8 이 실험이 «답하지 않은» 것

🔴 아래를 「됐다」로 읽으면 안 된다.

- **운영 규모에서 스냅숏 복원이 몇 초 걸리나.** 1,280 바이트 · 16 ms 는 H2 메모리 6행의 숫자다
- **운영 DB 의 기록 시점 스냅숏을 어디서 얻나.** v0 는 재생 환경이 H2 라 이 문제가 없다.
  v1 에서 진짜 DB 를 쓰면 다시 정해야 한다
- **`IDENTITY_CACHE = 32` 가 복원을 깨뜨릴 수 있나.** 세션 여러 개로 재야 한다
- **연관이 깊은 스키마에서 복원 순서 문제가 생기나.** 엔티티 2개에서 잰 결과다
- **캐시·정적 변수** — 설계 §4-2 가 애초에 「재현 안 된다」고 적어 둔 것이고 이 실험이 건드리지 않았다
