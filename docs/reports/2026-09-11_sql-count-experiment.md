# 2026-09-11 실측 — SQL 세기가 되는가

> 설계에 「그럴 것이다」라고 적어 둔 가정 둘을 처음으로 실제로 재 봤다.
> 코드: `demo-app/src/test/java/io/hindsight/demo/experiment/`

## §1 무엇을 재려고 했나

| # | 가정 | 틀렸다면 |
| --- | --- | --- |
| ① | `DataSource` 를 감싸면 앱이 보내는 SQL 이 **전부 보인다** | v0 기록 방식을 다시 짜야 한다 |
| ② | 한 번 실행한 SQL 이 **한 번만 세인다** | 「SQL 횟수」 오라클(설계 §6-1)이 무너진다 |
| ③ | 같은 조회를 두 번 하면 **같은 숫자**가 나온다 | 채점기가 매번 다른 답을 내면 채점이 아니다 |

🔴 **②가 진짜 걱정이었다.** 커넥션 풀(HikariCP)이 `PreparedStatement` 에 자기 껍데기를 한 겹
더 씌운다. 잡는 자리를 잘못 고르면 **풀의 껍데기와 드라이버의 진짜 구현이 둘 다 잡혀
같은 질의가 두 번 세인다.** 그러면 SQL 201건짜리 N+1 이 402건으로 보인다.

## §2 어떻게 쟀나

```
앱 ──▶ [우리 껍데기] ──▶ HikariCP ──▶ H2
          │
          └ DataSource → Connection → Statement 길목마다 얇게 덧씌우고
            execute 계열이 불릴 때만 «센다». 나머지는 그대로 통과시킨다
```

- 관측 대상: `demo-app` — 주문 목록 조회에 **일부러 심은 N+1** (`OrderService#findAll`)
- DB: **H2 메모리** — 서버도 도커도 안 띄웠다. 🔴 그래도 커넥션 풀은 HikariCP 그대로라
  ②를 확인하는 데 지장이 없다
- 붙인 자리: 스프링이 만든 `DataSource` 빈의 **바깥**. 🔴 **v0 기록기가 실제로 설 위치와 같다**
- 주문 20건 · 회원 20명

⚠️ **테스트에 `@Transactional` 을 안 붙였다.** 붙이면 저장과 조회가 같은 영속성 문맥에 묶여
회원이 이미 메모리에 있고, **N+1 이 안 일어난다.** 그러면 실험이 거짓말을 한다.

## §3 결과

```
┌─────────────────────────────────────────────────────────────
│ 🔬 실측 결과 — 주문 20건 조회
├─────────────────────────────────────────────────────────────
│ 돌려받은 주문     : 20 건
│ 나간 SQL 총 횟수  : 21 번
│ SQL 모양 종류     : 2 가지
├─ 모양별 횟수 ───────────────────────────────────────────────
│    1 번  select o1_0.id,o1_0.member_id,o1_0.product from orders o1_0
│   20 번  select m1_0.id,m1_0.name from member m1_0 where m1_0.id=?
└─────────────────────────────────────────────────────────────

🔬 같은 조회 두 번 → 21 번 / 21 번
```

| # | 가정 | 결과 |
| --- | --- | --- |
| ① | SQL 이 전부 보이나 | ✅ **보인다.** 21건 전부 |
| ② | 한 번만 세이나 | ✅ **21 = 1 + 20.** 42 가 아니다. **두 배로 안 세인다** |
| ③ | 두 번 돌리면 같은가 | ✅ **21 / 21** |

### 🎯 그리고 예상 못 한 수확 — 모양별로 묶으니 N+1 이 «그림»으로 보인다

```
   1 번  주문 목록
  20 번  회원 하나씩            ← 이 두 줄이 곧 N+1 의 서명이다
```

**「총 21번」보다 「한 모양이 20번」이 훨씬 강한 신호다.** 총 횟수는 데이터가 늘면 같이 늘어서
문턱을 정하기 어려운데, **「같은 질의가 여러 번」은 데이터 양과 무관하게 결함이다.**

🔄 **오라클(설계 §6-1)을 이 발견에 맞춰 다듬을 것.** 지금 설계는 「SQL 실행 수 ≤ K」인데,
「**같은 모양의 질의가 N번 이상 반복되면 안 된다**」가 더 정확하고 문턱도 덜 자의적이다.

## §4 왜 ②가 문제가 «안» 됐나

리뷰가 경고한 두 번 세기는 **바이트코드로 잡을 때** 생기는 문제다.
`hasSuperType(PreparedStatement)` 로 잡으면 풀의 껍데기와 드라이버 구현이 **둘 다** 걸린다.

v0 은 `DataSource` **바깥**에 한 겹만 덧씌운다. 우리 껍데기가 돌려준 `Statement` 만 세므로
안쪽에서 무슨 일이 있든 한 번이다.

⚠️ **즉 이 실험은 v1 의 위험을 없애 주지 않는다.** 에이전트로 갈 때 다시 재야 한다.
그때는 **이번 숫자(21)가 정답지 역할을 한다** — 에이전트가 21이 아닌 값을 내면 잡는 자리가 틀린 것이다.

## §5 겪은 것 둘

- **스프링 테스트는 생성자 주입을 기본으로 안 켠다** (`@TestConstructor` 기본값이 `ANNOTATED`).
  필드 주입 + `@Autowired` 로 바꿨다
- 🔴 **윈도우에서 Gradle 이 테스트 JVM 을 `x-windows-949` 로 띄운다.** 한글 출력이 전부
  깨져서 실측 결과를 읽을 수가 없었다. 루트 빌드에 `file.encoding=UTF-8` 을 박았다.
  문서·테스트 이름이 전부 한글인 프로젝트라 이건 배관이 아니라 **필수**다
