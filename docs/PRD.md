# PRD.md — Hindsight

> 무엇을 **왜** 만드는가. 어떻게 만드는가는 [DESIGN.md](DESIGN.md) 에 있다.

---

## §0 이 문서에 나오는 말

| 말 | 뜻 |
| --- | --- |
| 재현(reproduce) | 한 번 일어난 오류를 개발자 컴퓨터에서 똑같이 다시 일으키는 것 |
| 회귀(regression) | 고쳤던 버그가 나중에 되살아나는 것 |
| 회귀 테스트 | 그 되살아남을 막으려고 저장소에 영구히 남기는 테스트 |
| 관측 도구(APM) | 운영 중인 앱의 상태를 밖에서 지켜보는 도구. Datadog·New Relic 같은 것 |
| 에이전트(agent) | 관측 대상 앱과 같은 JVM 안에서 도는 코드 |

## §1 무슨 문제를 푸는가

운영 중인 자바 서비스에서 오류가 났을 때, 개발자의 시간은 **고치는 데** 들지 않는다.
**「무슨 일이 있었는지 알아내는 데」** 든다.

```
장애 접수  ─→  로그를 뒤진다   ─→  재현을 시도한다  ─→  원인을 찾는다  ─→  고친다  ─→  테스트를 짠다
              (한나절)          (안 되는 날이 많다)   (한나절)        (10분)     (한 시간)
                └──────────────────────────────────────────┘
                            여기가 시간의 대부분이다
```

가장 자주 나오는 말이 **「우리 쪽에선 재현이 안 되는데요」** 다. 이유는 단순하다.
**그 순간의 입력값이 아무 데도 안 남아 있다.**

- 로그에는 개발자가 **미리 찍어두기로 정한 것만** 있다. 정작 필요한 값은 대개 안 찍혀 있다
- 관측 도구(APM)는 「느리다」·「몇 번 터졌다」는 **집계**를 준다. 「어떤 값으로 터졌나」는 안 준다
- 스택 트레이스는 **어디서** 터졌는지는 알려주지만 **왜**는 안 알려준다

## §2 그래서 무엇을 만드나

> **오류가 나면 스스로 그 순간으로 되감아 재현하고, 원인을 짚고, 고쳐보고,
> 진짜 고쳐졌는지 스스로 채점한 뒤, 근거를 갖춘 PR을 올려놓는 도구.**
> 배포 버튼은 사람이 누른다.

앱에 옵션 한 줄(`-javaagent:hindsight-agent.jar`)만 붙이면 된다. 소스는 안 고친다.

## §3 왜 지금, 왜 이 조합인가

기록과 진단은 각각 따로 존재해 왔다. **둘을 붙이면 없던 것이 하나 생긴다 — 채점기다.**

| 가진 것 | 혼자서는 | 붙이면 |
| --- | --- | --- |
| 진단만 (LLM) | 「이게 원인인 것 같다」에서 끝. **맞는지 확인할 방법이 없다** | — |
| 재현만 (기록·재생) | 「재현은 해줄 테니 원인은 네가 찾아라」 | — |
| **둘 다** | — | **LLM의 패치를 기계가 걸러낸다** |

지금 AI 코딩 도구의 최대 약점은 *"그럴듯한데 맞는지 모르겠다"* 다. 재현이 가능하다는 것은
곧 **채점이 가능하다**는 뜻이고, 그러면 사람이 읽어야 할 후보의 수가 크게 준다.

### 🔴 §3-1 이 주장을 정확한 크기로 적어 둔다

> **채점기는 명백히 틀린 패치를 걸러낸다. 맞는 패치임을 증명하지는 않는다.**

⚠️ **「테스트가 통과했으니 고쳐진 것」은 이미 실패로 판명된 생각이다.** 자동 프로그램 수정
(automated program repair) 분야에서 측정한 **과적합률** — 채점은 통과했지만 실제로는 안 고쳐진
비율 — 이 연구에 따라 73~98%다. 그 분야가 「테스트 통과」를 정답 신호로 쓰기를 포기한 이유다.

그래서 이 프로젝트는 채점을 **증명이 아니라 거름망**으로 다루고, 거름망을 네 겹으로 쌓으며
(설계의 과적합 방지 절 §7-2), 마지막에 반드시 사람을 세운다. 🔴 **이 문단을 지우면
이 도구는 그럴듯한 오답 생성기가 된다.**

## §4 누가 쓰나

| 쓰는 사람 | 지금 하는 일 | 이 도구가 있으면 |
| --- | --- | --- |
| 서비스 담당 개발자 | 로그를 뒤지고 재현을 시도한다 | 기록을 열고 재생 버튼을 누른다 |
| 코드를 리뷰하는 사람 | 「이게 진짜 고친 게 맞나」를 눈으로 본다 | PR에 붙은 재생 결과를 본다 |
| **코딩 에이전트** | 운영 상황을 볼 수 없다 | 기록을 직접 읽고 재생한다 (v3) |

## §5 성공을 무엇으로 재나

| 재는 것 | 기준 |
| --- | --- |
| 사람 손 없이 **PR 하나**가 올라오고, 그 PR이 네 겹 채점을 다 통과하는가 | **v0 완료 조건** |
| 옵션 한 줄(`-javaagent`)로 아무 스프링 앱에 붙는가 | v1 완료 조건 |
| **오픈소스 프로젝트의 진짜 버그 3건**을 처리하는가 | v2 완료 조건 (설계 §11-1) |
| 붙였을 때 요청당 얼마나 느려지는가 | **50µs 이하** (설계 §10) |
| 개인정보가 기록 파일에 남는가 | **0건.** 가명화 검사가 통과해야 한다 |

🔴 **모든 단계의 성공 기준이 「사람 손 없이」로 끝난다.** 중간에 사람이 한 번이라도 손을 대면
그건 아직 안 된 것이다.

## §5-1 대표 예제는 N+1이 아니다

⚠️ N+1은 **아는 사람이 30초에 고치는 것**이다. 이걸 대표 예제로 쓰면 「쉬운 걸 비싸게 하는 도구」로
보인다. 대표 예제는 이것으로 잡는다.

> 새벽 3시에 협력사 API가 이상한 응답을 **한 번** 보냈고, 그걸로 NPE가 났다.
> 로그에는 스택 트레이스만 있다. **그 응답을 다시 얻을 방법이 없다.**

「그때 그 입력을 다시 얻을 수 없다」는 백엔드 개발자면 누구나 하루씩 날려 본 문제다.
N+1은 **오라클(테스트가 무엇을 검사하는지)을 설계하는 데 쓰는 시험 문제**로 남기고,
홍보 문구로는 쓰지 않는다.

## §5-2 어떻게 보여주나

완료 기준은 공학의 기준이고, 면접을 만드는 것은 **3분짜리 영상 하나**다.
그 장면을 먼저 정해 두고 거기에 맞춰 만든다.

> 데모 앱에 부하 → 예외 발생 → 화면에 *"기록 #17 포획됨"* →
> `hs replay 17` 로 **실패하는 테스트가 생김** → `hs diagnose 17` 로 원인과 패치 →
> **네 겹 채점을 통과** → **PR이 올라옴** → 그 테스트가 저장소에 남음

## §6 무엇을 하지 않는가 (범위 밖)

| 안 하는 것 | 왜 |
| --- | --- |
| **운영 배포** | 재생 통과는 「이 상황이 고쳐졌다」일 뿐 「다른 게 안 망가졌다」가 아니다 |
| 경쟁 상태(스레드 순서 버그)의 완전 재현 | 연구 영역. 상용 도구도 못 한다. 「의심된다」까지만 말한다 |
| 단계별 되감기 디버거 | 그건 다른 물건이다. 우리는 경계 값만 잡는다 |
| 여러 서비스를 가로지르는 재현 | v3 이후에 검토. 지금 설계하지 않는다 |
| 상용 관측 도구 대체 | 대시보드·알림·집계는 하지 않는다. 겹치지 않고 **붙여 쓴다** |

## §7 이미 있는 것들과 무엇이 다른가

🔴 **「세상에 없다」고 말하지 않는다.** 겹치는 것부터 적는다.

| 이미 있는 것 | 무엇을 하나 | **우리보다 나은 점** | 우리가 이기는 한 축 |
| --- | --- | --- | --- |
| **Keploy** (Go) | API·DB 호출을 기록해 테스트를 만든다. 자바용 에이전트도 있다 | 언어를 안 가린다. eBPF로 소켓에서 잡아 계측이 덜 든다 | 🎯 **소켓에서는 `Instant.now()`·`UUID.randomUUID()` 가 안 보인다.** 프로세스 안에서 일어나니까. 그래서 **재생이 얼마나 믿을 만한지를 잴 수 없다** (설계 §6-3) |
| **ReCrash** (ECOOP 2008) | 메서드 인자를 버퍼에 들고 있다가 크래시가 나면 JUnit 테스트를 만든다 | **우리와 거의 같은 일**을 18년 전에 했고, javac·Eclipse에서 실증했다 | LLM 이전 물건이라 「테스트를 만들어 사람이 본다」가 끝. 논문이 보고한 상시 부담이 **13~64%** 다 |
| **테스트 카빙**(carving) | 시스템 테스트에서 단위 테스트를 잘라낸다 | 이 방식의 **학술적 이름이 이것**이다 | 운영 중 사고를 방아쇠로 삼지 않는다 |
| **JFR** (JDK 기본) | GC·락·스레드 지표 | 공짜이고 이미 검증됐다 | 요청 본문·SQL 파라미터 같은 **값**은 안 남는다. 우리가 **그대로 갖다 쓴다** |
| **APM** (Datadog 등) | 지연·오류율 집계 | 운영에서 이미 표준 | 재현을 못 한다. 「어떤 값으로 터졌나」가 없다 |
| **Sentry Autofix 등** | 오류를 LLM으로 진단하고 PR을 올린다 | **이미 상용으로 판다** | 재생으로 채점하지 않는다 — 우리가 §7-2를 쌓는 이유 |
| **OpenTelemetry** | 추적의 표준 규격 | — | 경쟁이 아니라 **붙일 것**. 추적 ID를 빌려 쓴다 |
| **Undo LiveRecorder** | 실행을 기록해 되감는다 (주로 C/C++) | 되감기 깊이가 비교가 안 된다 | 상용. JVM+LLM 조합이 아니다 |

**셋을 한 물건에 넣은 것이 다른 점이다**: JVM 안에서 보기에 시각·난수까지 잡는 깊이 ·
LLM 패치를 재생으로 걸러내는 고리 · 코딩 에이전트에게 열어주는 통로.

🔴 **두 번째만 진짜 새로운 것이고 나머지 둘은 조합이다. 면접에서 이 구분을 흐리지 않는다.**
⚠️ **「세상에 없다」고 말하지 않는다.** 나를 이기는 도구의 이름을 먼저 말하는 것이
포트폴리오에서 신뢰를 얻는 가장 빠른 방법이다.

## §8 무엇이 이 프로젝트를 죽일 수 있나

| 위험 | 어떻게 막나 |
| --- | --- |
| 에이전트가 남의 앱을 죽인다 | 의존성 0 · 예외 봉쇄 · 자기 무력화 (설계 §2, 규율 파일) |
| 「얼마나 느려지는데?」에 답 못 한다 | 예산을 먼저 정하고 측정을 프로젝트에 포함 (설계 §9) |
| LLM이 테스트를 지워 통과시킨다 | 경로 화이트리스트 + 테스트 매번 재생성 (설계 §6-1) |
| 개인정보가 샌다 | 결정론적 가명화, 한 곳에서만 (설계 §8) |
| 범위가 폭주해 v0도 못 끝낸다 | v0에서 나간 요청·시각·난수를 뺐다 (설계 §10) |
