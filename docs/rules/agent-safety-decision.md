# 에이전트 안전 결정 — 우리가 죽을 때 남을 죽이지 않는다

> **2026-09-10 결정.** 설계 리뷰가 「앱을 죽일 수 있는 경로」를 여섯 개 짚었고, 그중 다섯 개가
> 처음 설계에 아예 없었다. 리뷰 원문 요약: [../review/2026-09-10-design-review.md](../review/2026-09-10-design-review.md)

## §1 무엇을 정했나

> **관측이 실패하는 것보다 관측 대상이 실패하는 것이 훨씬 나쁘다.**
> 둘 중 하나를 골라야 하면 **언제나 우리가 죽는다.**

성능을 보려고 붙였다가 서비스를 내리는 도구는 아무도 안 쓴다. 이건 취향이 아니라 이 부류
도구의 생존 조건이고, Datadog·New Relic 같은 상용 에이전트가 전부 지키는 선이다.

## §2 무엇을 알고 그렇게 정했나

리뷰가 짚은 죽는 경로들. 🔴 **의존성 충돌은 이 중 오히려 덜 흔한 쪽이었다.**

| 경로 | 무슨 일이 나나 | 막는 법 |
| --- | --- | --- |
| 🔴 **부트스트랩 가시성** | `java.time.Instant` 에 끼워 넣은 코드가 시스템 클래스로더에 있는 우리 클래스를 못 찾아 `NoClassDefFoundError`. **JVM이 아예 안 뜬다** | `hindsight-agent-boot` 을 `premain` 에서 부트스트랩에 먼저 올린다 |
| 예외 전파 | 계측 코드가 던진 예외가 남의 요청 스레드를 타고 올라간다 | 모든 진입점 `try { … } catch (Throwable)`. **절대 밖으로 안 던진다** |
| 힙 고정 | `HttpServletRequest`·`ResultSet`·엔티티를 60초 붙들면 남의 힙에서 OOM | 잡는 즉시 스칼라로 복사. **참조를 안 들고 있는다** |
| 무한 큐 | 트래픽이 튀면 큐가 자라 OOM | **유계 큐.** 차면 버리고 센다 |
| 재진입 | 에이전트의 파일 쓰기가 다시 계측에 걸려 무한 루프 | `ThreadLocal` 재진입 가드 |
| 스레드 정체 | 100ms 걸리는 덤프가 보관 스레드를 막아 **하필 사고 순간에** 이벤트를 버린다 | 덤프는 별도 I/O 스레드 |
| 의존성 충돌 | 우리가 끌고 들어간 Jackson 2.17이 앱의 2.15와 부딪힌다 | 셰이딩 + 빌드 검사 (§3) |

## §3 🔴 의존성 금지선은 빌드가 지킨다

문서에 「의존성 0」이라고 적어두는 것만으로는 **안 지켜진다.** 언젠가 누군가(사람이든 Claude든)
편하다는 이유로 한 줄을 추가하고, 그 순간 남의 클래스패스가 오염된다. 조용히.

그래서 `build.gradle.kts` 의 `checkAgentDependencies` 가 `check` 에 걸려 있다.
허용 목록(`byte-buddy`, `hindsight-model`) 밖의 의존성이 `runtimeClasspath` 에 들어오면
**빌드가 실패한다.**

⚠️ **「의존성 0」이라고 쓰지 않는다.** 표에 ByteBuddy가 있는데 0이라고 하면 그냥 틀린 말이다.
정확한 표현은 **「셰이딩된 것 딱 하나」** 다.

🔴 그리고 `hindsight-model` 에 **Jackson 애너테이션을 붙이지 않는다.** 붙이는 순간
`jackson-annotations` 가 model의 의존성이 되고, 에이전트가 model을 쓰므로 **Jackson이 남의 JVM에
들어간다.** 매핑 설정은 전부 `hindsight-core` 쪽 믹스인에 둔다.

## §4 무엇을 버렸나

| 검토했지만 안 쓴 길 | 왜 |
| --- | --- |
| 셰이딩만으로 격리 | 셰이딩은 **이름 충돌만** 푼다. 우리 클래스가 앱에 보이는 것 자체는 안 막는다. 그래서 v1에 격리 클래스로더를 넣는다 |
| ByteBuddy도 안 쓰고 직접 ASM | ByteBuddy는 그 자체로 런타임 의존성이 없고(ASM을 이미 안에 넣어 뒀다) Datadog·OpenTelemetry가 실제로 셰이딩해 쓴다. 직접 짜는 값이 이득보다 크다 |
| 에이전트를 아예 안 쓰고 라이브러리로 | 소스를 고쳐야 한다. 「옵션 한 줄로 붙는다」가 이 도구의 값어치라 포기할 수 없다. **다만 v0은 이 방식으로 간다** — 위험을 뒤로 미루려고 (build-order-decision) |

## §5 무엇이 이 결정을 뒤집게 만드나

- 자기 무력화가 **자주** 걸린다면, 그건 안전장치가 아니라 계측이 잘못된 것이다.
  무력화 횟수를 세고, 잦으면 설계를 다시 본다
- 유계 큐가 정상 트래픽에서도 자꾸 찬다면 창 크기나 잡는 범위가 틀린 것이다
- 🔴 **성능 예산(요청당 50µs)을 못 지키면 못 지켰다고 적는다.** 참고로 비슷한 도구(2008년 ReCrash)가
  논문에서 보고한 상시 부담은 **13~64%** 다. 5%는 야심찬 목표지 당연한 값이 아니다
