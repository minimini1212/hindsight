# 재생 전 DB 복원 방법 — 스냅숏으로 되돌린다

> **2026-09-11 결정.** [재생의 정의에 복원을 넣은 결정](replay-state-decision.md)이 남긴 숙제다.
> 🧭 근거가 된 숫자: [`reports/2026-09-11/db-restore-experiment.md`](../reports/2026-09-11/db-restore-experiment.md)

## 1. 무엇을 정했나

🔴 **재생 전 복원은 「스냅숏을 떠 두고 그걸로 되돌리기」로 한다.** 되돌릴 항목을 우리가
나열해서 하나씩 원복하는 방식(행 지우고 다시 넣기, 트랜잭션 롤백)은 쓰지 않는다.

그리고 **가짜 DB 는 복원 수단이 아니다.** 기록에 없는 질의를 알아채는 장치로만 남는다
([`DESIGN`](../DESIGN.md) §6-2) — 그건 채점하는 방법이 아니라 채점할 수 없다고 말하는 방법이다.

## 2. 무엇을 알고 그렇게 정했나

### 후보 셋을 갈라서 쟀다

| 후보 | 결과 |
| --- | --- |
| ㉠ **가짜 DB** — 기록된 질의에만 답한다 | 🔴 N+1 의 정석 수정이 보낸 질의가 기록에 **0 / 1** 로 없다. 이 도구가 겨누는 대표 버그의 제대로 된 수정이 전부 채점 불가가 된다 |
| ㉡ **스냅숏** — 떠 두고 그걸로 되돌린다 | ✅ 행과 자동 증가 카운터가 **같이** 돌아왔다. 쓰기 요청 재생이 글자까지 같다. 1,280 바이트 · 복원 16 ms (H2 메모리 · 6행) |
| ㉢ **트랜잭션 롤백** — 열고 재생한 뒤 되돌린다 | 🔴 행은 돌아오는데 **다음 `id` 가 4 → 5 로 남는다.** 재생을 두 번 하면 `id` 가 4 · 5 · 6 으로 갈린다 — 재생이 결정론이 아니다 |

### 🔴 스냅숏을 고른 진짜 이유는 속도가 아니라 「세지 않아도 된다」는 것이다

되돌릴 것을 **전수로 세어 봤다.** H2 에게 무슨 객체를 들고 있나를 묻고(`INFORMATION_SCHEMA`
목록 35개가 분모) 값을 들고 있을 수 있는 것을 전부 세니 **행 밖의 객체는 0 개**였고,
복원 목록은 **행 · 자동 증가 카운터** 둘이었다.

🔴 **그런데 그 0 은 엔티티 2개짜리 `demo-app` 의 0 이다.** 뷰·트리거·시퀀스를 쓰는 앱에서는
0 이 아니고, 그러면 「나열해서 원복하는」 코드는 조용히 한 항목을 빠뜨린다. 그게 부분 복원이고,
부분 복원은 무복원보다 위험하다 — 무복원은 답이 다르게 나와서 눈에 띄지만, 부분 복원은
**재생이 죽고 채점기가 그걸 「패치가 못 고쳤다」로 읽는다.**

스냅숏은 목록을 몰라도 되돌린다. **틀릴 수 있는 자리가 없는 쪽을 골랐다.**

### 🔴 반대 근거 — 이걸 알고도 이렇게 정했다

- **운영 규모 복원 시간을 재지 않았다.** 16 ms 는 6행짜리 H2 메모리다. 재생 한 번에 스냅숏
  복원이 몇 분 걸리면 고리가 안 돈다. 이것이 이 결정을 뒤집는 첫 번째 조건이다(§4)
- **운영 DB 의 「기록 시점 스냅숏」을 어디서 얻나는 답하지 않았다.** v0 는 재생 환경이 H2 라
  이 문제가 없다. v1 에서 진짜 DB 를 쓰면 다시 정한다
- **행 밖에 상태가 하나 더 있다는 걸 알았고, 영향은 모른다.** H2 는 자동 증가 값을 세션에게
  32개씩 미리 나눠 준다(`IDENTITY_CACHE = 32`). 이 실험 조건에서는 눈에 띄는 모양으로
  작동하지 않았지만, **영향이 없다고 재지는 않았다.** 모름으로 적어 두고 목록에 올렸다
- **복원해야 할 값을 읽는 자리가 DB 마다 다르다.** H2 는 `COLUMNS.IDENTITY_BASE`,
  PostgreSQL 은 시퀀스, MySQL 은 `AUTO_INCREMENT` 속성이다. 스냅숏 방식은 이 차이를
  **읽지 않아도** 되지만, 「복원됐는지 확인하는」 코드는 여전히 DB 별로 갈린다

## 3. 무엇을 버렸나

| 버린 길 | 왜 |
| --- | --- |
| 🔴 **트랜잭션 롤백 단독** | 카운터가 안 돌아온다. 재생 두 번의 답이 4 · 5 · 6 으로 갈렸다. 데이터 계약이 「가장 위험한 기록」이라고 부르는 `rows: true, identityCounters: false` 를 **매번** 만든다 ([`DATA_CONTRACT`](../DATA_CONTRACT.md) §7-3) |
| 🔴 **가짜 DB 로 재생하기** | 정석 수정이 보낸 질의가 기록에 0 / 1 로 없다. 「얕은 패치는 통과하고 구조적 수정은 채점 불가」가 되어 채점기가 거꾸로 작동한다 |
| **행을 지우고 다시 넣기** | 실험 ⑦-B 가 이미 답했다 — 재생이 예외로 죽는다 ([replay-state-decision](replay-state-decision.md)) |
| **되돌릴 항목을 나열해서 원복하기** | 지금 목록이 둘이라 할 수 있어 보이지만, 목록은 앱마다 다르고 늘어난다. 한 항목을 빠뜨린 날이 부분 복원이 되는 날이다 |
| **`id` 처럼 달라지는 자리를 빼고 비교하기** | 이 프로젝트가 금지한 모양이다. 「다를 수 있으니 안 본다」는 「모름」을 「없음」으로 접는 것이다 |

## 4. 무엇이 이걸 뒤집게 만드나

- **운영 규모에서 스냅숏 복원이 재생 한 번당 수 분으로 나올 때.** 그때는 스냅숏을 매번 되돌리는
  대신 「기록에 담긴 질의에만 답하는 가짜 DB + `DIVERGED`」로 가고, **채점할 수 있는 패치의 범위가
  줄어드는 것을 대가로 받아들인다.** 🔴 그 경우 「제대로 고친 패치를 채점 못 한다」를
  한계로 명시한다 — 조용히 통과시키지 않는다
- **`IDENTITY_CACHE` 같은 「연결에 딸린 상태」가 복원을 깨뜨리는 사례가 나올 때.** 스냅숏으로도
  DB 밖의 상태는 안 돌아온다. 그러면 복원 범위에 「연결을 새로 맺는다」가 들어간다
- **복원 목록이 다섯을 넘을 때.** 지금은 둘이다. 넘으면 「무엇을 되돌렸는지」를 기록에 적는
  방식 자체를 다시 본다 (필드 넷으로 못 담는다)
- **복원했는데도 갈리는 사례가 나올 때.** 그건 복원 범위 밖의 비결정성(시각·난수·순서)이고,
  이 결정이 아니라 계측 쪽 문제다
