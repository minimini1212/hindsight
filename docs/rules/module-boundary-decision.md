## §2 왜 13개는 틀렸나

### 강제되는 것과 아닌 것

| 원래 모듈 | 따로 둔 이유였던 것 | 진짜인가 |
| --- | --- | --- |
| `model` | 안팎이 공유하는데 안쪽은 의존성을 못 늘린다 | ✅ **물리적** |
| `agent` | 셰이딩된 별도 jar, manifest 가 다르다 | ✅ **물리적** |
| `agent-boot` | **다른 클래스로더**. 같은 jar 에 못 넣는다 | ✅ **물리적** |
| `demo-app` | 관측 대상 | ✅ 당연 |
| `recorder-simple` | v0 기록기 | ✅ **§3 — 오히려 거꾸로 알고 있었다** |
| `guard` | 「파일을 쓰는 유일한 통로」 | ❌ **§4 — 자기기만** |
| `core`·`replay`·`brain`·`cli`·`mcp`·`server`·`testkit` | 개념이 다르니까 | ❌ 패키지면 된다 |

### 개념이 다른 것은 모듈이 아니라 패키지다

「재생」과 「진단」이 다른 일인 건 맞다. 그런데 그걸 **모듈**로 가르면 무엇을 얻나?

- 빌드 파일이 하나 더 생긴다
- `settings.gradle.kts` 가 길어진다
- 이름을 하나 더 외워야 한다
- 클래스 한두 개짜리 모듈이 생긴다

얻는 것은 **의존 방향 강제**뿐이다(「재생은 진단을 몰라야 한다」 같은 것).
그건 값이 있지만, 모듈 다섯 개보다 **검사 한 개**가 싸다. ⬜ 나중에 붙인다 (TODOS).

## §3 🔴 `recorder-simple` 은 거꾸로 알고 있었다

접으려다 알아챘다. **`recorder-simple` 을 `core` 에 합치면 안 된다.**

```
recorder-simple 는 demo-app «안»에서 돈다
  → demo-app 이 그걸 의존한다
  → 그게 core 안에 있으면 demo-app 이 core 를 의존한다
  → 🔴 Spring AI 와 picocli 가 관측 대상 앱으로 딸려 들어간다
```

**우리가 막으려던 바로 그 일이다.** 에이전트만 조심하면 된다고 생각했는데,
v0 의 기록기도 «남의 앱 안»에 들어가는 물건이라 같은 규칙을 받는다.

🧭 이게 §1 의 기준이 옳다는 증거다. 「개념」으로 나눴으면 놓쳤을 것을
「누구의 클래스패스」로 물으니 바로 보였다.

## §4 🔴 `hindsight-guard` 는 막는 척한 것이었다

원래 이유: *"패치 경로 검사를 자기 모듈에 두면, 우회하려면 눈에 띄게 이상한 것을 import 해야 한다."*

**틀렸다.** 모듈 경계는 파일 쓰기를 **못 막는다.** 같은 프로젝트 안의 다른 코드가
`java.nio.file.Files` 를 직접 부르면 그만이다. 그건 우리 모듈을 우회한 게 아니라
**애초에 우리 모듈을 안 쓴 것**이고, Gradle 은 그걸 모른다.

즉 모듈 경계는 **보안 장치가 아니라 그림**이었다. 진짜로 막으려면 둘 중 하나다.

- ⬜ **검사로 막는다** — 「`brain` 패키지가 `java.nio` 를 직접 부르면 실패」. 아직 없다 (TODOS)
- ✅ **채점으로 막는다** — 이미 있다. 패치가 건드린 경로를 `git apply` **전에** 확인하고,
  재생 테스트는 매번 기록에서 새로 만든다 (설계 §7-1)

⚠️ **그림을 장치로 착각한 것이 이 실수의 본질이다.**
`guard` 는 `io.hindsight.core.guard` 패키지로 남는다. 하는 일은 그대로다.

## §6 무엇이 이 결정을 뒤집게 만드나

- **화면이 필요해지면** `hindsight-server` 를 진짜로 가른다. Spring Boot 플러그인은
  모듈 단위라 그때는 선택의 여지가 없다. **미리 만들지는 않는다**
- `hindsight-core` 가 너무 커져서 한 사람이 훑기 어려워지면 다시 본다.
  🔴 다만 그때도 기준은 「개념이 다르다」가 아니라 **「올라가는 자리가 다르다」**여야 한다
- 여러 사람이 나눠 맡게 되면 모듈 경계가 소유권 경계로 값을 한다. 지금은 1인이라 해당 없다
