> 라는 질문을 받고 다시 세어 보니, **물리적으로 강제되는 것은 넷뿐**이었다.

| 모듈 | 어디에 올라가나 | 자바 |

## §2 왜 13개는 틀렸나

### 강제되는 것과 아닌 것

| 원래 모듈 | 따로 둔 이유였던 것 | 진짜인가 |
| --- | --- | --- |
| `model` | 안팎이 공유하는데 안쪽은 의존성을 못 늘린다 | ✅ **물리적** |
| `agent` | 셰이딩된 별도 jar, manifest 가 다르다 | ✅ **물리적** |
| `agent-boot` | **다른 클래스로더**. 같은 jar 에 못 넣는다 | ✅ **물리적** |
| `demo-app` | 관측 대상 | ✅ 당연 |
| `recorder-simple` | v0 기록기 | 🔄 **§3 에서 「따로여야 한다」고 했다가 §6-2 에서 뒤집었다** |
| `guard` | 「파일을 쓰는 유일한 통로」 | ❌ **§4 — 자기기만** |
| `core`·`replay`·`brain`·`cli`·`mcp`·`server`·`testkit` | 개념이 다르니까 | ❌ 패키지면 된다 |

### 개념이 다른 것은 모듈이 아니라 패키지다

「재생」과 「진단」이 다른 일인 건 맞다. 그런데 그걸 **모듈**로 가르면 무엇을 얻나?

- 빌드 파일이 하나 더 생긴다
- `settings.gradle.kts` 가 길어진다
- 이름을 하나 더 외워야 한다
- 클래스 한두 개짜리 모듈이 생긴다

얻는 것은 **의존 방향 강제**뿐이다(「재생은 진단을 몰라야 한다」 같은 것).
그건 값이 있지만, 모듈 다섯 개보다 **검사 한 개**가 싸다. ⬜ 나중에 붙인다 (TODOS).

## §3 🔄 `recorder-simple` — 여기서 한 판단은 같은 날 §6-2 에서 뒤집혔다

> ⚠️ **이 절은 기록으로 남긴다. 결론은 §6-2 가 이긴다.**
> 지우지 않는 이유: 무엇을 근거로 그렇게 생각했는지가 남아야 같은 길을 다시 안 걷는다.

접으려다 이렇게 생각했다. *"`recorder-simple` 을 `core` 에 합치면 안 된다."*

```
recorder-simple 는 demo-app «안»에서 돈다
  → demo-app 이 그걸 의존한다
  → 그게 core 안에 있으면 demo-app 이 core 를 의존한다
  → 🔴 Spring AI 와 picocli 가 관측 대상 앱으로 딸려 들어간다
```

🔴 **여기서 멈춘 것이 실수였다.** 한 걸음 더 갔으면 알았을 것이다 —
**기록을 저장하려면 어차피 `core` 의 코덱이 필요하다.** 모듈을 나눠도 demo-app 은 `core` 를
의존하게 되고, 딸려 오는 것은 똑같다. **막으려던 것을 못 막는다.**

🧭 그래도 §1 의 기준(「누구의 클래스패스」)이 옳다는 것 자체는 이 과정이 보여줬다.
「개념」으로 물었으면 이 질문이 아예 안 나왔다. 다만 **기준을 세우는 것과 그 기준을
끝까지 적용하는 것은 다른 일**이고, 여기서는 중간에 멈췄다.

## §4 🔴 `hindsight-guard` 는 막는 척한 것이었다

원래 이유: *"패치 경로 검사를 자기 모듈에 두면, 우회하려면 눈에 띄게 이상한 것을 import 해야 한다."*

**틀렸다.** 모듈 경계는 파일 쓰기를 **못 막는다.** 같은 프로젝트 안의 다른 코드가
`java.nio.file.Files` 를 직접 부르면 그만이다. 그건 우리 모듈을 우회한 게 아니라
**애초에 우리 모듈을 안 쓴 것**이고, Gradle 은 그걸 모른다.

즉 모듈 경계는 **보안 장치가 아니라 그림**이었다. 진짜로 막으려면 둘 중 하나다.

- ⬜ **검사로 막는다** — 「`brain` 패키지가 `java.nio` 를 직접 부르면 실패」. 아직 없다 (TODOS)
- ✅ **채점으로 막는다** — 이미 있다. 패치가 건드린 경로를 `git apply` **전에** 확인하고,
  재생 테스트는 매번 기록에서 새로 만든다 (설계 §7-1)

⚠️ **그림을 장치로 착각한 것이 이 실수의 본질이다.**
`guard` 는 `io.hindsight.core.guard` 패키지로 남는다. 하는 일은 그대로다.

## §6 🔄 6개도 다시 세어 봤다 (같은 날, 추가 질문을 받고)

*"나머지는 꼭 나눠야 하는 것들인거야?"* 를 묻길래 하나씩 **「안 나누면 무슨 일이 나나」**로
다시 따졌다. 답이 갈렸다.

| 모듈 | 안 나누면 | 판정 |
| --- | --- | --- |
| `hindsight-agent` | manifest 에 `Premain-Class` 가 있는 별도 jar 여야 하고 셰이딩이 필요하다 | ✅ **물리** |
| `hindsight-agent-boot` | 다른 클래스로더에 올라간다. 같은 jar 면 `NoClassDefFoundError` 로 **JVM 이 안 뜬다** | ✅ **물리** |
| `hindsight-model` | **v0 에는 아무 일도 안 난다.** v1 부터 물리 | 🟡 **규율** |
| *v0 기록기* | 아무 일도 안 난다 | 🟠 **성급한 판단이었다 → 미정으로 되돌림** |

🔴 **진짜 강제는 둘뿐이고 그 둘 다 v1 이다.**

### §6-1 `model` 은 규율이지만 이미 값을 했다

v0 만 보면 `model` 을 `core` 에 합쳐도 된다. 「의존성 0」이 물리가 되는 건 v1 부터다.

그런데 합쳤으면 어떻게 됐을지가 **이미 관측됐다.** `Integrity.isIncomplete()` 가 JSON 필드로
새서 왕복이 깨졌을 때, 합쳐져 있었으면 `@JsonIgnore` 한 줄 붙이고 넘어갔을 것이다.
그리고 v1 에 가서 **레코드 여덟 개에서 애너테이션을 걷어내는 작업**을 해야 했다.

🧭 **나중에 붙이기 어려운 제약은 처음부터 붙인다.** 「의존성 0」이 그런 종류다.
반대로 「재생과 진단을 나눈다」는 나중에 붙여도 되는 종류라서 패키지로 족했다.

### §6-2 🔴 `recorder-simple` 은 이유가 스스로 무너진다

§3 에 「demo-app 안으로 들어가니 따로여야 한다」고 적었다. **그 논리가 성립을 안 한다.**

기록을 저장하려면 `core` 의 코덱이 필요하다. 그럼 demo-app 이 `core` 를 의존하게 되고,
**결국 Spring AI 와 picocli 가 demo-app 으로 딸려 들어간다.** 모듈을 나눠도 못 막는다.

남는 이유는 「demo-app 이 포트폴리오 산출물이니 디버깅 배관이 안 섞이는 게 낫다」뿐이고,
이건 취향이다.

⬜ **그래서 지금 정하지 않는다.** 아직 코드가 없다. 만들 때 정한다.
🔴 13개가 됐던 것도 코드 없이 미리 정해서였다 — 같은 실수를 반복하지 않는다.

⚠️ **v1 에 가면 이 물음 자체가 사라진다.** 진짜 에이전트는 `core` 를 안 쓰고 JSON 을
직접 쓰므로 의존성이 0 이고, `recorder-simple` 은 그때 지워진다.

### §6-3 그리고 지금 실제로 있는 모듈은 **2개**다

「6개」는 계획이지 상태가 아니다. 디스크에 있는 것은 `hindsight-model` 과 `hindsight-core` 뿐이다.
나머지 넷은 문서 안의 지도이고, **첫 파일을 쓸 때 그때 생긴다.**

## §7 무엇이 이 결정을 뒤집게 만드나

- **화면이 필요해지면** `hindsight-server` 를 진짜로 가른다. Spring Boot 플러그인은
  모듈 단위라 그때는 선택의 여지가 없다. **미리 만들지는 않는다**
- `hindsight-core` 가 너무 커져서 한 사람이 훑기 어려워지면 다시 본다.
  🔴 다만 그때도 기준은 「개념이 다르다」가 아니라 **「올라가는 자리가 다르다」**여야 한다
- 여러 사람이 나눠 맡게 되면 모듈 경계가 소유권 경계로 값을 한다. 지금은 1인이라 해당 없다
