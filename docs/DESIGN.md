## §0 이 문서에 나오는 말

| 말 | 뜻 |
| --- | --- |
| 에이전트(agent) | 관측 대상 앱과 **같은 JVM 안에서** 도는 우리 코드. `-javaagent` 로 붙는다 |
| 계측(instrumentation) | 원본 소스를 안 고치고 실행 시점에 코드를 끼워 넣는 것 |
| 링 버퍼(ring buffer) | 정해진 크기만큼만 들고 있다가 오래된 것부터 덮어쓰는 저장 공간 |
| 경계(boundary) | 프로세스 밖과 값이 오가는 자리. HTTP 요청·응답, DB 질의, 시각, 난수 |
| 기록(recording) | 사고 순간 앞뒤의 경계 값을 한 덩어리로 묶어 저장한 파일 |
| 재생(replay) | 저장한 기록을 다시 흘려 넣어 그때 일을 한 번 더 일으키는 것 |
| **오라클(oracle)** | **테스트가 「맞았다/틀렸다」를 판정하는 기준.** 입력만으로는 테스트가 안 된다 |
| 특성화 테스트 | 「원래 이랬다」를 굳히는 테스트. 「이래야 한다」를 정하는 명세 테스트와 다르다 |
| 과적합(overfitting) | 채점만 통과하고 실제로는 안 고쳐진 패치가 만들어지는 현상 |
| 방아쇠(trigger) | 링 버퍼를 파일로 떨구게 만드는 조건 |
| JFR | Java Flight Recorder. JVM이 기본 제공하는 실행 기록기(GC·락·스레드 지표) |
| 가명화 | 원본 값을 가짜로 바꾸되 같은 원본은 늘 같은 가짜가 되게 하는 것 |
| 셰이딩(shading) | 의존 라이브러리를 내 패키지 이름 안으로 옮겨 남의 것과 안 부딪히게 하는 것 |

## §1 한 장 요약

```
[상시]   최근 몇 초~몇 십 초의 경계 값을 링 버퍼에 덮어쓰며 들고 있다
           │
           ▼ 방아쇠(예외 · 지연)
① 포획    그 창을 파일 하나로 떨군다              → recordings/<id>.json
           │
           ▼
② 재현    기록을 다시 흘려 넣어 실패를 재현한다   → 실패하는 JUnit 테스트
           │                                          (무엇을 검사하는지는 §6-1)
           ▼
③ 진단    LLM이 원인과 패치 초안을 낸다
           │
           ▼
④ 채점    ㉠ 패치 전에 정말 실패했나  ㉡ 패치 후 통과하나
           ㉢ 앱의 기존 테스트가 다 통과하나  ㉣ 되돌리면 다시 실패하나
           │  하나라도 아니면 → ③으로 (최대 3회)
           ▼ 넷 다 예
⑤ 제출    브랜치·커밋·PR. 배포 버튼은 사람이 누른다
           │
           ▼
⑥ 보관    그 기록은 회귀 테스트 후보로 남는다
```

### 🔴 §1-1 채점기가 증명하는 것과 증명하지 않는 것

이 프로젝트의 핵심 주장은 「재생이 가능하면 채점이 가능하다」다. **그 주장을 정확한 크기로 적어 둔다.**

> **채점기는 명백히 틀린 패치를 걸러낸다. 맞는 패치임을 증명하지는 않는다.**

자동 프로그램 수정(automated program repair) 분야에서 **테스트 통과를 정답의 근거로 삼는 방식은
이미 실패로 판명됐다.** 측정된 과적합률 — 채점은 통과했지만 실제로는 안 고쳐진 비율 — 이
연구에 따라 73~98%다. 그 분야가 「테스트 통과」를 정답 신호로 쓰기를 포기한 이유다.

🔴 **그래서 이 설계는 채점을 「증명」이 아니라 「거름망」으로 다룬다.** §7-2가 그 거름망을
겹으로 쌓는 자리이고, §8이 마지막에 반드시 사람을 세우는 이유다.
이 문단을 지우거나 약하게 만들지 않는다 — 없애는 순간 이 도구는 그럴듯한 오답 생성기가 된다.

## §2 만드는 순서 — 🔴 왜 바이트코드를 먼저 하지 않나

**이 절이 이 설계에서 가장 중요한 결정이다.**

처음 설계는 v0에서 `-javaagent` 와 ByteBuddy(바이트코드를 실행 중에 고치는 라이브러리)부터
만들려 했다. 리뷰가 지적한 문제는 이렇다.

> **가장 위험하고 가장 오래 걸리는 부분을 맨 앞에 두고, 이 프로젝트의 존재 이유인
> 「고리」를 맨 뒤에 뒀다.** 일정이 밀리면 잘려나가는 것은 항상 뒤쪽이다.
> 즉 **잘릴 가능성이 가장 큰 것이 하필 핵심**이었다.

그래서 뒤집는다.

| | 처음 순서 | 🔄 바꾼 순서 |
| --- | --- | --- |
| 먼저 | 에이전트(바이트코드·셰이딩·클래스로더) | **고리 전체** — 기록·재생·오라클·진단·채점·PR |
| 나중 | 고리 | **기록기를 진짜 에이전트로 갈아끼운다** |

**핵심은 v0에서 바이트코드를 아예 안 쓴다는 것이다.** 기록은 이렇게 한다.

```
v0 의 기록 방법 (바이트코드 없음)
  들어온 요청  →  jakarta.servlet.Filter 를 하나 등록한다        ← 그냥 스프링 빈이다
  DB 질의     →  DataSource 를 감싸는 클래스를 하나 만든다      ← 그냥 데코레이터다
```

이건 **200줄쯤이고 오늘 당장 된다.** 클래스로더도, 셰이딩도, `premain` 도 없다.
대신 **2주 뒤에 데모 영상이 나온다** — 버그 발생 → 기록 → 실패 테스트 → 패치 → 통과 → PR.

그다음 v1에서 기록기를 진짜 에이전트로 갈아끼운다. 이때 **이미 도는 시스템이 회귀 검사 역할을 한다** —
같은 상황에서 v0 기록기와 v1 에이전트가 같은 기록을 만드는지 비교하면 된다.

🔴 **기록기를 두 번 만드는 값은 나흘쯤이다. 얻는 것은 「위험보다 데모가 먼저 온다」는 것이다.**

## §3 모듈

> 🔴 **모듈은 「누구의 클래스패스에 올라가나」로만 나눈다.**
> 읽기·재생·진단·명령줄 같은 구분은 전부 **패키지**다.
>
> 🔄 **2026-09-10: 13개에서 6개로 접었다.** 「개념이 다르니 모듈도 다르게」로 나눴더니
> 클래스 한두 개짜리 모듈이 다섯 개 생겼다. 특히 `hindsight-guard` 를 「파일을 쓰는 유일한
> 통로」라며 모듈로 뺐는데, **모듈 경계는 파일 쓰기를 못 막는다** — 막는 척한 것이었다.
> 🧭 [`rules/module-boundary-decision.md`](rules/module-boundary-decision.md)

### 관측 대상 앱 «안»에서 도는 것 — 의존성을 함부로 못 늘린다

| 모듈 | 자바 | 의존성 | 하는 일 | 강제인가 |
| --- | --- | --- | --- | --- |
| `hindsight-model` | **17** | **없음** | 기록 파일의 자료 구조(record)만. 🔴 안팎이 공유한다 | 🟡 v1 부터 물리. v0 에는 **규율** |
| *v0 기록기* | 21 | model, core | `Filter` + `DataSource` 감싸기 | ⬜ **모듈일지 demo-app 안의 패키지일지 미정** |
| `hindsight-agent-boot` | **17** | **없음** | 🔴 부트스트랩에 올라가는 얇은 껍데기 (§3-2) | ✅ **물리** — 다른 클래스로더 |
| `hindsight-agent` | **17** | model + ByteBuddy(셰이딩) | 계측·링 버퍼·방아쇠·덤프 | ✅ **물리** — 별도 jar·셰이딩 |

🔴 **진짜로 강제되는 것은 아래 둘뿐이고, 둘 다 v1 이다.**

- `hindsight-model` 은 v0 만 보면 `core` 에 합쳐도 아무 일도 안 난다. 그래도 따로 두는 이유:
  「의존성 0」은 **나중에 붙이기 어려운 제약**이라서다. 합쳐 뒀으면 `@JsonIgnore` 를 붙이며
  살다가 v1 에 레코드 여덟 개에서 걷어내야 했을 것이다 — 실제로 그럴 뻔했다
  ([`rules/module-boundary-decision.md`](rules/module-boundary-decision.md) §6-1)
- ⬜ **v0 기록기는 지금 정하지 않는다.** 아직 코드가 없다. 만들 때 정한다 (같은 문서 §6-2)

### 관측 대상 앱 «밖»에서 도는 것

| 모듈 | 자바 | 의존성 | 하는 일 | 단계 |
| --- | --- | --- | --- | --- |
| `hindsight-core` | 21 | model, Jackson, JUnit 5, Spring AI, picocli | **읽기·재생·오라클·진단·채점·명령어 전부** | v0 |
| `demo-app` | 21 | Spring Boot | 🔴 **진짜 서비스다. 소품이 아니다** (§3-4) | v0 |

`hindsight-core` 안의 패키지: `store`(읽기·쓰기) · `privacy`(가명화) · `replay`(재생·오라클) ·
`guard`(패치 경로 검사) · `brain`(진단·채점) · `cli`(명령어) · `mcp`(v3).
기록 표본은 `hindsight-model` 의 테스트 픽스처에 있다 — 🔴 별도 소스 세트라 본체 jar 에 안 들어간다.

⬜ **v3 에 화면이 필요해지면 `hindsight-server` 를 가른다.** Spring Boot 플러그인이 모듈
단위라서 그때는 선택의 여지가 없다. **미리 만들지 않는다.**

⬜ **패키지 의존 방향은 아직 검사가 없다.** 「`replay` 가 `brain` 을 몰라야 한다」는
지금 사람이 지킨다. 모듈 다섯 개보다 검사 한 개가 싸다 (TODOS).

### §3-1 🔴 에이전트에 Spring을 쓰면 안 되는 이유

에이전트는 관측 대상 앱과 **같은 JVM, 같은 클래스패스**에서 돈다. 에이전트가 끌고 들어간
라이브러리가 그대로 남의 앱에 섞인다.

> 상대 앱이 Jackson 2.15를 쓰는데 에이전트가 2.17을 끌고 들어가면 **상대방 앱이 죽는다.**

- `hindsight-agent`·`hindsight-agent-boot`·`hindsight-model` 의 **외부 의존성은 ByteBuddy 하나뿐**이고
  그것도 셰이딩한다. 🔴 「의존성 0」이라고 쓰지 않는다 — 표에 ByteBuddy가 있는데 0이라고 하면
  그건 그냥 틀린 말이다. **「셰이딩된 것 딱 하나」**가 정확한 표현이다
- 🔴 `hindsight-model` 에 **Jackson 애너테이션을 절대 안 붙인다.** 붙이는 순간
  `jackson-annotations` 가 model의 의존성이 되고, 에이전트가 model을 쓰니 **Jackson이
  남의 JVM에 들어간다.** 매핑 설정은 전부 `hindsight-core` 쪽 믹스인(mixin)에 둔다
- 이 금지선은 **빌드가 직접 지킨다** — `build.gradle.kts` 의 `checkAgentDependencies` 가
  허용 목록 밖의 의존성을 발견하면 빌드를 실패시킨다. 문서에만 적어두면 언젠가 누가 한 줄 추가한다

### §3-2 🔴 클래스로더 — v1에서 일주일을 쓸 자리

셰이딩은 **이름 충돌**만 푼다. 진짜 어려운 건 이 셋이고, 처음 설계에는 아예 없었다.

1. **`-javaagent` 는 시스템 클래스로더에 올라간다.** 그래서 우리 클래스가 전부 앱에 보인다.
   Datadog·New Relic은 셰이딩만 하는 게 아니라 **격리된 자체 클래스로더**에 본체를 올리고
   시스템 경로에는 얇은 껍데기만 남긴다. 우리도 그렇게 한다
2. 🔴 **`java.time.Instant` 같은 JDK 핵심 클래스에 끼워 넣은 코드는 부트스트랩 클래스로더에서
   돈다.** 그 코드가 시스템 클래스로더에 있는 우리 클래스를 못 찾으면 `NoClassDefFoundError` 가
   나고 — **JVM이 아예 안 뜬다.** 관측 도구가 앱을 죽이는 가장 확실한 방법이다.
   그래서 `hindsight-agent-boot`(정적 디스패치 홀더만, 100줄 남짓)을 `premain` 에서
   부트스트랩에 먼저 올린다
3. **`java.sql.PreparedStatement` 는 인터페이스다.** 구현체는 드라이버 쪽에 있고,
   `hasSuperType` 으로 잡으면 **모든 클래스 로딩마다 상속 계층을 뒤진다** — 시작 시간 예산이
   여기서 날아간다. 게다가 HikariCP의 `HikariProxyPreparedStatement` 와 드라이버의 구현체가
   **둘 다 잡혀 질의가 두 번 기록된다.** 🔴 v0의 성공 기준이 「SQL 201건」인데 402건이 나오면
   이틀을 태운다. 한 층에서만 잡고 나머지는 위임(delegate) 여부로 걸러낸다

### §3-3 🔴 우리가 죽을 때 남을 죽이지 않는다

의존성 충돌은 에이전트가 앱을 죽이는 **덜 흔한** 방법이다. 흔한 쪽은 이것들이고, 전부 막는다.

- 🔴 **계측 코드의 모든 진입점을 `try { … } catch (Throwable t)` 로 감싼다.** 절대 밖으로
  안 던진다. 실패하면 세기만 하고 조용히 죽는다
- 🔴 **자기 무력화(kill switch).** 내부 실패가 N회(기본 50) 쌓이면 계측을 스스로 끄고 한 번만
  로그를 남긴다. **성능이 나빠지는 것보다 관측을 포기하는 게 낫다**
- 🔴 **앱이 가진 객체를 붙들고 있지 않는다.** `HttpServletRequest`·`ResultSet`·엔티티를
  60초 들고 있으면 남의 힙을 잡아 **OOM을 낸다.** 잡는 순간 스칼라 값으로 복사하고 참조는 버린다
- 🔴 **큐는 반드시 유계(bounded)다.** `ConcurrentLinkedQueue` 를 쓰지 않는다 — 무한 큐는
  트래픽이 튀는 순간 남의 앱에서 OOM이 된다. 차면 **버리고 센다**
- 🔴 **덤프는 요청 스레드에서도, 보관 스레드에서도 안 돈다.** 별도 I/O 스레드가 한다.
  100ms 걸리는 덤프가 보관 스레드를 막으면 **하필 사고 순간에 이벤트를 버린다**
- **끄는 스위치를 문서에 적는다** — `-Dhindsight.disabled=true`. 운영자가 우리 없이도
  앱을 돌릴 수 있어야 한다

### §3-4 🔴 `demo-app` 은 소품이 아니라 진짜 서비스로 만든다

처음 설계에서 `demo-app` 은 버그를 심을 대상일 뿐이었다. 그러면 이 프로젝트를 다 끝내도
**스프링 코드를 거의 안 쓴 상태**가 된다. 자바·스프링 자리에 지원하면서.

⚠️ **평가하는 사람이 이해할 수 없는 포트폴리오는 높은 점수가 아니라 0점을 받는다.**
바이트코드 계측을 평가할 수 있는 면접관은 소수다. 그런데 스프링 서비스는 누구나 평가할 수 있다.

그래서 `demo-app` 에 일주일을 더 쓴다.

- JPA 연관관계가 있는 진짜 도메인 모델, 트랜잭션, 페이징
- Redis 캐시, Docker Compose, 테스트 스위트, CI, OpenAPI 문서
- 그 위에 버그를 심는다

이러면 포트폴리오가 **두 겹**이 된다. *"스프링 부트 서비스를 만들었고, 그걸 디버깅하는
JVM 에이전트도 만들었다."* 앞쪽은 모두가 평가할 수 있고, 뒤쪽은 아는 사람이 알아본다.

## §4 기록 — 무엇을 잡고 무엇을 안 잡나

### §4-1 잡는 것

| 종류 | v0 잡는 법 | v1 잡는 법 | 남기는 값 |
| --- | --- | --- | --- |
| 들어온 요청 | `Filter` 등록 | `DispatcherServlet#doService` | 메서드·경로·쿼리·헤더·본문·**응답 상태와 본문** |
| DB 질의 | `DataSource` 감싸기 | JDBC 계측 | SQL·파라미터·행 수·결과 행·소요시간 |
| 나간 요청 | — | HttpClient 계측 | 요청 전문 + 응답 전문 |
| 시각·난수 | — | 부트스트랩 계측 | 호출 순번과 반환값 |
| JVM 지표 | — | **JFR** (직접 안 만든다) | GC·락 대기·스레드 |

🔴 **응답 본문을 반드시 남긴다.** 상태 코드만 검사하는 테스트는 예외를 삼키는
`@ExceptionHandler` 하나로 통과시킬 수 있다 (§7-1).

🔴 **v1에서 `DispatcherServlet#doService` 를 이름으로 잡는다.** `jakarta.servlet.Filter` 는
인터페이스라서 앱의 모든 필터가 잡히고 — 스프링 시큐리티가 있으면 열다섯 개다 — **같은 요청이
열다섯 번 겹쳐 기록된다.**

### §4-2 안 잡는 것 — 그리고 그게 무슨 뜻인지

| 안 잡는 것 | 그래서 못 하는 것 |
| --- | --- |
| 🔴 **앱 안에 쌓인 상태** | **가장 중요한 항목.** 캐시 내용, 커넥션 풀 상태, 세션, 정적 변수, Hibernate 2차 캐시. 요청 하나를 재생해도 **이전 요청들이 쌓아 놓은 상태는 재현 안 된다** |
| 스레드 실행 순서 | 경쟁 상태(race condition) 버그의 완전 재현 |
| 비동기 경계 | `@Async`·`CompletableFuture`·WebFlux 로 넘어간 뒤의 이벤트는 어느 요청 것인지 모른다. `background` 로 따로 담고 **버리지 않는다** |
| 파일 입출력 | 파일을 읽어 동작이 갈리는 버그 |
| 앱 내부 메서드 호출 | 단계별 되감기 디버깅. 그건 다른 물건이다 |
| 다른 JVM의 기록 | 마이크로서비스를 가로지르는 재현 |

### 🔴 §4-3 이 목록이 「가치 있는 걸 다 뺐다」로 읽히지 않게

위 표만 보면 *"재현이 어려운 버그는 다 제외했네"* 로 읽힌다. 그 반론을 **여기서 미리 답한다.**

남는 것은 「경계로 들어온 값이 원인인, 단일 JVM의 결정론적 실패」다. 그게 왜 가치 있냐면,
**그 부류의 실패가 재현이 안 되는 이유는 어려워서가 아니라 「그때 그 입력값이 아무 데도 안 남아서」**이기 때문이다.

> 새벽 3시에 협력사 API가 이상한 응답을 한 번 보냈고, 그걸로 NPE가 났다.
> 로그에는 스택 트레이스만 있다. **그 응답을 다시 얻을 방법이 없다.**

이건 백엔드 개발자면 누구나 하루씩 날려 본 문제다. 🔴 **홍보 문구를 N+1로 잡지 않는다** —
N+1은 아는 사람이 30초에 고치는 것이라, 대표 예제로 쓰면 「쉬운 걸 비싸게 하는 도구」로 보인다.
**대표 예제는 「그때 그 응답을 다시 얻을 수 없다」로 잡는다.**

### §4-4 상관 식별자와 두 층 저장

- 🔴 요청이 동시에 여러 개 들어오면 SQL이 어느 요청 것인지 알아야 한다. 모든 이벤트가
  **`corrId`(상관 식별자)** 를 갖는다. 🔴 `Thread.getId()` 로 대신하지 않는다 —
  가상 스레드는 식별자가 재사용된다
- 「최근 60초」는 산수가 안 맞는다. 그래서 **전문 층(5초·16MB)과 요약 층(60초·16MB)** 으로 나눈다.
  🔴 담으려던 시간과 실제 담긴 시간을 **둘 다 파일에 적는다.**
  자세한 것은 데이터 계약의 「두 층으로 나누는 이유」 절(§2-1)과 「온전한가」 절(§8)

## §5 포획

**원인은 결과보다 먼저 일어난다.** 예외가 터진 순간부터 기록을 시작하면 증상만 남고 원인은 안 남는다.
그래서 비행기 블랙박스와 같은 구조를 쓴다 — 계속 덮어쓰다가 사고 때만 디스크로 떨군다.

| 방아쇠 | 조건 | 언제부터 |
| --- | --- | --- |
| 예외 | 진입점 밖으로 예외가 나감 | v0 |
| 지연 | 진입점 소요시간이 임계값 초과 | v0 |
| 손으로 | `hs capture` | v1 |
| 자원·메모리 | JFR 지표 | v2 |

### §5-1 포획 폭주를 막는 장치

⚠️ **장애는 한 번 나면 초당 수백 번 난다.** 상한이 없으면 사고 순간에 디스크를 채워 앱을 두 번 죽인다.

- **묶기**: `(진입점, 방아쇠 종류, 스택 서명)` 이 같으면 한 건으로 본다.
  🔴 예외 종류만으로 묶지 않는다 — **지연 방아쇠에는 예외 종류가 없다**
- **시간당 상한**(기본 20) · **총량 상한**(기본 1GB, 넘으면 오래된 것부터)
- 🔴 **모든 상한은 설정값이고 한 모듈에서만 읽는다.** 호출하는 쪽마다 기억하게 만들면
  언젠가 한 곳이 잊는다. 값과 기본값은 데이터 계약의 「상한값」 절(§9)

### §5-2 `hs capture` 는 동적 부착이 아니다

JDK 21 이후 **실행 중인 JVM에 에이전트를 나중에 붙이는 것은 경고 대상**이고 방향은 금지 쪽이다.
`-javaagent` 로 처음부터 붙는 건 영향 없다. 손으로 포획하려면 **에이전트가 `premain` 에서
열어둔 파일이나 소켓**을 쓴다.

## §6 재생과 오라클

### 🔴 §6-1 오라클 — 테스트가 무엇을 검사하는가

**처음 설계에 이 절이 통째로 없었다.** 그리고 그게 이 설계의 가장 큰 구멍이었다.

테스트는 **입력**과 **오라클**로 이루어진다. 입력을 아무리 잘 재생해도 **「맞았다」를 무엇으로
판정할지**가 없으면 테스트가 아니다. 방아쇠 종류별로 정한다.

| 방아쇠 | 🔴 오라클 | 왜 |
| --- | --- | --- |
| 예외 | 그 **예외 타입**이 진입점 밖으로 안 나감 **＋ 응답 상태와 본문이 기록과 같음** | 🔴 「안 던진다」만으로는 안 된다. `catch (Exception e) { return null; }` 로 통과된다 |
| **지연·N+1** | 🔄 **같은 모양의 질의가 N번 이상 반복되면 실패** (총 횟수가 아니라 **모양별 반복**) | 🔴 **시간으로 재면 안 된다.** 재생에서는 DB가 가짜라 180ms가 0ms가 된다. **지연 버그는 시간이 아니라 횟수로 잡는다** |
| 값이 틀림 | 응답 본문이 기록과 같음 | — |

🔴 **N+1이 이 절을 만들게 한 이유**: N+1은 **예외를 안 던진다.** 지연으로만 잡히는데 재생에서
시간이 사라진다. 그래서 실행 «횟수»를 오라클로 삼는다. 시간과 달리 **완전히 결정론적**이다.

🔄 **2026-09-11 실측으로 다듬었다.** 처음에는 「SQL 실행 수 ≤ K」로 적었는데,
실제로 재 보니 **모양별로 묶은 그림이 훨씬 강한 신호**였다.

```
주문 20건 조회 → SQL 21번
     1 번  select ... from orders        ← 목록
    20 번  select ... from member where id=?   ← 🔴 이 한 줄이 N+1 의 서명이다
```

**「총 21번」보다 「한 모양이 20번」이 낫다.** 총 횟수는 데이터가 늘면 같이 늘어서 문턱이
자의적이 되는데, **「같은 질의가 여러 번」은 데이터 양과 무관하게 결함**이기 때문이다.
🧭 실측: [`reports/2026-09-11/sql-count-experiment.md`](reports/2026-09-11/sql-count-experiment.md)

⚠️ **이 테스트는 특성화 테스트다.** 「원래 이랬다」를 굳히는 것이지 「이래야 한다」를 정하는 게 아니다.
사양이 바뀌면 이 테스트는 **틀린 게 아니라 낡은 것**이다. 그 구분을 문서와 화면에 적는다.

### 🔴 §6-2 `DIVERGED` — 제대로 고치면 기록이 무효가 된다

**이 도구가 겨누는 대표 버그가 이 문제를 일으킨다.**

N+1을 고치는 정석은 질의 201개를 **조인 하나**로 바꾸는 것이다. 그런데 **그 새 질의는 기록에 없다.**
가짜 DB가 돌려줄 값이 없다. `WHERE` 절 추가, 컬럼 하나 더 읽기, 캐시 추가, 배치 처리도 전부 같다.

🔴 **즉 「제대로 된 수정」일수록 재생이 깨진다.** 이걸 실패로 처리하면 채점기는
**예외를 삼키는 얕은 패치를 구조적인 수정보다 높게 친다.** 정확히 거꾸로다.

그래서 **실패도 통과도 아닌 세 번째 결과**를 만든다.

```
재생 중 기록에 없는 경계를 만남
   └→ 기록의 SQL 지문(요약 층)과 정규화한 모양으로 대조
        ├ 가까운 것 있음 → DIVERGED + 「무엇이 무엇으로 바뀌었나」를 붙여 사람에게
        └ 없음           → DIVERGED + 「모르는 질의」로 사람에게
```

🔴 **통과로 치지 않는다. 고장으로도 치지 않는다.** 오히려 이게 **가장 좋은 PR 설명**이 된다:
*"패치가 질의 201개를 1개로 바꿨다. 재생으로는 채점할 수 없으니 근거를 붙여 사람에게 넘긴다."*

### §6-3 등급은 주장이 아니라 실측이다

처음 설계는 「어떤 계측이 걸렸나」로 등급을 미리 매겼다. 그런데 캐시가 따뜻했는지, 정적 변수에
뭐가 쌓였는지는 계측 목록으로 알 수 없다. **`DETERMINISTIC` 이라고 적힌 기록이 실제로는 갈라질 수 있다.**

🔴 그래서 **재생 중에도 같은 계측을 켜고, 재생이 만든 경계 호출을 기록과 대조한다.**

- 전부 맞고 순서도 같음 → `VERIFIED_DETERMINISTIC` — **관찰이지 약속이 아니다**
- 안 맞는 호출이 있음 → `DIVERGED` + 갈라진 호출 목록

이 한 번의 변경이 §6-2의 정책과 §6-3의 등급을 **같은 장치 하나로** 해결한다.
🔴 이게 이 프로젝트에서 기술적으로 가장 흥미로운 부분이고, 포트폴리오에서 앞세울 것도 이것이다.

### 🔴 §6-4 재생은 «되돌린 자리»에서 돈다 — 복원은 재생의 일부다

**재생은 요청을 다시 보내는 게 아니다. 기록 시점 상태로 되돌린 뒤 다시 보내는 것이다.**

한때 이 절이 없었고, 그래서 「쓰기 요청은 재생해도 같은 답이 안 나오니 채점할 수 없다」는
결론까지 갔다. 되돌린 범위만 바꿔서 세 번 재 보니 그게 아니었다.

```
되돌린 범위          재생 결과
없음                 응답이 다르다              id 3 → 4
행만                 🔴 재생이 예외로 죽는다     "없는 회원: 1"
행 + 자동 증가 카운터  ✅ 글자까지 같다
```

🧭 실측: [`reports/2026-09-11/write-replay-experiment.md`](reports/2026-09-11/write-replay-experiment.md)
· 결정: [`rules/replay-state-decision.md`](rules/replay-state-decision.md)

🔴 **축은 「읽기냐 쓰기냐」가 아니라 「되돌렸나」다.** 되돌리지 않으면 읽기 요청도 갈라진다 —
그 사이 다른 요청이 DB 를 바꿨으면 목록 조회의 응답도 달라진다.

#### 🔴 행을 되돌리는 것은 상태를 되돌리는 것이 아니다

위 표의 가운데 줄이 이 절에서 가장 중요하다. 행을 **같은 내용·같은 개수로** 복원했는데도
재생이 죽었다. 행에 붙은 `id` 가 1·2·3 이 아니라 2·4·5 였기 때문이다 — 행을 지워도
DB 가 들고 있는 「다음 `id` 는 몇 번」이라는 숫자는 안 돌아간다. **그것도 상태다.**

🔴 **부분 복원은 무복원보다 위험하다.** 무복원은 답이 다르게 나오고(눈에 띈다),
부분 복원은 재생이 죽는다 — 그리고 채점기는 그 죽음을 **「패치가 못 고쳤다」로 읽는다.**
패치는 아무 잘못이 없는데 우리 쪽 복원 부족으로 LLM 이 벌을 받는다.

#### 그래서 복원을 «했는지»를 기록에 적는다

복원할 수 없는 자리가 반드시 생긴다(운영 DB, 캐시, 외부 시스템). 그때 **모른 채로 통과시키지
않는다.** 어디까지 되돌렸는지를 기록에 적고, 못 되돌렸으면 등급은 `PARTIAL` 이고
`missing` 에 `"STATE"` 가 들어간다. 필드 모양: [`DATA_CONTRACT.md`](DATA_CONTRACT.md) §7-3.

⬜ **아직 안 정한 것**: 운영 규모 DB 를 기록 시점으로 어떻게 되돌리나.
실험은 H2 메모리라 한 줄이면 됐다. 진짜 서비스는 그렇지 않다.

## §7 고리 — 과적합을 어떻게 막나

### §7-1 🔴 채점표를 고치지 못하게 막는다

LLM에게 *"테스트를 통과시켜라"* 라고 하면 **테스트를 지워서 통과시킨다.**

- 패치가 건드릴 수 있는 경로는 **화이트리스트**: 기본 `src/main/java/**`
- 🔴 **절대 금지**: `src/test/**`, 기록 파일, `.git/**`, `.github/**`(CI를 고쳐 통과시킬 수 있다),
  `gradle/**`·`*.gradle*`(빌드를 고칠 수 있다), **Hindsight 자신의 모듈**(자기 채점기를 약화시킬 수 있다)
- ⚠️ `src/main/resources/**` 는 **자동 통과 대상이 아니다.** `application.yml` 하나로 검증을 끄거나
  기능 플래그를 뒤집을 수 있다. 여기를 건드린 패치는 **중간 확신도**로 내려 사람에게 보낸다
- 검사는 `git apply` **전에** 한다. 경로를 실제 경로로 펴서(`..`·심볼릭 링크 거부) 확인한다
- 이 검사는 `io.hindsight.core.guard` 패키지에 모아 두고, **패치를 파일로 쓰는 코드는 여기뿐이다**
  - 🔄 **한때 이걸 «모듈»로 뺐다가 접었다** (2026-09-10). 「자기 모듈이면 우회하기 어렵다」는
    이유였는데 **틀렸다** — 모듈 경계는 파일 쓰기를 못 막는다. 같은 프로젝트의 다른 코드가
    `java.nio.file.Files` 를 직접 부르면 그만이고 Gradle 은 그걸 모른다.
    🔴 **그건 장치가 아니라 그림이었다.**
  - ⬜ **진짜로 막으려면 검사가 필요하다** — 「`brain` 이 `java.nio` 를 직접 부르면 실패」.
    아직 없다 (TODOS). 지금 실제로 막는 것은 아래 두 줄(적용 전 경로 확인 · 테스트 재생성)이다
- 재생 테스트는 매번 **기록에서 새로 만들어** 돌린다. 디스크에 있는 것을 믿지 않는다

### §7-2 🔴 과적합을 막는 네 겹

화이트리스트는 **채점표를 지킬 뿐 채점을 옳게 만들지 않는다.** §1-1의 73~98%를 줄이는 건 이 넷이다.

| 겹 | 무엇을 확인하나 | 무엇을 막나 |
| --- | --- | --- |
| ㉠ **기준선 실패** | 생성된 테스트가 **패치 전 코드에서 정말 실패**하는가 | 애초에 버그를 못 살린 테스트로 「고쳤다」고 선언하는 것 |
| ㉡ 검증 통과 | 패치 후 통과하는가 | — |
| ㉢ 🔴 **앱의 기존 테스트 전체** | 프로젝트가 원래 갖고 있던 테스트가 다 통과하는가 | 하나 고치고 마흔 개 깨뜨리는 패치. **고리 안에서 돌린다** |
| ㉣ **되돌리기 검사** | 패치를 되돌리면 다시 실패하는가 | 패치와 무관하게 통과하던 헛된 테스트 |

🔴 **㉢을 고리 밖(PR 이후 CI)에 두면 안 된다.** 처음 설계가 그랬는데, 그러면 **프로젝트의 진짜
테스트를 한 번도 안 돌린 패치로 PR을 자동 생성**하게 된다.

⚠️ 그리고 새 `@ExceptionHandler`·넓은 `catch`·재시도·타임아웃 늘리기가 패치에 들어 있으면
자동으로 **중간 확신도**로 내린다. 이것들이 「증상만 덮는」 수정의 전형이다.

### §7-3 확신도에 따라 행동을 나눈다

| 확신도 | 조건 | 행동 |
| --- | --- | --- |
| 높음 | `VERIFIED_DETERMINISTIC` + ㉠~㉣ 전부 통과 + 변경이 `src/main/java/**` 안 | PR 자동 생성 |
| 중간 | `PARTIAL` 이거나 설정 파일을 건드렸거나 증상 덮기 패턴이 보임 | 재현 테스트 + 진단만. 패치는 초안으로 첨부 |
| 중간 | **`DIVERGED`** | 「무엇이 무엇으로 바뀌었나」를 붙여 사람에게 (§6-2) |
| 낮음 | 3회 시도가 다 실패 | 기록과 테스트만 남기고 사람을 부른다 |

🔴 **「모르겠다」고 말할 줄 아는 것이 이 도구의 신뢰를 만든다.**

### §7-4 🔄 비용 — 얼마가 드는지 숫자로 적는다

⚠️ 이 절은 리뷰가 *"토큰·비용 상한이라고만 적혀 있고 숫자가 없다"* 고 지적한 자리다.
**숫자 없는 상한은 상한이 아니다.**

**한 건을 진단하는 데 드는 것** (입력 3만 토큰 · 출력 4천 토큰으로 잡을 때)

| 모델 | 1회 시도 | 버그 1건 (최대 3회) |
| --- | --- | --- |
| Haiku 4.5 | 약 $0.05 | 약 **$0.15** |
| Sonnet 5 | 약 $0.10 | 약 **$0.30** |
| Opus 5 | 약 $0.25 | 약 **$0.75** |

- 시도 **3회** (설정값). 실패하면 사람에게 넘긴다
- 기록 하나당 **$1 상한**(기본, 설정값). 넘으면 멈추고 사람을 부른다
- 🔴 **상한에 걸려 멈춘 것을 「못 고쳤다」로 적지 않는다.** 「돈이 떨어져 멈췄다」와
  「세 번 해보고 못 고쳤다」는 다른 사실이다 — 「모름」을 「없음」으로 접는 것과 같은 부류

#### 🔴 프롬프트 캐싱 — 이 구조에서 값이 특히 크다

채점 고리는 **최대 3번 재시도**하고, 그때마다 **기록과 소스를 다시 보낸다.** 같은 내용을.
프롬프트 캐싱을 쓰면 그 반복분이 **약 10분의 1 값**이 된다.

```
캐싱 없이 : 3회 × 30,000 토큰 = 90,000 토큰 전액
캐싱 있으면: 30,000 전액 + 60,000 × 0.1  →  약 40% 값
```

⚠️ **캐싱은 앞부분이 한 글자도 안 바뀔 때만 듣는다.** 그래서 프롬프트 순서를 이렇게 고정한다.

| 순서 | 무엇 | 재시도마다 바뀌나 |
| --- | --- | --- |
| ① | 지시문 | ❌ |
| ② | 기록 요약 · 관련 소스 | ❌ |
| ③ | ← **여기까지 캐시 표시** | |
| ④ | 시도 번호 · 직전 실패 이유 | ⭕ |

🔴 **시각·시도 횟수를 앞쪽에 넣으면 캐시가 매번 깨진다.** 값이 통째로 사라지는데
깨진 것을 알아채기도 어렵다 — 응답의 `cache_read_input_tokens` 가 0 인지 **검사로 확인한다.**

#### MCP 는 돈이 안 든다 (v3)

MCP 는 공개 규격이고 `hindsight-mcp` 는 우리 컴퓨터에서 도는 우리 프로세스다.
켜두는 데 드는 돈이 없고 호스팅도 필요 없다. ⚠️ 다만 **도구 설명이 에이전트의 문맥을 먹는다** —
설명을 짧게 쓰고 도구 개수를 늘리지 않는다.

### §7-5 검증은 우리 비밀값을 들고 도는 코드를 실행한다

패치된 코드가 우리 컴퓨터에서 돈다. `.env` 에 가명화 키와 GitHub 토큰이 있다.
`System.getenv()` 한 줄이면 둘 다 나간다.

- 검증은 **환경변수를 씻어낸 별도 프로세스**에서 돌린다 (`HINDSIGHT_*`·`GITHUB_TOKEN` 제외)
- 개인 프로젝트라 격리 상자(sandbox)까지는 안 만든다. **대신 이 신뢰 경계를 문서에 적는다**

## §8 제출 — 배포는 하지 않는다

검증 통과 → 브랜치 → 커밋 → PR(근거 첨부) → 기존 CI → **사람이 머지** → 기존 파이프라인이 배포.

🔴 **이 도구는 운영 배포를 하지 않는다.** ㉠ 재생 검증은 「이 상황이 고쳐졌다」만 증명한다.
㉡ 재생은 경계 안쪽만 본다. ㉢ 되돌리기 비용이 비대칭이다 — 아홉 번 맞혀도 한 번 사고 나면 아무도 안 쓴다.

PR 본문: 포획된 상황 · 생성된 테스트와 **그 오라클** · ㉠~㉣ 결과 · 재생 등급 · 시도 횟수 ·
`DIVERGED` 면 무엇이 어떻게 바뀌었는지.

## §9 개인정보

**그냥 가리면 재생이 깨진다.** 사용자 번호를 `***` 로 바꾸면 그 번호로 조회하던 코드가 안 돈다.
그래서 `HMAC-SHA256(비밀키, 원본)` 으로 **같은 원본은 늘 같은 가명**이 되게 한다.

```
hong@abc.com   →  user_7f3a1c@example.invalid    ← 언제나 같은 값
010-1234-5678  →  010-0000-4821                   ← 형태는 지키고 값만 바꾼다
```

### §9-1 🔴 가명정보는 익명정보가 아니다

⚠️ **이 절을 「법적으로 안전해졌다」로 읽으면 안 된다.**

- 개인정보보호법에서 가명처리한 값은 여전히 **가명정보**이고 **개인정보다.** 처리 근거가 필요하다
- 미국에 있는 LLM 제공자에게 보내는 것은 **국외이전**이다
- HMAC은 **값의 범위가 좁으면 대조로 되돌릴 수 있다.** 전화번호·한국 이름·작은 사용자 번호 공간이
  그렇다. 키가 기록과 같은 컴퓨터의 `.env` 에 있으면 더욱
- 🔴 **그래서**: 가명화는 법적 면책이 아니라 **겹으로 쌓는 방어의 한 겹**이다.
  **데모와 공개 기록은 전부 합성 데이터만 쓴다.** LLM으로 보낼 때는 지정한 필드만 보내는
  **허용 목록 방식**도 함께 둔다 — 모르는 JSON에 대한 금지 목록은 언젠가 반드시 샌다

### §9-2 어디서 가명화하나

🔴 **가명화는 에이전트 안, 파일로 쓰기 직전, 한 곳에서만 한다.** 바깥에서 하면 **원본이 먼저
디스크에 닿는다.** 비밀키는 `-Dhindsight.key.file=` 로 경로만 넘기고, `premain` 에서 한 번 읽고,
로그에도 덤프에도 절대 안 남긴다.

⚠️ 본문은 에이전트 입장에서 **그냥 바이트 뭉치**라 「필드 경로」가 없다. v0에서는 JSON일 때만
필드를 보고, 아니면 **본문을 통째로 버리는 쪽**을 기본으로 한다.

**무조건 버리는 것**: `Authorization`·`Cookie`·`Set-Cookie`, 비밀번호·토큰 이름의 필드,
카드번호·주민등록번호 패턴.

## §10 성능

「얼마나 느려지는데?」에 답 못 하는 관측 도구는 아무도 안 붙인다.

| 항목 | 목표 | 어떻게 재나 |
| --- | --- | --- |
| 요청당 추가 시간 | **50µs 이하** (초당 200요청, demo-app 기준) | 🔴 「p99 5%」는 잴 수 없는 말이다. p99가 2ms면 5%는 100µs다. **절대값으로 적는다** |
| 경계 이벤트 하나당 | 2µs 이하 | |
| 앱 시작 시간 증가 | 300ms 이하 | |
| 상시 메모리 | 32MB 이하 | 전문 16MB + 요약 16MB |

⚠️ 참고로 이런 종류의 도구(2008년 ReCrash)가 논문에서 보고한 상시 오버헤드는 **13~64%** 다.
5%는 야심찬 목표지 기본값이 아니다. **못 지키면 못 지켰다고 적는다.**

- 링 버퍼 쓰기는 요청 스레드를 막지 않는다. 큐가 차면 **버리고 센다**
- 🔴 **측정 하네스는 v0의 과제다.** 「나중에 잰다」로 두면 안 재게 된다.
  에이전트 붙임/뗌을 비교해 `docs/reports/` 에 숫자를 남긴다

## §11 🔴 이 도구 자신을 어떻게 시험하나

바이트코드 에이전트를 어떻게 테스트하는지가 처음 설계에 없었다. 이건 **면접에서 반드시 물어보는 것**이다.

| 무엇을 | 어떻게 |
| --- | --- |
| 에이전트가 진짜 붙는가 | **별도 JVM을 띄워서**(`ProcessBuilder`) 픽스처 앱을 `-javaagent` 로 돌리고 기록 파일이 나오는지 본다 |
| 🔴 **셰이딩이 됐는가** | **완성된 jar를 열어 `net.bytebuddy` 로 시작하는 패키지가 없는지 검사한다.** 이 프로젝트에서 값이 가장 큰 테스트 한 개다 |
| 앱 클래스패스를 안 더럽히는가 | 에이전트를 붙인 앱에서 보이는 클래스 수가 안 늘었는지 |
| 기록 형식이 안 갈라지는가 | 🔴 **왕복 테스트** — 기록기가 쓴 것을 core가 읽어 다시 만들면 같아야 한다. 쓰는 쪽과 읽는 쪽이 두 벌이라 없으면 조용히 갈라진다 |
| 직렬화가 이상한 값에 안 깨지는가 | 골든 파일 테스트 — 제어 문자, 짝 없는 서로게이트, `NaN`, 아주 긴 문자열, 이진 본문 |
| 재생이 결정론적인가 | 같은 기록을 두 번 재생해 결과가 같은지 |
| 🔴 **화이트리스트가 진짜 막는가** | LLM을 **가짜로 갈아끼우고**, `src/test/**` 를 고치려는 패치가 거부되는지 |
| 성능 | 붙임/뗌 비교 (§10) |
| **Java 17에서도 도는가** | 🔴 demo-app을 CI에서 **17·21·25 셋 다** 돌린다. 「17로 컴파일」과 「17에서 실행」은 다른 일이다 |

### §11-1 🔴 심은 버그로만 성공을 재지 않는다

⚠️ **자기가 심은 버그로만 측정한 성적표는 면접관이 바로 알아본다.**

- 심을 버그 목록을 **먼저 문서에 고정**하고 그다음에 고리를 돌린다 (나중에 고르면 유리한 것만 고르게 된다)
- 🔴 **오픈소스 스프링 프로젝트의 실제 이슈 3건**을 가져와 돌려 본다.
  **진짜 버그 3건이 심은 버그 20건보다 낫다**

## §12 붙이는 법

```bash
./gradlew :hindsight-agent:shadowJar          # build/libs/hindsight-agent.jar
java -javaagent:hindsight-agent.jar \
     -Dhindsight.config=./hindsight.properties \
     -Dhindsight.key.file=./key.txt \
```

- Docker에서는 `JAVA_TOOL_OPTIONS` 로 넣는다. IntelliJ 실행 구성 예시도 README에 적는다
- 🔴 **GitHub Releases 배포는 v3 이후.** 지금은 직접 빌드해 쓴다

## §13 단계 — 각 단계가 그 자체로 완결된다

### v0 — 고리 전체, 바이트코드 없음 (3~4주)
모듈 셋: `hindsight-model` · `hindsight-core` · **진짜 `demo-app`**
(`core` 안에 `store`·`privacy`·`replay`·`guard`·`brain`·`cli` 패키지가 생긴다)
⬜ **v0 기록기**는 따로 모듈일지 demo-app 안의 패키지일지 만들 때 정한다 (§3)

- 기록은 `Filter` + `DataSource` 감싸기로. ByteBuddy·셰이딩·클래스로더 **없음**
- 오라클(§6-1) 셋, `DIVERGED`(§6-2), 과적합 네 겹(§7-2), 화이트리스트(§7-1)
- 측정 하네스(§10), 왕복 테스트(§11)
- **끝났다는 기준**: 심어 둔 버그가 터지면 → 기록이 남고 → 실패하는 테스트가 생기고 →
  LLM이 고치고 → 네 겹을 다 통과하고 → **PR이 하나 올라온다.** 사람 손 없이
- ✅ **여기서 3분짜리 데모 영상이 나온다.** 그게 면접을 만드는 물건이다

### v1 — 기록기를 진짜 에이전트로 (4~6주)
`hindsight-agent-boot`·`hindsight-agent`

- `premain`·ByteBuddy·셰이딩·격리 클래스로더·부트스트랩 shim (§3-2)
- 나간 요청, 시각·난수 계측. 재생 등급 실측(§6-3)
- **v0 기록기와 같은 기록이 나오는지 대조하는 것이 회귀 검사다**
- **끝났다는 기준**: 옵션 한 줄로 아무 스프링 앱에 붙고, jar 검사(§11)가 통과한다
- ⚠️ **여기가 일정 위험이 가장 큰 구간이다.** 길어지면 v0가 이미 완결된 물건이므로 멈춰도 된다

### v2 — 넓히기 (2~3주)
JFR 연동, 요약 층, 자원·메모리 방아쇠, 오픈소스 실제 버그 3건 시험(§11-1)

### v3 — 열어주기 (2주)
`core.mcp` 패키지(코딩 에이전트용)와 — **여기서 처음으로 모듈이 하나 늘어난다** —
`hindsight-server`(화면). Spring Boot 플러그인이 모듈 단위라서 그때는 갈라야 한다.
🔴 서버는 재생도 해야 한다 —
v3의 목표가 *"재생해봐"* 이므로

### 🔴 일정에 대한 정직한 말
합계 11~15주다. 앞서 적었던 10~12주는 **한 번도 안 밀린다는 가정**이었다.
**v0+v1이 진짜 기준선이고 v2·v3는 여유가 있으면 하는 것이다.**
12주 차에 v3를 약속하는 계획은 9주 차에 버려진 저장소가 되기 가장 쉬운 계획이다.

### 나중에 (지금 설계하지 않는다)
차등 재생 · 분산 재현 · 부하 시나리오 생성 · 실측 기반 API 문서

## §14 이 설계가 하지 않기로 한 것

| 안 하는 것 | 왜 |
| --- | --- |
| 운영 배포 | §8 |
| 경쟁 상태의 완전 재현 | 연구 영역. 「의심된다」까지만 |
| 스레드 실행 순서 기록 | 위와 같음 |
| 격리 상자(sandbox) 안에서 검증 실행 | 개인 프로젝트에 과하다. 대신 환경변수를 씻고 경계를 문서화(§7-4) |
| 상용 관측 도구 대체 | 대시보드·알림·집계는 안 한다. 붙여 쓴다 |
| v0에서 바이트코드 | §2. 위험을 뒤로 미룬다 |
| 여러 요청을 한꺼번에 재생 | v2 이후. v0·v1은 요청 하나만. 그래서 §4-2에 「쌓인 상태」를 적었다 |

## §15 위험 목록

| 위험 | 어떻게 다루나 | 어디 |
| --- | --- | --- |
| 🔴 채점기가 얕은 패치를 선호한다 | 과적합 네 겹 + `DIVERGED` + 주장 자체를 줄임 | §1-1, §6-2, §7-2 |

| 성적표가 조작으로 보인다 | 버그 목록 선고정 + 오픈소스 실제 버그 | §11-1 |
